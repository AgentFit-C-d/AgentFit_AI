## 1. 확인한 흐름

1. `candidate_first_profile._source_mention`은 이미 후보 ID·원문 start/end·정확한 값·앞뒤240자를 제공한다.
2. A/B 분류 호출이 field/status와 새 인용문 및 occurrence를 다시 생성한다.
3. `_ground`가 새 인용을 원문에서 정확히 찾고, `_decision` 또는 `validate_direct`가
   해당 인용이 바로 그 후보 위치를 덮는지 확인한다.
4. A는 추가 의미 축/mentionKind 일관성을, B는 field/status 일관성을 검사한다.
5. 허용된 후보만 공통 `project_candidate_profile`로 변환된다. 모든 후보 sidecar는 보존된다.

따라서 원문 위치가 없는 것이 아니다. **이미 주어진 위치 대신 모델이 인용을 재생성하는 단계**에서

## 4. 인용만 보완하는 안의 위험

B의 C004–C007은 같은 제목 인용을 반환했다. 서버가 후보 위치로 인용을 채워 넣고
기존 confirmed를 그대로 허용하면 C005–C007은 복구되는 대신 C004 오확정도 통과한다.
이것은 저장 응답과 현재 gate 규칙에서 도출되는 **예상 반례**이며 수정 모델의 실측 결과가 아니다.
이번에는 변경 후 점수나 새로운 성공률을 생성하지 않았다.

따라서 `mentionLocated`(원문에 있는 위치), `contextBound`(판단 문맥 연결),
`semanticDecision`(해당 필드의 사실인지)를 분리해야 한다.
기존 응답의 anchor를 복구하더라도 과거 보류를 자동 확정으로 올리는 후처리는 금지한다.

  이 가설은 저장 응답 분석으로 입증되지 않는다.
- 미확인: 새 관계 계약의 실제 모델 정확도, 일반 문서 성능, 독립 사람 정답 검토, 사용자 확인·저장 영향.
