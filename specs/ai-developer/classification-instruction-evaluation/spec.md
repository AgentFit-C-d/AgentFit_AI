# 분류 지침만 바꾸는 단위 ID 비교 명세

2026-10-01 · **평가 설계 초안 / 실행 미승인 / 새 모델 호출 0회**

## 목적과 범위

사용자가 요청한 두 혼동을 줄이는지 비교한다.

1. 지원 플랫폼·호환 대상과 제품이 실제로 연결하는 외부 서비스.
2. 외관·품질을 설명하는 표현과 제품이 제공하는 구체적인 동작.

U(단위 ID + 기존 분류 지침)를 기준선으로 유지한다. U+C는 같은 U 요청에
`classification-guidance-draft.txt`의 분류 설명만 덧붙인다. 새 관계 검증기,
분류 축, 모델 단계, 재검토·수정 호출은 만들지 않는다. 서비스·Spring·배포 변경과
큰 goal 재개는 범위 밖이다. 이번 산출물은 명세·평가안·정답 초안이며 실행 코드가 아니다.

## 확인한 기준선

- 코드 기준: `096cfa4`의 실험. 실제 Q/U 호출 당시 코드는 `ef0ac09`.
- 보존 자료: `E:/AgentFit/output/b-evidence-selection-v1/`.
- linkding의 U: 후보68개, 인용 결함2개, 승인 정답10개 중 모델 오확정3개/
  서버 gate 통과 오확정3개, 정상6개 누락0개, 전체 보류32개, 9호출/457.014초.
- 잘못 통과한 항목은 Firefox·Chrome·Clean UI. 태그 정리 기능은 정상 복구됐다.
- **이 수치는 새 문서의 U 결과가 아니다.** 새 문서의 두 arm 결과는 모두 미측정이다.

## 분류 기준

| 관계/표현 | 정답을 정하는 원칙 |
| --- | --- |
| 지원 OS·브라우저·기기 | 사용자가 제품을 실행하거나 접근하는 호환 대상이라는 사실만으로 외부 연동, 구현 기술 또는 배포 기술로 올리지 않는다. 현재 10개 필드에 해당하지 않으면 `other/irrelevant`. |
| 실제 외부 서비스 | 대상 제품이 이름이 특정된 별도 서비스와 운영 중 데이터를 주고받거나 인증 등 기능을 이용한다는 문맥이 있어야 `external_integrations/confirmed`. 이미 지원하는 선택형 연동은 모든 사용자의 필수 설정이 아니어도 유효하다. |
| 프로토콜·형식 | 실제 연동 기능이 있더라도 프로토콜 이름 자체를 서비스 제공자로 바꾸지 않는다. 기능 동작과 서비스명을 각각 해당 후보의 범위에서 판단한다. |
| 배포처·기부처·개발 도구 | 그 문맥만으로 실행 중 제품의 외부 연동을 추론하지 않는다. 이름의 전역 금지 목록은 만들지 않는다. |
| 외관·품질 설명 | 보기 좋음·가독성·빠름·안정성 등 평가만 있고 동작이 없는 후보는 `other/irrelevant`. `Features` 제목 아래에 있어도 동일하다. |
| 정상 기능 | 원문이 동작·모드·자동 처리·입출력이나 상태 변화를 명시하면 `features`. 명사구, UI 기능, 백그라운드 기능도 인정한다. 버튼 이름·명령형 문장·실행 완료 증명을 추가로 요구하지 않는다. |
| 혼합 문장 | 같은 문장 안의 외관 설명과 실제 기능을 선택된 정확한 범위로 구별한다. 인접한 기능 때문에 외관 후보를 기능으로 바꾸거나, 외관 수식어 때문에 정상 기능을 버리지 않는다. |
| 애매함·충돌 | 원문 전체와 해당 구역을 함께 보고 필드 또는 현재 범위가 불명확하면 `tentative`로 보존한다. 후보·근거를 삭제하지 않는다. 알려진 필드는 유지하고 정할 수 없을 때만 `other`. |

기존 대상 프로젝트·시점·부정·계획·상충 근거 기준은 유지한다. 문서에 확정된 요구사항은
아직 미구현이어도 확정 가능하며, 제공 중인 선택 기능과 검토 중인 선택안을 혼동하지 않는다.
모델의 `confirmed`는 사용자 승인이나 저장 완료를 의미하지 않는다.

## 비교에서 고정할 것

| 항목 | 양쪽에 동일하게 적용 |
| --- | --- |
| 기준선 | 기존 `build_pair(...)[payloads][U]`와 U 정규화/gate |
| 변경 허용 범위 | U+C의 system message 끝에 분류 지침 파일 내용을 LF로 한 번 추가 |
| 모델 | `deepseek-ai/deepseek-v4.1-flash` / NVIDIA의 기존 endpoint |
| 설정 | temperature=0, thinking=false, max_tokens=8192, 후보8개/배치 |
| 응답 규격·순서 | `id → field → supportUnitIds → counterUnitIds → status`; properties와 required 순서까지 동일 |
| 입력 문맥 | 문서 원문 전체 + 후보별 앞뒤240 Unicode code points + 문서 전체 줄 단위 목록/원래 heading 링크. 양쪽 user message 바이트 동일. |
| 근거 계약 | 전체 source SHA256와 start/end 기반 ID, 지원/반대근거 각각 최대8단위·4000자, 원 후보 전체와 비제목 후보 줄 포함 |
| 입력 상한 | 원문24000자·1000단위. 초과 시 문맥 축소 없이 계획 재검토 |
| 검증 | unknown/foreign/중복 ID, 잘못된 span, 근거 부족에 대한 기존 처리 유지. 퍼지 보정 없음. |
| 보존 | 양쪽 같은 후보·순서·원문·정답. 출력 누락/호출 실패도 분모에서 빼지 않음. |
| 금지 | 이름·문서 ID 예외, 정답/리뷰 이유를 모델 입력에 주입, 후처리로 의미 변경, 추가 모델 호출, 평가 후 정답 완화 |

선택된 근거 ID는 모델 출력이므로 arm마다 달라질 수 있다. **제공하는 단위 목록과
검증 방식**을 고정한다. 지침 추가에 따른 토큰 증가도 실험 효과의 일부로 기록한다.

## 데이터 분리

- 개발용: 기존 linkding68개/승인 gold10개와 `development-contrasts.md`의 합성 대조 사례.
  기존 원본 및 Q/U 결과를 덮어쓰지 않는다. 새 평가 점수와 합산하지 않는다.
- 별도 문서: Fluent Reader와 LocalSend의 공식 README 전체. commit·원본 byte hash·라이선스를
  `sources.json`, `sources/`에 고정했다. 수집은 공개 문서 다운로드이며 모델 호출이 아니다.
- 후보32개(각16개)는 **원문에서 사람이 검토할 수 있게 선정한 진단용 후보**다. 추출 모델로
  새로 만들지 않았다. 이 비교는 고정 후보의 분류 실험이며 문서 전체 추출 재현율 평가가 아니다.
- 정답 초안: `gold-draft.json`, 검토용 `gold-review.md`. 명확 초안30개는 정상16개,
  범위 밖13개, 명시적 부정1개. 추가2개는 사람 검토 필요로 주 정확도 점수에서 제외한다.
  두 항목 모두 후보·원문·출력과 전체 보류 분모에는 남긴다.
- 기존 `specs`와 `work/harness`에서 두 제품의 사용 기록을 검색했으나 찾지 못했다.
  현재 설계자가 문서를 읽고 정답 초안을 만들었으므로 완전 블라인드 검증은 아니다.
  전체 과거 비공개 기록 및 모델 사전학습 노출 여부는 확인하지 못했다.
- 새 README 2개만으로 다른 문서 전반의 실사용 품질을 보장하지 않는다.

## 이번 종료 조건

평가안·분류 지침 초안·정답 초안을 사용자에게 보여주고 종료한다. 원문 hash·위치·후보 수 등
자료 무결성만 로컬 확인한다. 지침을 실제 payload에 연결하거나 모델을 호출하지 않는다.
후속 실행은 정답 검토와 별도 실행 요청 이후다. 이전 한 쌍의18회 승인은 이미 사용했으며
이번 계획에 추가 호출 권한으로 이월하지 않는다. 무료 확인이 유효하지 않으면 호출하지 않는다.
