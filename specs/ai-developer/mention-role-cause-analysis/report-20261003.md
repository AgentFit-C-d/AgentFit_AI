## 결론과 우선순위

- **확인:** 현재 enum으로 정상 긍정 사실 10개 필드 모두를 모순 없이 표현할 수 있다. 프로젝트명·유형·도메인은 `mentionKind=other`, 해당 field, `role=product_fact`로 표현 가능하다. 새 역할이나 스키마가 필요한 상태는 아니다.

### 확인된 지침 공백과 한계

1. 기존 [역할 명세](E:/AgentFit/tmp/worktrees/document-input-runtime/specs/ai-developer/mention-role-classification/spec.md)는 `other=기존 다른 Profile 필드`를 명시하지만, 전달 지침에는 “Other Profile fields keep their existing definitions.”만 있다. 스키마 description은 “a different Profile field”를 제시하므로 완전한 표현 불능은 아니다.
2. 분류 지침의 “Use other for facts outside the ten fields.”는 field 이름을 붙이지 않는다. `field.other`와 `mentionKind.other`가 같은 단어여서 혼동 여지가 있다. 엄밀히 양립 불가능한 정의라고 확정하기보다는 **대상 차원의 불명확성**으로 분류한다.
3. external_service는 “named outside provider/service itself”로 정의돼 있고 field 지침에는 “the product integrates with”가 있다. 그러나 호환 Client·설정 출력 대상과 인증/데이터 제공자를 직접 구분하지 않는다. 제품명이 붙었다고 외부 제공자라는 해석을 허용할 필요는 없다.
4. 프로젝트명이라는 명사와 그 제품이 문장의 주어로서 수행하는 동작을 혼동할 수 있다. 현재 지침은 action을 요구하므로 이름 자체를 product_operation으로 분류한 원시 출력은 그 구별을 지키지 못했다.

### AgentFit

소개 원문: “AgentFit은 개발 초보자가 자신의 프로젝트에 어떤 AI 개발 도구와 설정이 필요한지 판단하고, 실제로 사용할 준비를 하도록 돕는다.”

- 추출된 정확한 이름 위치가 분류 모델 입력에 있다. 대표 사례의 최초 문제를 추출 누락이나 후처리 임의 삭제로 볼 근거는 없다.
- 제목/소개에서 원시 `field=project_name`, `mentionKind=external_service`, role=product_fact 등 축은 긍정으로 나왔다. external_service는 대상 자체가 아닌 outside provider여야 하므로 역할이 잘못됐다.
- 마지막 요약의 `mentionKind=product_operation`도 후보가 이름 자체이므로 동작 역할과 맞지 않는다. 서버는 불일치를 정확히 보류했다. 서버가 정답 역할의 project_name을 거절했다는 사례는 아니다.
- v2 제목과 소개는 잘못된 역할 외에 유일한 소개 문장을 occurrence=1로 지정했다. 제목 후보에 제목 인용 자체는 유효하지만 추가 인용이 틀려 groundingValid=false였다. 이 두 행에서 `_decision`이 먼저 적용한 것은 grounding 실패다. 역할 규칙만의 손실로 세면 안 된다.
- v2 최종 project_name=null이며 이름 확인 후보는 남았다. v3는 검토 실패 후 failed여서 최종 이름 상태는 미측정이다.

추가 관측: `[6764,6769)`의 “웹 서비스”는 v2에서 external_service라 보류, v3에서 mentionKind=other지만 의미 축 role=non_product라 제외됐다. 이는 **mentionKind와 role 축의 혼동을 함께 설명해야 할 이유**다. 이번 최소 8후보의 주 비교에는 추가하지 않고 별도 관측으로 남긴다.

문서에는 팀 설명용 가상 예시도 있다. 그 주변 AgentFit/다른 프로젝트 언급 전부를 동일한 정답으로 처리하지 않았다. 대상 주체/예시 주체가 애매한 발생 위치는 사람이 검토해야 하며 주 비교에 포함하지 않는다.

### Codex

원문 `[4006,4067)`: “초기 지원 Client는 Codex 중심이며 Catalog는 팀이 검증한 약 15~20개 도구를 목표로 한다.”

- 실제 입력에는 이 문장과 전체 문서가 있다. 두 원시 출력 모두 external_integrations/external_service/confirmed, target/current/positive/adopted/product_fact, conflictsChecked=true, counterEvidence=[]였다.
- 인용은 유효하지만, 이 문장은 설정·호환성의 지원 대상을 정한다. Codex의 인증/데이터 서비스를 제품이 사용하는 관계를 명시하지 않는다. 기존 골드의 external_integrations는 GitHub다.
- **최초 오류: 의미 분류.** 서버 허용 조합을 잘못 짠 사례가 아니라, 의미적으로 잘못된 축들이 구조적으로 일관돼 통과한 사례다. 필드·역할 조합표만 강화해 같은 정상 외부 서비스까지 막는 것은 적절하지 않다.
- v2 GLM 요청24의 checkedCandidateIds에는 C082가 있고 wrongCandidateIds에는 없다. 최종 external_integrations=[GitHub,Codex]로 남았다. 이는 후속 검토의 놓침이다.
- 검토 입력에는 field/status와 원문 위치·문맥이 있고, 원시 mentionKind/축은 없다. 검토 지침에도 outside provider라는 축약 정의와 필드 정의가 있으나 Client/provider 대비는 없다. 그것이 놓침의 유일 원인인지는 미확인이다.
- v3는 첫 GLM 요청에서 실패했다. Codex에 대한 GLM 재검토 결과나 최종 Profile 통과가 반복됐다고 주장할 수 없다.

### GitHub 정상 연동과 인용 오류

“GitHub 로그인만 제공하고 저장소 권한은 요청하지 않는다.”는 인증 연동을 긍정하고 별도의 저장소 접근 권한을 부정한다. 두 명제를 서로 상충으로 판단하면 안 된다.

두 실행의 흐름도 로그인 후보는 올바르게 supported다. v2 필수 범위 후보도 통과했고 최종 GitHub가 보존됐다. v2 정책 후보, v3 필수 범위/정책 후보는 **여러 인용 중 하나의 occurrence가 존재하지 않아** groundingValid=false였다. 하나의 유효한 인용이 있어도 현재 검증기는 잘못된 추가 인용을 무시하지 않는다. 이번 역할 지침 개선 점수에 인용 개선을 섞지 않고 별도 계수한다.

### 별도 서버 정책 문제: tentative/proposed

추가 합성 문맥 “AtlasID 연동을 검토 중이며 채택은 미정이다.”에 external_integrations/external_service, tentative, commitment=proposed, 나머지 축은 target/current/positive/product_fact, 유효 근거를 주면 현재 `_decision`은 **excluded**다. `commitment != adopted` 분기가 마지막 tentative 보류보다 먼저 적용되기 때문이다. raw tentative는 보존된다.

반면 commitment=unclear 또는 역할 unclear, 해결되지 않은 counterEvidence가 있으면 needs_confirmation이다. 따라서 ‘정확한 역할을 응답하면 모든 미정이 자동으로 보류된다’고 주장할 수 없다. 이 추가 사례는 기존 골드에 넣지 않았으며 실제 모델 오류 건수에도 넣지 않았다. 의미 역할 설명 보완과 독립된 서버 정책 수정 후보로 남기고, 이번에는 수정하지 않는다. 다음 비교에서도 raw tentative와 server excluded를 나눠 보고해야 한다.
