# B 인용문 vs 원문 단위 ID — 실제 한 쌍 결과

2026-10-01 / 코드 `ef0ac09` / `feature/b-evidence-selection-comparison`.

## 결론

**원문 단위 ID는 근거 위치 오류와 정상 누락을 줄였다. 모델의 의미 오확정은 그대로였으며,
잘못된 확정이 서버 판정 gate를 통과하는 수는 늘었다. 현재 결과로 서비스에 적용하지 않는다.**

Q는 기존 B의 인용문 방식, U는 같은 B 분류 기준의 단위 ID 방식이다.
과거 다축 A와 직접 분류 B를 다시 비교한 실험이 아니다.

## 요청한 핵심 사례

| 후보·정답 | Q 모델 제안 → gate | U 모델 제안 → gate | 판단 |
| --- | --- | --- | --- |
| C005 태그 정리 / features | features·confirmed → 보류 | features·confirmed → supported | **정상 기능 복구** |
| C004 Clean UI / Profile 제외 | features·confirmed → 보류 | features·confirmed → supported | **오확정 통과 증가** |

- Q의 두 후보는 `support: []`였다. 근거가 없어 보류됐지만 원래 모델의 confirmed는 그대로 기록돼 있다.
- U의 C005는 원문 `- Organize bookmarks with tags\n`의 정확한 단위 `[563,594)`를 선택했다.
- U의 C004는 원문 `- Clean UI optimized for readability\n`의 정확한 단위 `[526,563)`를 선택했다.
  위치는 맞지만 외관 설명을 제품 기능으로 판단한 의미 오류가 남았다.
- 추가로 정상 프로젝트명 linkding(C001)이 보류→supported로 복구됐다.
- Django·JavaScript·PWA·Internet Archive는 양쪽 모두 올바른 필드로 supported였다.
- Firefox·Chrome을 외부 서비스로 보는 오확정은 양쪽 모두 통과했다.
- 따라서 모델 자체 오확정3건은 두 방식 모두 Firefox·Chrome·Clean UI다. Q에서는 Clean UI가
  인용 부족으로 막혔고 U에서는 해당 차단이 사라졌다. 분류 기준이나 정답을 바꿔 숨기지 않았다.
