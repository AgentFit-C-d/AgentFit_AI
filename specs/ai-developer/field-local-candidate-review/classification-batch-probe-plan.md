# 한정 진단: 실패한 분류 요청을15후보씩 분할

## 목적과 선택

GLM의30후보 분류 세 번째 호출(C060~C089)이600.008초 뒤 전송 미완료로 종료됐다. 이미 종료한 실행·자료·점수를 보존한다. 사용자 자율 진행 승인하에, 제품 코드를 바꾸지 않는 작은 진단으로 출력 판단 범위를 줄였을 때 해당 후보를 끝까지 분류할 수 있는지 확인한다.

실패한30후보를 같은 순서로 C060~C074, C075~C089 두 묶음으로만 나눈다. 원문 전체, 각 후보의 정확한 위치·문맥, explicit-v1 지침, 모델별 기존 adapter 설정, 출력8192토큰, 호출600초를 유지한다. 이 진단은 배치 크기 변경과 실행 시점 차이를 포함한다. 한 번의 성공을 실패 원인 규명·반복 안정성으로 간주하지 않는다.

전체 문서 재실행이나 시간 상한 확대보다 먼저 이 범위에서 완료 여부를 확인한다. 새로운 분류 지침은 추가하지 않는다. 과거 GLM 첫2묶음의 라벨은 보관되지 않았으므로 재사용하거나 정답으로 채우지 않는다.

## 사전 지정 입력·관측

- 기존 분류 freeze와 원문·173후보 snapshot에서 위30개만 선택한다. 각 묶음15개/ID순서/출처 hash를 새 freeze에 기록한다.
- 순서:첫 묶음 DeepSeek→GLM,둘째 묶음 DeepSeek→GLM,각1회. 새 결과 폴더 classification-batch15-probe-v1, 기존 파일 덮어쓰기0.
- 기존 `classify_profile_candidates`는15개 입력이면1회 호출한다. 공개 API·기본 서비스·제품 Python 파일 변경0.
- 첫 묶음의 지정 동작 C061/C066/C069/C071/C073이 features/confirmed인지 개별 집계한다. 나머지 모든 후보는 ID·field·status와 이전 라벨 대비 변화로 기록한다. 전체30개를 모두 사람이 채점한 것으로 간주하지 않는다.
- 완료 여부와 함께 안전한 provider_error, elapsed_ms, response_bytes를 기존 analysis_call_metadata 계약으로 기록한다. 실패를 점수0으로 뭉개거나 부분 라벨을 완료 Profile로 사용하지 않는다.
- 후보 이름·답·기존 분류는 모델 입력에 추가하지 않는다. 결과에 원문·원본 응답·키·예외 자유 텍스트를 기록하지 않는다.

## 예산·검증·중단

- 최대4모델 호출,재시도0. 각 자식660초/모델 호출600초,전체2640초 상한. 각 묶음/모델은1회 호출만 허용한다. 무료 범위·만료·파일 hash를 호출 전 검사하며 거절·제공자 오류·계약 오류가 나면 나머지 실행을 중단한다. 유료 대체·자동 재시작0.
- 이전 실행기 안의 무료 접근 검사는18회 예약을 보수적으로 확인한다. 실제 새 진단은 고정된4개 요청 각각1회로 제한한다. 예약 수가 실제 사용량·계정 잔량이라는 뜻은 아니다.
- 로컬 각180초/API0:분할15개가 원래30개와 정확히 같음,모델 간 입력/지침/스키마 동일성과 기존30개 대비 지침 불변,제공자 오류 코드·비밀 비노출,무료 거절0호출,부모 결과/메타데이터 검증.
- 실행 전 새 계획·실행기·원문·후보·코드 hash를 고정한다. 기존 결과 hash는 시작/종료 후 대조한다. 현재 종료한38073을 재실행하지 않는다.

## 후속 판단

완료와 지정 기능 분류가 개선되면15개 묶음의 전체 문서 비교를 별도 등록한다. 한 묶음의 통과를 실사용 판정이나 모델 전면 교체 근거로 삼지 않는다. 실패하면 안전한 오류 코드를 근거로 전송·출력 계약·의미 판단 중 어느 문제인지 구분하고, 조건을 바꿔 반복 호출하지 않는다. 필드 해석·새 문서·사람 수정 부담·실제 Spring·운영 gate는 그대로 남는다.
