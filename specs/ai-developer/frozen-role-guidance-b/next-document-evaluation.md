  개발 문서이므로 이 한 번으로 다른 문서에 대한 일반화를 주장하지 않는다.
- 현재 코드·의존성·전체 실행 파일·원문·골드·모델·지침·스키마·실행 설정을 새 폴더에 동결한다.
- integrated-nvidia, nvidia_only=True, confirmation-v3를 명시한다.
  원문부터 추출→원문 연결→분류→검토→기능 정리→최종 응답을 새로 실행한다.
  과거 후보·응답·골드를 모델 입력에 주입하지 않는다.
- 기존 DeepSeek/GLM만 사용하되 실행 직전 무료 조건을 확인한다. 별도 실제 실행 승인을 받는다.
  제안 제한은 이전과 같은 총50회·1800초·요청당600초·재시도0이다.
  남은 시간보다 짧은 요청 제한과 종료 여유를 유지하고 첫 실패에서 멈춘다.
  이 제한으로 완주를 보장하지 않으며 시간 초과·실패도 결과로 보고한다.

## 2. 측정과 비교

- 전체 완료 여부: 최종 v3 응답 생성/검증 여부, 실패 단계·진단, 실행하지 않은 범위.
- 10개 필드: 기대값·실제 값·상태 및 원문 근거. 모델 판단·서버 처리·사용자 승인을 구분한다.
- 같은40개 의미: 보존·명시 보류·누락·사람 검토, 최종 긍정 오답.
  기능 문자열 개수와 세부 의미 개수를 별도로 센다.
- 이름·유형·도메인·정상 인증 연동·지원 Client 오분류, 텍스트 입력 연결,
  재접속 유지·정보 부족/후보 없음 처리를 후보 발생 위치별로 추적한다.
- 후보 추출 누락·위치 연결 실패·분류 오류·검토 손실·후처리 손실을 구분한다.
- 단계마다 입력/출력 후보 수·모델 호출 수·실패 수·요청별 시간·시간 합계와 전체 벽시계를 기록한다.
  제공자 응답 시간과 rate limit 대기 시간을 기록에서 구별할 수 없으면 미확인으로 둔다.
- 확인 후보 수·질문 수를 함께 비교해 모두 보류하는 결과를 개선으로 세지 않는다.
- 비교 대상: 과거 완주v2, 과거 실패v3, 새 B 실행을 별도 열로 둔다.
  실패v3의 미생성 최종 점수를0으로 채우지 않으며 오프라인 재생은 별도 표로 둔다.
  반복1회·여러 코드 수정·응답 변동이 함께 있으므로 단독 인과 효과나 재현성을 확정하지 않는다.

## 3. 약29분 병목을 줄일 순서 — 별도 승인 후 한 변수씩

저장된 실제 요청 메타데이터 기준:

| 단계 | 완주v2 | 실패v3 |
|---|---:|---:|
| 일반 추출 | 2회 / 81.279초 | 2회 / 97.592초 |
| 동작 추출 | 1회 / 106.679초 | 1회 / 250.668초 |
| 의미 분류 | 19회 / 804.278초 | 20회 / 1072.452초 |
| 의미 검토 | 3회 / 768.565초 | 1회 / 302.263초, 실패 |
| 전체 벽시계 | 25회 / 1762.135초 | 24회 / 1724.336초 |

1. 먼저 위 새 기준선에서 완주·역할 분류·정상 정보 보존을 확인한다.
   이전 실패v3 시간은 완주 시간이 아니다.
2. **의미 분류**부터 검토한다. 후보8개씩 직렬 호출하는 비용과 원문 반복 제공량을 측정한 뒤,
   문맥·스키마·분류 기준을 유지하는 묶음 크기 조정을 별도 비교한다.
   호출 감소가 인용 오류·누락·확인 부담을 늘리지 않는지 같은 정답으로 검사한다.
3. **GLM 검토**의 후보 검토와 원문 누락 검토를 나눠 확인한다.
   완주v2의 원문 누락 검토만 약413초였다. 출력·추론 예산 또는 검토 묶음 조정은
   별도 실험으로 비교하고 v3 보류 안전장치는 유지한다. 검토 제거를 먼저 하지 않는다.
4. 이후 동작 추출의 출력 크기와 위치 연결 실패를 평가한다.
   현재 기록에서 요청 외 시간은 약1.5초이므로 로컬 투영 최적화의 우선순위는 낮다.
5. RPM 상향과 제한된 병렬화는 실제 rate-limit 대기 근거·호출 및 전체 시간 제한 보장을
   확인한 다음 검토한다. RPM만 올리면 단일 요청 생성 시간이 줄어든다고 가정하지 않는다.

실제 개선 결과가 아니다. 이번 작업에서는 위 변경이나 실제 요청을 실행하지 않았다.
