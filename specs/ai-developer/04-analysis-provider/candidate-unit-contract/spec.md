# 후보 구역 계약 실험 명세

## 목적

후보 생성 모델이 중복 `unitId`를 반환하거나 인용문을 다른 구역에 붙여 전체 문서가 실패하는 문제를 줄인다. 서버의 정확한 원문 위치 검증을 유지하고, 모델이 원문에 없는 문구를 만든 경우에는 계속 실패시킨다. 이 변경은 opt-in 평가 경로에서만 실험한다. 기본 분석기와 공개 Profile에는 적용하지 않는다.

## 근거

[진단 기록](diagnosis.md)의 E01은 배열 내 중복 ID, E03·E04는 인접 구역의 정확한 문구를 잘못된 ID에 넣은 사례다. 인접 문맥을 제거한 대조 실험은 유효성과 정답 문구 회수율을 높이지 못했다.

## 계약

1. **ID 구조 보장:** 후보 응답은 배열 대신 `units` 객체를 사용하며, 요청 묶음의 각 `unitId`를 정확히 하나의 필수 속성으로 둔다. 다른 ID와 누락은 strict JSON schema 및 서버 검증에서 거부한다. 각 속성의 값은 현행 인용 문자열 배열이다. 묶음 크기는 기존 `batch_sections` 규칙을 유지한다(고정 합성 자료에서는 호출당 3개 구역). 구역당 최대 30개 인용, 인용 길이와 총 후보 120개 제한도 유지한다.
2. **원문 위치 복원:** 모델이 선택한 구역의 `text`에 인용이 있으면 현행 위치 계산을 따른다. 없으면 문서 전체에서 **정확히 하나의 구역**에 그 문자열이 존재할 때에만 해당 구역으로 옮긴다. 같은 구역 내 반복 등장은 현행 `expand_occurrences` 규칙대로 모두 펼친다. 여러 구역에 걸쳐 같은 인용이 나타나거나 원문 어디에도 없으면 `ANCHORED_CANDIDATE`로 거부한다. 이동 후 같은 구역·인용이 중복되면 한 번만 보존한다. 인용 문자열을 번역·정규화·수정하거나 의미로 위치를 추론하지 않는다.
3. **원자성:** 모든 묶음의 응답을 모아 위 규칙을 검증한 뒤 후보 ID와 span을 확정한다. 어느 묶음이든 실패하면 부분 후보를 성공으로 반환하지 않는다. 최종 후보는 원문 위치 순으로 정렬해 안정적인 ID를 부여한다. 모델이 생략한 사실을 서버가 새로 만들지는 않는다.
4. **실험 범위:** 기존 합성 8건을 동일한 Solar Pro4 설정으로 평가한다. 현행 배열 계약과 새 계약을 각각 실행해 유효 문서 수, 정답 문구 span 회수, 원문 불일치·모호성·중복·ID 오류, 호출 수와 지연을 기록한다. 키, 벡터, 실제 문서, 원본 응답은 결과 파일에 저장하지 않는다.

## 사전 성공 관문

- 새 계약은 합성 8건에서 문서 8/8 유효, 정답 문구 27/27 회수, 원문 밖 인용·모호한 이동·부분 성공 0건이어야 한다. 동일 입력의 현행 계약보다 유효성과 회수율이 낮아지면 실패다.
- 후보 단계는 문서당 최대 2회 호출, 전체 서비스는 기존 최대 6회·60초를 유지할 수 있어야 한다. 평가에는 호출 수와 지연을 기록한다.
- 이 관문을 통과해도 합성 튜닝 자료이므로 기본 분석기에 자동 적용하지 않는다. 별도 고정 평가와 전체 Profile 품질 확인이 필요하다.

## 대안과 선택 이유

- 인접 문맥 제거: 실제 일회성 비교에서 더 많은 오류와 정답 누락이 나와 선택하지 않았다.
- 구역별 단독 호출: 구역이 6개인 문서에서 후보 단계만 6회가 되어 전체 6회 예산을 소진한다.
- 모델 출력값을 무조건 신뢰하거나 불일치 문구를 유사 문자열로 보정: 원문 근거 계약을 깨므로 허용하지 않는다.

## 비목표

필드·역할·확정 여부 판단 개선, 임베딩 검색, 공개 API 변경, 실패 원본 보관 정책 변경, 실제 문서 전송은 이 실험에 포함하지 않는다.
