# 후보 구역 계약 실험 결과

## 고정 비교

기존 임베딩 실험에서 만든 합성 다구역 문서 8건(정답 문구 27개)에 Solar Pro4 후보 생성을 적용했다. 문서별로 기존 배열 계약과 새 ID별 객체 계약의 실행 순서를 번갈아 바꿨다. 새 계약은 기존과 같은 원문·인접 문맥·모델 설정을 사용했고, 정확한 원문 문자열이 유일한 다른 구역에 있을 때만 위치를 옮겼다. [실행 계획](results/run1/plan.json), [문서별 지표](results/run1/results.json), [집계](results/run1/summary.json).

| 지표 | 기존 배열 계약 | 새 ID별 계약 |
| --- | ---: | ---: |
| 유효 문서 | 4/8 | 8/8 |
| 유효 문서의 정답 문구 회수 | 12/13 | 27/27 |
| `ANCHORED_CANDIDATE` 실패 | 4건 | 0건 |
| 문서당 최대 후보 호출 | 2회 | 2회 |
| 후보 단계 지연 중앙값 | 2,000ms | 1,898.5ms |
| 관측 p95 지연 | 12,000ms | 5,609ms |

새 계약은 E03·E04에서 잘못 배정된 인용 각 2개를 정확한 구역으로 옮겼다. E04에서는 이동 후 중복 2개를 합쳤다. E01은 필수 키 구조 덕분에 모든 구역을 반환했다. 새 계약의 정답 문구 27/27개와 유효 문서 8/8건, 원문 불일치 0건, 최대 2회 호출은 사전 관문을 통과했다. 이 결과에서 기본 분석기 반영은 하지 않았다.

## 진단 지표 보완 실행

독립 리뷰에서 run1의 기존 방식 실패 원인이 `ANCHORED_CANDIDATE` 하나로만 저장된 누락을 확인했다. run1의 결과는 수정하지 않았다. [사전 보완 기록](results/run2-note.md)에 따라 실패 응답을 메모리에서 분류하는 진단 옵션만 추가해 같은 조건으로 run2를 실행했다. [run2 집계](results/run2/summary.json)와 [문서별 지표](results/run2/results.json)를 별도로 보존한다.

| 지표 | run2 기존 배열 계약 | run2 새 ID별 계약 |
| --- | ---: | ---: |
| 유효 문서 | 5/8 | 8/8 |
| 유효 문서의 정답 문구 회수 | 17/17 | 27/27 |
| 실패 세부 원인 | ID 중복·누락 1건, 다른 구역 인용 2건 | 0건 |
| 문서당 최대 후보 호출 | 2회 | 2회 |
| 후보 단계 지연 중앙값 | 2,054.5ms | 1,921.5ms |
| 관측 p95 지연 | 11,969ms | 14,515ms |

run2에서도 새 계약은 8/8건 유효·27/27개 회수로 사전 관문을 통과했다. 기존 계약의 세 실패 원인은 `id_coverage` 1건과 `wrong_unit` 2건이었다. run1의 네 실패 원인은 당시 분류하지 않았으므로 추정하지 않는다. run2의 새 계약 p95가 기존보다 길어 지연 개선은 입증되지 않았다.

## 검증과 제약

- 테스트 우선으로 ID별 스키마, 원문 위치 복원, 모호한 인용 거부, 반복 위치, 120개 한도, 부분 결과 거부, 평가 결과의 안전한 출력과 호출 수를 확인했다.
- 리뷰 지적을 재현한 두 회귀 테스트는 수정 전 `diagnose` 미지원으로 실패했고, 수정 후 통과했다. 수정 후 전체 `unittest` 344건이 통과했다.
- 기존 방식은 run1에서 4/8건, run2에서 5/8건 유효했다. 모델 응답 변동이 있으므로 두 번의 교차 비교만으로 안정적인 실패율이나 지연 차이를 추정할 수 없다. 각 p95는 문서 8건의 관측 최대치다.
- 이 자료는 튜닝에 사용한 합성 문서다. 새로운 기획서, 긴 실제 문서, 최종 Profile의 필드·역할·확정 여부 판단 품질은 검증하지 않았다. 서버 전체의 6회·60초 예산을 실제 서비스 경로에서 확인하지도 않았다.
- 기본 분석기, 공개 Profile, 실패 원본 보관 정책은 변경하지 않았다. 실험 결과에는 키·원본문서·인용 문자열·원본 API 응답을 저장하지 않았다.

**판정:** 이 합성 자료에서 후보 구역 계약의 구조 오류는 줄었으며 사전 관문을 통과했다. 기본 서비스에 적용하려면 별도 고정 자료와 전체 Profile 품질 평가가 필요하다.
