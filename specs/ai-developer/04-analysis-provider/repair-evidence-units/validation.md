# 검증 결과

## 수정 단계 비교
Solar Mini 4, 상태 v2·값 경계 v2를 사용했다. 수정 단계는 최대 4096토큰·40초이며 전체 분석의 6회·60초 한도는 그대로다.

| 평가 | 설정 | 통과 |
| --- | --- | --- |
| 기존 상태 13건 × 3 | 단위 분리 + none | 33/39 |
| 기존 상태 13건 × 3 | 단위 분리 + low | 39/39 |
| 문제 4건 진단 | 기존 구역 + low | 4/4 |
| 새 대조 9건 | 기존 구역 + low | 9/9 |
| 같은 새 대조 9건 | 단위 분리 + low | 7/9 |

단위 분리만으로는 S02 중복 병합과 S10 잘못된 추가 선택이 남았다. low 추론을 적용하면 기존 세트의 결과가 개선됐지만, 이는 단위 분리의 효과로 단정할 수 없다. 기존 구역을 유지한 low도 문제 4건과 새 9건을 통과했다. 단위 분리 없는 상태 13건 전체의 3회 비교는 아직 하지 않았다.

분리 방식 U06은 INCOMPLETE_RESPONSE였다. 서버 분할 결과 Dr. Atlas가 둘로 나뉘므로 전체 이름을 단일 단위에서 인용할 수 없다. 응답 미완료 자체의 내부 원인은 확인하지 못했다. U09는 같은 단위 안에서 이름이 반복되어 SOURCE_REPAIR_INVALID였다. 서버의 모호한 근거 거부를 완화하지 않았다.

## 지연 및 결정
단위 분리+none의 수정 단계 중앙값은 500ms, p95는 891ms였다. 같은 세트의 low는 중앙값 4828ms, p95 28438ms였다. 반복 대기 2초는 이 지연에 포함되지 않는다. 단독 수정 지연을 전체 서비스 지연으로 해석하면 안 된다.

분리 옵션은 실험용 기본 False로 남긴다. 상태 판단과 low 추론도 기본값을 바꾸지 않는다. 기존 구역+low를 전체 흐름의 후보로 검증한다.

## 코드와 한계
전체 unittest 290건 통과. 손실 없는 오프셋, CRLF·URL·소수점, 반복 인용 검증, 400개 초과 실패, 수정 단계만 분리/low 적용, 기존 초기 추출·공개 Profile 유지 등을 검사했다. 독립 코드 검토에서 차단 문제는 없었으며 약어 과분할 위험은 실제 비교에 포함했다.

모든 결과는 짧은 합성 자료다. 39회는 서로 다른 문서 39개가 아닌 13건의 반복이다. 새 9건도 고객 기획서가 아니며 일부는 알려진 위험을 검증하도록 작성했다. 이 비교는 무작위 대규모 평가가 아니다. 독립 실제 문서·사람 수정 부담은 미검증이고 실사용 품질 달성을 주장하지 않는다. 예약 공개 문서는 열거나 전송하지 않았다.

## 전체 흐름 결과
기존 구역+상태v2+수정low는 **11/12**였다. 중앙값 14133.0ms, p95 44594ms, 최대 5회 호출이었다. N-004는 source_repair에서 INCOMPLETE_RESPONSE로 실패했고 completion_tokens=4096, max_tokens=4096이었다. 토큰 상한 소진과 응답 미완료가 함께 관측됐다. 내부 추론 내용은 보관하지 않아 소진의 구체적인 내용은 미확인이다.

첫 실행에서 회귀가 발견되어 계획의 조건에 따라 추가2회 반복은 수행하지 않았다. 성공11건은 정답과 일치했지만, 실패1건을 제외한 성공률로 보고하지 않는다. 과거 값 경계v2만의 전체36/36과 이번 설정은 상태 프롬프트와 수정 추론도 달라 직접적인 단일변수 비교가 아니다.

**결론:** 근거 단위 분리는 채택 보류한다. low는 수정 판단의 개선 가능성을 보였으나 전체 흐름에서 토큰 상한 실패와 지연 증가가 남아 채택 보류한다. 현재 기본 분석기는 그대로다. 후속은 분할 휴리스틱 추가보다 동일 입력·프롬프트에서 수정 응답 토큰 예산과 지연을 함께 비교하는 것이 우선이다. 예산 확대가60초 이내 성공을 보장하지 않으므로 별도 측정이 필요하다.
