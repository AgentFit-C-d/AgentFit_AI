# 후보 검토의 필드 의미 통일

## 목적과 근거

실사용 가능한 분석을 위해 정상 정보를 보존하면서 예시·미정·잘못된 역할은 제외한다. 이전 작업은 이름 보존 구현·실제 재생·push·CI를 완료한 progress다. H02의 동일 후보 비교에서 DeepSeek가 웹 대시보드 형태를 모두 제외했고 기능15개 중5개만 유지했다. 희소한6개 검사로는 이런 손실을 검출하지 못했다.

분류 프롬프트는 10개 필드를 정의하지만 backend를 포괄적인 implementation technologies로 설명한다. 분리 검토는 features/database/external_integrations만 설명한다. 기존 semantic_review의 backend=언어·프레임워크·런타임, 미구현 확정 요구 포함, 명사형 동작 허용 규칙이 전달되지 않는다. 정의 불일치가 원인 후보이며 모델 성능 문제와 구분해 검증한다.

## 선택과 범위

- 필드 정의만 통일하는 선택형 `explicit-v1`을 우선한다. 모델 교체만으로는 단계 간 의미 차이가 남는다. 새 판단/수정 파이프라인은 이번 실험에 추가하지 않는다.
- 기본값 `legacy`의 요청·모델·공개 Profile·서비스 경로는 유지한다. opt-in 후보 분류·전체 검토·분리 후보 검토·커버리지 검토에 같은 지침을 전달한다.
- 10개 필드 정의, 확정/미정/부정/다른 대상, 기획 요구와 구현 완료의 구분을 공통 문자열로 둔다. backend는 언어/프레임워크/런타임, 외부 연동은 구체적 외부 제공자다. 내부 모듈·저장소·예시 기술·개발 도구를 혼동하지 않는다.
- 현재 문서가 요구하는 제품 범위에서 확정된 미구현 기능은 포함한다. 선택지·결정 유보·명시적 이후 확장안은 현재 기능으로 확정하지 않는다. 완료된 배포나 현존 제품이라는 이유를 요구하지 않는다.
- features의 명사구가 해당 위치 문맥에서 동작을 분명히 가리키면 문장형 동사가 없다는 이유로 제외하지 않는다. 기술명·입력 문서·내부 컴포넌트 이름만으로 기능을 추정하지 않는다. 중복 표현은 후보 검토에서 사실의 거짓으로 바꾸지 않고 기존 최종 변환 규칙을 따른다.

## 동일 입력 비교

기존 종료된 paired JSON의 classification_refs를 승인된 원문 해시와 다시 대조한다. 추출·분류는 재호출하지 않고 같은 후보·라벨을 고정해 동일 모델의 legacy/explicit-v1 검토를 비교한다. 각각 새 원문 커버리지 검토와 기존 finalize를 거친다.

재생기는 문서/원본 해시·후보 범위·유일한 안전 ID·분류·후보 수·반려 수를 검증하고 API 키가 문서/ID에 있으면 호출 전 차단한다. snapshot에 원문 값은 필요 없다. 반려 후보의 세부 사유는 복구 불가하므로 snapshot_rejected로 표시하고 반려 개수·확인 필요 조건을 유지한다. 오류는 안전한 코드만 저장한다. 원문·후보 값·응답·키를 결과에 저장하지 않는다.

## 검증과 판단

- 계약 전달/기본값 보존, 잘못된 정책 사전 거부, snapshot 변조·오프셋·중복·해시·키 유출 차단, 후보 공유 상태 오염 방지, 모델 오류 분모 유지, 반려 후보 보류를 단위 검증한다.
- H02는 튜닝 사례다. 같은 모델·같은 입력·다른 검토 지침만 비교한다. 기존6개 검사와 필드별 보존/제외 수를 함께 기록하고 확정 웹 형태의 두 후보·문맥상 기능·미래 확장안 등을 원문과 대조한다. 사후 사람/개발자 대조는 독립 정답률로 주장하지 않는다.
- 정상 정보 보존과 잘못된 확정 감소가 함께 관찰돼야 다음 문서로 확대한다. 단순 제외 수 감소나6/6으로 서비스에 승격하지 않는다.

사용자의 목표 단위 자율 승인에 따라 명세·계획·구현을 직접 진행한다.
