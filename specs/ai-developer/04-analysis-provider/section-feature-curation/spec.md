# 구역 기능 후보에서 핵심 기능 선택 — 선택형 실험 명세

## 배경과 목적

AI 담당 PRD의 대상은 `핵심 기능`이고 공개 Profile의 `features`는 최대 30개다. Campfire PRD 구역 추출은 후보 128개(구역별 30/30/30/4/30/4, 정확 중복 0)를 만들어 Profile 생성 전에 실패했다. 모델이 많은 세부 문장을 기능으로 잘게 선택하는 상황에서, 원문 근거를 유지하며 30개 이하의 핵심 기능 후보를 선택할 수 있는지 검증한다.

## 선택한 설계

- 기존 구역 추출·검증·정확 중복 제거를 그대로 사용하되, 30개 상한 검사는 내부 수집과 공개 Profile 투영 사이에 둔다.
- 고유 후보가 30개 이하이면 기존 결과를 그대로 사용한다. 31개 이상이면 **선택형 curation 모드에서만** 후보마다 고정 ID를 붙이고 Solar에 핵심 기능 ID를 최대 30개 고르게 요청한다. ID에는 서버가 고른 실제 원문 selector 값과 읽기 전용 구역 제목 문맥을 함께 전달한다.
- 서버는 반환된 ID가 제공한 후보의 유일한 부분집합인지, 1~30개인지 검증한 뒤 원문 순서로 원래 selector 항목을 투영한다. 모델이 새 값·근거·줄 위치를 만들 수 없다. 누락을 감추는 순서 기준 상위 30개 절단은 하지 않는다.
- 선택 호출이 실패하거나 구조가 맞지 않으면 안전 실패한다. 선택 결과도 기존 Profile 근거 검증과 A/B 및 전체 구역 의미 검토를 통과해야 하며, 검토 이슈는 자동 완료로 만들지 않는다.
- 모델에게 모든 세부 조건이 아니라 독립적인 사용자/운영 능력을 고르게 요청하되, 고유한 확정 핵심 기능을 누락하지 말라고 지시한다. 정답률은 모델 판단이므로 실문서 평가로 확인한다.

## 경계와 불변식

- 기본 `section_feature_curation=False`; `section_feature_extraction=True`와 그 선행 조건이 있어야 활성화된다. 기본 분석기·FastAPI·공개 Profile은 변경하지 않는다.
- 선택 호출은 후보 31개 이상일 때만 1회 발생한다. 최대 제공자 호출은 curation 모드에서 19회, 평가 전체 기한은 1,200초다. 기존 모드는 18회 또는 이하를 유지한다.
- 후보 수집은 최대 7청크 × 청크당 30개 = 210개다. 구역 범위·근거·role·상충·정확 중복 검증을 약화하지 않는다. 후보가 30개를 넘고 curation 모드가 꺼져 있으면 계속 `SECTION_FEATURE_OVERFLOW`로 실패한다.
- 안전 평가 산출물에는 단계·호출 수·후보 개수·선택 개수·실패 코드만 남긴다. 원문·선택 값·ID별 내용·원본 응답·키·Profile은 저장하지 않는다.
- 튜닝 문서의 부분 정답은 서비스 승격 근거가 아니다. 추가 문서 4건의 전송 제한은 유지한다.

## 수용 기준

1. 합성 문서 31개 이상에서 허용 ID 30개 이하를 반환하면 선택 항목만 원문 순서와 원래 근거로 Profile에 전달한다.
2. 알 수 없는 ID, 중복 ID, 0개, 31개 이상, 잘못된 구조, 호출 실패는 자동 완료 없이 실패한다.
3. 후보 30개 이하에는 추가 호출 없이 기존 경로와 같은 결과를 반환한다.
4. 같은 Campfire 튜닝 문서 1건에서 19회 상한·구조·부분 정답·정답 밖 값·검토 상태를 평가한다. 이전 128개 실패와의 차이는 한 번의 확률적 실행 차이로 해석한다.
5. 전체 테스트, Linux CI, 독립 코드 리뷰를 통과한다.

## 대안 판단

- 공개 Profile의 30개 상한을 늘리면 Spring·Frontend 계약을 바꿔야 하고 세부 조건 과다 수집을 해결하지 못한다.
- 첫 30개를 서버가 임의 절단하면 원문 뒤의 핵심 기능 누락을 숨긴다.
- 이 설계의 모델 선택도 누락 위험이 있으므로 전체 문서 구역 검토와 확인 필요 상태를 반드시 유지한다.
