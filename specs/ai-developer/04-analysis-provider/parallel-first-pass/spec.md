# 최초 추출 병렬 실행 실험

## 근거와 가설

공개 한국어 튜닝 문서 `ORDER101`의 한 번 실행에서 core 11.4초, features 6.4초, repair 22.2초가 걸려 전체 40초 기한에 도달했다. core와 features는 모두 같은 원문만 입력받고 서로의 응답을 사용하지 않는다. **가설:** 두 최초 호출을 동시에 시작하면 수정 호출에 남는 시간을 늘려 `PROVIDER_TIMEOUT`을 줄일 수 있다. Provider가 병렬 요청을 느리게 처리할 수 있으므로 실제 지연과 품질을 별도로 측정한다.

## 계약

- `RecoverableSolarAnalyzer(parallel_first_pass=True)`에서만 최초 core와 features 요청을 동시에 실행한다. 기본값 `False`, 기본 Solar 및 FastAPI 서비스 동작은 유지한다.
- 두 호출 모두 기존 원문·프롬프트·스키마·모델 설정을 사용한다. 결과를 모두 받은 후 기존 필드별 근거 검증과 수정·의미 검토를 순서대로 진행한다. 병렬 호출이 실패하면 진행 중인 다른 최초 호출을 회수한 뒤 기존 안전 오류 경로로 끝낸다.
- 진단 순서는 core, features로 고정한다. 최대 6회 호출, 전체 40초 평가/60초 분석 제한, 개별 40초 상한, 공개 Profile과 근거 검증 계약을 유지한다.
- 공개 평가 CLI에 선택 옵션을 제공하고 실행 계획에 기록한다. 기본 서비스를 바꾸기 전에 이미 사용한 공개 튜닝 문서에서 지연·호출·완전성·근거 오류를 관찰한다. 독립 검증과 Spring 확인 저장 E2E 전에는 기본값을 켜지 않는다.

## 검증

1. 두 최초 Provider 호출이 실제로 겹치며, 결과 필드와 호출 수가 기존 순차 경로와 같다.
2. 기본 경로의 요청·진단 순서는 그대로이고, 병렬 한쪽 실패 시 실행 중인 호출이 남지 않는다.
3. Provider 타임아웃이 남은 전체 기한에 의해 제한되고, 잘못된 근거가 자동 확정되지 않는다.
4. 이미 사용한 공개 튜닝 문서의 한 번 실행에서 단계별 지연과 안전한 점수를 기록하고, 다른 모델 실행의 확률적 차이를 개선량으로 단정하지 않는다.
