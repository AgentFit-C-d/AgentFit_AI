# 후보 위치 우선 Profile 분석 명세

## 배경과 목적

기본 분석기는 모델이 값·인용·문맥을 작성하고 서버가 사후 수정한다. 새 비식별 문서 세 건에서 Profile 완료가 0/3이었고, 정확한 값 기반 인용 복구도 0/3이었다. 이 방식의 추가 프롬프트 수정은 중단한다. 원문 위치를 먼저 고정한 후보를 만들고, 모델에는 후보 ID의 의미 판단만 맡기는 선택형 내부 분석기를 만든다.

## 계약

1. 입력은 서비스가 정규화한 원문 텍스트다. LangExtract 등 후보 생성기가 위치 제안을 해도 서버가 `ground_anchored_extractions`로 정확한 시작·끝을 재계산한다. 원문과 일치하지 않거나 반복 위치가 모호한 후보는 확인 필요로 보류한다.
2. 서버는 확정된 후보마다 안정적인 ID·원문 구간을 부여한다. 필드·확정 여부 판정 모델은 ID별 `{field,status}`만 반환하고 인용·값·오프셋을 다시 쓰지 않는다. 10개 Profile 필드와 `other`, `confirmed/negated/tentative/irrelevant`를 지원한다. 모든 ID가 정확히 한 번 판정돼야 한다.
3. 서버는 `confirmed`인 후보의 원문 구간에서만 값과 근거를 만든다. 미정·부정·다른 제품·가상 예시·중복·상충은 자동 확정하지 않는다. 스칼라 충돌, 30개 초과 기능, 불완전 후보 집합은 확인 필요로 보류한다.
4. 의미 판정과 문서 커버리지는 별개다. 후보가 빠졌는데 남은 후보가 모두 맞다는 이유로 Profile을 자동 완료하지 않는다. 전체 문서 검토가 누락·오분류를 확인해야 자동 완료할 수 있다.
5. 실험은 기존 공개 Profile, Spring 계약, 기본 Solar 분석기의 동작을 바꾸지 않는다. 원문·후보 텍스트·모델 응답·키를 공유 결과에 기록하지 않는다. 안전한 ID·오류 코드·수치만 기록한다.

## 검증 기준

- 반복·부정·검토안·다른 제품·표·기능 30개 초과의 고정 합성 사례에서 잘못된 자동 확정 0건을 우선 관문으로 삼는다.
- 후보 누락, 오분류, 위치 불명, 중복, 커버리지 미완료, 처리 시간, 모델 호출 수를 분리해 측정한다.
- 기존 개발 문서와 새 비식별 문서 세 건은 구조 검토에 사용됐으므로 독립 최종 검증군이 아니다. 실사용 승격에는 별도 신규 문서·실제 서버 입력 경로·Spring 연동 검증이 필요하다.
