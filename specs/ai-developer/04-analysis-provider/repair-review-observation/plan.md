# 계획
1. 골드 별칭/부재/미정/스칼라 비교 및 메타데이터 보호 테스트.
2. 평가 전용 관측기로 실제 분석 호출을 그대로 실행하고 중간 Profile을 메모리에서 채점한다.
3. Mini4/v2/원문수정on/검토low/6회60초를 유지한 대표4건 진단.
4. 원인이 구분되면 해당 단계만 다음 변경 대상으로 정한다. 이4건을 서비스 품질 점수로 사용하지 않는다.

## 진단 후 수정 단계 단독 비교
4건 관측에서 Q001의 수정은 두동작을 하나로 묶었고, Q004는 부재 누락이 유지됐다.
Q002/N004는 틀린 초안을 검토가 통과시켜 수정이 실행되지 않았다.
수정 모델의 능력을 검토 탐지와 분리하기 위해 같은4건에 고정된 null초안+missing 이슈를 주고 수정 호출만 비교한다.
기존 수정 프롬프트와 일반 예시를 추가한 프롬프트를 각4건1회 비교한다.
모델Mini4/추론none/4096토큰/스키마/입력/골드는 동일하다. 사례와 다른 단어의 예시를 사용한다.
이 단독 호출의 통과를 전체 분석 성공으로 집계하지 않는다. 단독 기준선 자체가 실패하면 구조·판단 이슈를 기록한다.

## 새 합성 반례8건 확장
단독 수정4건에서 기본0/4, 예시3/4. 전체 분석 성공이 아니다.
transfer-cases.json의 새8건과 골드를 API 호출 전에 고정한다.
예시 프롬프트를 추가 수정하지 않고 같은 기본/예시 조건으로 각8건 비교한다.
명시적 미정/개발용 도구/전체 부재/부분 부재+실제 채택/과거→현재/다른제품예시를 포함한다.
모두 개발자가 만든 합성 자료이며 독립 고객 문서 holdout은 아니다.

## opt-in 전체 흐름 확인
단독 비교에서 기존4건0→3, 새8건2→6으로 개선 관측.
예시 내용을 바꾸지 않고 repair_examples=True로 실제 수정 단계에만 연결한다. 기본False.
관측기 --repair-examples 옵션으로 앞서 같은4건 전체 흐름을 실행한다.
최종 효과가 없으면 단독 점수를 전체 성능으로 주장하지 않는다.
