# 문맥 인용 기반 LangExtract 근거 평가 명세

## 목적

실사용 가능한 Profile 분석을 향해, 반복된 같은 문구의 서로 다른 등장 위치를 안전하게 구분한다. 기존 선택형 LangExtract·Solar 실험은 한국어 조사에 붙은 이름의 문자 위치를 얻지 못했다. 같은 문구의 출력 순서나 개수만으로 위치를 추정하면 오확정할 수 있으므로 반복 위치 자동 배정은 금지한다.

## 설계 선택

1. **채택: 후보별 고유 문맥 인용.** LangExtract의 `candidate_attributes.anchor`에 후보를 포함하는 원문 연속 구간을 모델이 복사한다. 서버가 문서 전체에서 문맥 인용이 정확히 한 번 등장하고 그 안에 후보가 정확히 한 번 등장하는 경우에만 후보의 문자 위치를 계산한다. 라이브러리의 정확 정렬 위치가 있으면 계산 위치와 일치해야 한다.
2. 등장 순서/인덱스 추정은 중복 출력과 누락을 구별할 수 없어 사용하지 않는다.
3. 별도 위치 판단 모델 호출은 첫 실험 범위를 키우므로 이 단계에서는 사용하지 않는다.

## 범위와 계약

- `feature/anchored-langextract-evaluation`은 기존 선택형 평가기에만 적용한다. 기본 FastAPI 분석기, 공개 Profile, Spring 계약, 기본 PDF worker는 변경하지 않는다.
- 모델 응답은 `extractions: [{candidate: string, candidate_attributes: {anchor: string}}]`의 엄격한 JSON 스키마를 사용한다. 인용과 문맥은 원문에서 복사한 연속 문자열이어야 한다. 모델은 긍정/부정/검토 여부를 판단하지 않는다.
- 후보별 문맥은 비어 있지 않아야 하고, 원문 전체에서 고유해야 하며, 해당 후보 문자열을 정확히 한 번 포함해야 한다. 중복된 최종 문자 위치, library 정렬 위치와 문맥 위치의 불일치, 미정렬·변형 인용은 자동 확정하지 않는다.
- 원문에 한 번만 등장하는 후보의 기존 정확 위치 복구는 유지하되, 문맥이 제출되어 충돌하면 보류한다. 반복 후보는 검증된 문맥 없이 자동 확정하지 않는다.
- 최종 상태 판단에는 기존 `guard_candidate`를 적용한다. 문맥은 위치 선택에만 쓰고 상태 판단 근거를 생략하지 않는다.
- API 키, 원문, 후보 인용, 문맥 인용, 원본 모델 응답을 결과 JSON·일반 로그에 기록하지 않는다. 명시적 `--live`, SHA-256으로 고정한 합성 사례, subprocess 전체 호출 기한, 실패별 안전 코드 계약을 유지한다.

## 평가와 승격 기준

- 반복·부정·검토안 18개 기존 골드를 바꾸지 않고 먼저 테스트한다. 같은 원문을 공유하는 짝 사례는 한 번 추출한 결과로 함께 채점해 호출별 변동을 제거한다. 실패는 두 사례 모두에 남긴다.
- 위치 정확·모호·충돌·중복, 자동 오확정, 허용 누락, 모델 응답 실패를 구분해 기록한다. 이전 안전 설정의 18건 결과는 실패 3, 허용 누락 7, 골드 위치 일치 2, 오확정 관측 0이다. 독립 실행이므로 수치 차이만으로 개선을 단정하지 않는다.
- 자동 확정된 근거는 모두 정확한 원문 문자 구간이어야 하고 오확정은 0이어야 한다. 합성 18건에서 실패와 허용 누락을 0으로 만드는 것을 이 실험의 목표로 삼되, 달성해도 별도 실제 문서 검증과 Spring 통합 전에는 기본 경로에 적용하지 않는다.

## 실패 처리

- 문맥 없음/중복/잘못된 부분 문자열/충돌, 모델 스키마 오류, LangExtract 파싱 실패는 해당 사례를 보류하거나 안전 실패 코드로 기록한다. 일부 성공을 전체 성공으로 집계하지 않는다.
- 문맥 인용은 문서의 지시문으로 실행하지 않고, 정확 문자열 검증 데이터로만 사용한다.
