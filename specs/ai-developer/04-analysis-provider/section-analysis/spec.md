# 구조 보존 구역별 문서 분석
상태: 사용자가 방향 승인, 구체적인 처리 흐름 검토 단계.
목적: 특정 문서에 예외 규칙을 추가하지 않고 문서 전체에서 근거 있는 사실을 수집하고 역할·확정 상태를 판단한다.
## 관찰
현재 evidence-v1 공통 검증은140테스트 통과하지만 최종7사례 정답1개,오답반환1개,오류5개다. 공통 근거 검증을 유지한다.
현재 입력을 제목 기준으로 측정: MABC2106자/6구역/최대693자, AgentFit7610자/15구역/최대858자. 원문은 Git 제외.
## 요구사항
FR1: Markdown 제목 계층·문단·표·코드블록과 원본 문자 위치를 보존한다. 일반 텍스트는 문단 경계로 처리한다. 공백·CRLF·Unicode를 정규화하거나 버리지 않는다.
FR2: 모든 원문 구간이 한 번 이상 분석 입력에 포함됐는지 서버가 검사한다. 구역ID는 서버가 부여하며 누락·중복 응답은 실패다. 응답의 구역 확인 자체가 의미적 누락 없음을 증명하지는 않는다.
FR3: 상위 제목과 문서 범위를 각 구역에 전달한다. 제목이 '예시'라고 검색에서 제외하지 않으며 모든 구역을 처리한다. 제목·문서내 지시는 데이터로 취급한다.
FR4: 각 구역은 사실 후보와 정확 인용을 추출한다. 현재제품/다른제품/예시, 확정/검토/부정/미정, 필드역할을 이후 통합 단계에서 대조한다. 개발 업무를 제품 기능으로 단정하지 않는다.
FR5: 후보는 원본 구역의 정확 근거에 묶인다. 다른 구역의 인용을 도용하거나 없는 후보ID를 통합에 사용하는 것은 거절한다. 필요한 문맥은 원문 그대로 보존한다.
FR6: 전역 통합은 스칼라 충돌, 확정과없음의 충돌,중복,최종결정·과거의 구분을 처리한다. 판단 불가일 때 임의 하나를 채택하지 않는다.
FR7: 기존 Profile10필드와 Solar,공통 근거 검증,실패 원본7일,최대6호출·60초 예산을 유지한다. 임베딩/벡터DB는 추가하지 않는다.
FR8: 기존 분석기는 비교 기준으로 남긴다. 새 방식은 별도 실험 진입점으로 검증하고 품질 확인 전 기본 분석기를 교체하지 않는다.
## 호출 흐름
1. 서버가 구조를 보존해 나눈 구역들을 최대2개 묶음으로 배정한다. 구역을 선택하거나 생략하지 않는다.
2. 각 묶음에서 모든 구역의 사실 후보 추출:1~2회.
3. 전체 후보의 역할·확정성·충돌을 대조해 Profile 초안 통합:1회.
4. 원문 전체와 초안 의미 검토:1회.
5. 의미 오류 시 후보 근거 범위에서 수정:최대1회,수정후 재검토:최대1회.
총3~6회. 구역 추출/통합의 잘못된 구조·근거는 즉시 실패한다. 현재 방식의 별도 구조수정1회까지 함께 제공하면 상한을 넘으므로 새 실험에서는 제외한다. 검토 실패를 성공으로 반환하지 않는다.
## 입력 및 예산
실험은 묶음당 최대12000원문 코드포인트,총2묶음으로 시작한다. 제목문맥 등 실제 요청 크기는 별도 기록한다. 하나의 원자 블록이 상한을 넘거나 전체 배정이 불가능하면 호출 전에 명시적 오류로 종료하고 부분 분석을 반환하지 않는다. 기존 분석기의100000자 입력 계약은 변경하지 않는다.
표·코드블록을 임의로 잘라 의미를 잃지 않는다. 긴 구역은 문단·완전한 블록 경계로 나누고 상위 제목 경로를 반복 제공한다.
전체60초 예산을 공유하며 호출 전후 확인한다. 현재 urllib의 하드60초 반환 한계는 남아 있다. 동시 호출은 첫 실험에서 도입하지 않는다.
## 완료 기준
SC1: 원문 재구성·누락없는 범위 분할·제목 계층·표·코드블록·CRLF/Unicode·상한초과를 회귀 검증한다.
SC2: 구역 응답 누락/중복,잘못된 근거/후보ID,스칼라충돌,제외할 개발업무,다른프로젝트·가상예시,반복기능,absence/unknown을 검증한다.
SC3: 같은 문서·정답으로 기존 방식과 비교하고 정답반환·오답반환·실패·지연·토큰·호출을 모두 집계한다. 처리한 구역 수와 실제 의미적 포괄성 점수는 구분한다.
SC4: 작은 비교 통과 후에만 미사용 문서·합성사례로 확대한다. 신규문서 미제공은 일반화 미확인으로 남긴다.
SC5: 개선이 입증되지 않으면 기존 결과를 덮어쓰지 않고 운영 채택을 보류한다.
