# 검토 이슈 확인 게이트 검증

## 결정적 검증

- 최초 검토가 이슈를 반환하고 수정·재검토가 통과한 가짜 제공자 사례에서 기본 경로는 `complete`, 선택형 게이트는 `needs_confirmation`이 됐다. 추가 제공자 호출은 없었다.
- 게이트 이력이 다음 분석 호출에 남지 않는 테스트를 포함해 전체 단위 테스트 428건이 통과했다.

## 합성 20건 단일 실행

[run1 결과](results/run1/summary.json)는 Solar Pro4에 `require_issue_free_review`를 켠 새 실행이다. 사례당 분석은 한 번이며 이전 실행과 응답을 공유하지 않는다.

| 항목 | 결과 |
| --- | ---: |
| `complete` / `needs_confirmation` / `failed` | 8 / 6 / 6 |
| 검토 이슈 게이트가 확인 상태로 낮춘 사례 | 0 |
| 기존 값 채점의 잘못된 자동 확정 | 1 (`Q-001`) |
| 관측 60초 초과 | 2 |
| 최대 제공자 호출 | 6 |
| 평가 관문 | 실패 |

`Q-001`은 독립 정답 근거 두 곳에 비해 후보 용량이 부족했지만, 의미 검토가 해당 필드를 지적하지 않아 게이트가 발동하지 않았다. 따라서 이번 실험은 실사용 오확정 감소를 입증하지 못한다. 결정적 테스트가 보여준 것은 **검토가 실제 이슈를 반환한 경우에 한정된 안전 효과**다. 사용자 확인 부담도 이번 실행에서는 새로 늘지 않았다.

산출물 3개에서 합성 문서 원문과 API 키 문자열이 없는지 검사했다. Profile 전체·모델 원본 응답은 결과에 기록하지 않는다. 실제 문서에 대한 사람 검증과 의미 근거 채점은 여전히 없으며 기본 분석기·서비스 API에는 게이트를 적용하지 않았다.

## 다음 문제

후보에 누락된 사실을 의미 검토가 놓치면 게이트만으로는 막을 수 없다. 다음 개선은 모델의 빈 검토 결과에만 의존하지 않는 후보 누락 감지 또는 추가 확인 경로가 필요하다. 비용은 자동 확정 감소와 사용자 확인 부담을 같이 측정해야 한다.
