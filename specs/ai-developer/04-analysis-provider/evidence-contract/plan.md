# 구현 계획안
1. 기존 v27/v28 실패와 정답을 보존하고 공통 계약용 spec/schema를 고정한다.
2. evidence.py에 원문 일치·문맥 유일성·코드포인트 위치 계산과 구조화 오류를 구현한다. 모델 호출 없는 실패 테스트부터 시작한다.
3. 스칼라/배열/외부연동/기능 항목을 내부 정규 형태로 검증하고 기존 Profile로 변환한다. unknown/absent 근거는 별도 분기한다.
4. features 전용 occurrence 및 core 줄id 응답을 내부 새 계약으로 교체한다. 공개 출력은 이전과 호환 검사한다. 스키마 버전을 별도로 남긴다.
5. 기존 단계 추출과 최대1회 구조수정·1회 의미수정에 공통 진단을 연결한다. 오류를 통과시키기 위한 fallback을 추가하지 않는다.
6. 고정 오프라인 전체회귀 → 실제문서와 합성의 작은 대조 → 효과 확인 시 미사용 반례/신규문서 순서로 검증한다.
7. 호출수·지연·토큰·의미 정답을 함께 평가하고 악화되면 운영 채택하지 않는다. 별도 feature 브랜치에 코드·검증을 push한다.
대안: occurrence 설명만 보완(범용 재발 방어 부족,실험실패), 모든 문자열 후보ID 열거(기존v23 품질회귀·토큰증가), 위 공통 정확인용 계약(권장,실호출효과는 검증필요).
실행: 현재 작업에서 순서대로 구현. 공개 계약/6회/60초 변경이 필요해지면 별도 구체안 검토.
