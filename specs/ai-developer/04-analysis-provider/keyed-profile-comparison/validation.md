# ID별 후보 계약의 전체 Profile 비교 결과

## 실행 범위

기존 배열 후보 계약과 새 ID별 후보 계약을 동일한 Solar Pro4, v2 후보 확장, 동일한 판단·의미 검토 설정으로 20건씩 교차 실행했다. 12건은 전체 10개 Profile 필드의 값·미정·부재를 채점했고, 다구역 8건은 사전 지정된 27개 현재 제품 사실과 배제 문구를 채점했다. 정답은 모델에 보내지 않았다. 전부 기존 튜닝 합성 자료다.

첫 실행(`results/run1`)은 오확정 범위를 좁게 세고 제공자·검증 오류를 합산한 채점 결함이 발견돼 최종 판정에서 제외했다. 독립 코드 검토의 지적을 반영한 뒤 두 번째 실행(`results/run2`)의 [계획](results/run2/plan.json), [사례별 결과](results/run2/results.json), [집계](results/run2/summary.json)를 최종 비교로 사용했다. 실행 사이 모델 출력 변동이 있으므로 첫 실행 수치는 안정성 추정에만 참고한다.

| 지표 | 배열 기준선 | ID별 후보 |
| --- | ---: | ---: |
| 전체 Profile 최종 유효 | 7/12 | 7/12 |
| 전체 Profile 완전 일치 | 7/12 | 6/12 |
| 전체 Profile 필드 일치, 실패 0점 | 70/120 | 69/120 |
| 양쪽 모두 성공한 6건 필드 일치 | 60/60 | 59/60 |
| 전체 Profile 오확정 | 0 | 1 |
| 다구역 최종 유효·지정 사실 완전 일치 | 0/8 | 1/8 |
| 다구역 지정 사실, 실패 0점 | 0/27 | 3/27 |
| 다구역 제공자 시간 초과 | 2 | 5 |
| 모든 사례의 최대 호출 수 | 6 | 6 |
| 다구역 지연 중앙값 | 15,844ms | 60,062ms |

새 방식은 다구역 E05 한 건에서 지정 사실 3/3을 맞혔다. 그러나 다른 7건은 최종 Profile을 내지 못했다. 짧은 Q-001은 양쪽 모두 결과를 냈지만 새 방식이 `features`를 잘못 확정해 9/10으로 떨어졌다. 기존 배열 방식의 후보 구조 오류는 줄일 수 있어도, 후속 의미 판단·검토와 전체 시간 제한 문제는 그대로 남는다.

## 관문과 제약

- 20건 모두 동일 조건으로 시도했고 호출 수는 양쪽 모두 최대 6회였다. 일부 블로킹 네트워크 호출은 실제 경과가 60초를 조금 넘었다(기준선 최대 60,078ms, 새 방식 최대 60,140ms). 현재 공통 분석 경로는 엄격한 60초 반환을 보장하지 않는다.
- 새 방식의 오확정 1건은 기준선 0건보다 많다. 다구역 제공자 시간 초과도 2→5건으로 늘었다. 사전 관문 `false_confirmations_no_increase`와 `budget`이 실패했다. 평가 스크립트의 종료 코드 1은 이 관문 실패를 뜻한다.
- 전체 Profile의 검증 오류 증가 여부와 전체 오류 건수는 관문을 통과했지만, 성공률·오확정·지연 결과를 뒤집지 못한다.
- 결과 파일에는 키·문서 원문·인용문·모델 원본 응답을 저장하지 않았다. 신규 실제 문서의 일반화 성능과 사용자 수정 부담은 확인하지 못했다.

**결론:** ID별 후보 계약은 opt-in 실험 코드로 보존하되 기본 분석기에 적용하지 않는다. 현 자료로는 실사용 가능성을 입증하지 못했다. 다음 병목은 후보 포맷보다 후속 의미 판단/검토 실패와 시간 초과다.

## 검증

연결·채점 회귀 테스트를 포함한 `python -m unittest discover -s tests -q` 351건 통과. `git diff --check` 통과. 독립 검토에서 발견한 오확정 누락, 오류 유형 혼합, 성공 건만 분모에 넣는 문제를 수정하고 고정 분모와 공통 성공 쌍을 모두 기록했다.
