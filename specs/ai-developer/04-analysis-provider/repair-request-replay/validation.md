# 검증 결과
## 입력 차이
전체 흐름에서 캡처한 N-004 수정 요청은 단독 평가의 document/requestedFields/previous/issues/units/system prompt/schema와 모두 같았다. Mini와 Pro4 비교 실행에서 원래 요청 SHA256도 같았다. 입력 구성 차이 가설은 이번 관측에서 지지되지 않았다.
Mini의 동일 payload 3회 별도 재생은1/3, Pro4의 model 필드만 바꾼3회는3/3이었다. Mini 실패2회는 INCOMPLETE_RESPONSE다. 두 모델의 별도 재생 timeout은40초다. 원래 전체 흐름 timeout은 당시 별도 기록하지 않았으므로 전체 흐름과 재생의 모든 실행 조건이 같았다고 주장하지 않는다. 이번 두 전체 흐름 자체는 성공했다.

## 고정 상태13건 확장
Pro4/low는11/13이었다. S04/S05가40초에 PROVIDER_TIMEOUT으로 실패했다.
Pro4/none은12/13이었다. S02는 SOURCE_REPAIR_INVALID였고 나머지는 성공했다. 단독 수정 중앙값844ms, 최장2360ms였다. 숫자는 summary.json을 기준으로 한다.
모델·추론 설정만으로 모든 문제가 해결되지는 않았다. 반복 인용의 위치 지정은 여전히 실패했다. 각13건1회이며 독립 고객 문서나 실사용 준비 완료 근거가 아니다. 기본 모델·분석기는 변경하지 않았다.

## 검증과 해석 제한
전체 unittest292건 통과. 새 테스트는 원문/키 미보관과 Pro4를 선택해도 model 외 payload가 동일함을 검증한다. 독립 검토의 원래 timeout 기록 의견을 반영했다. 이미 끝난 결과를 소급 수정하지 않았다.
Mini/Pro4 비교는 순차 실행이고 표본이 작아 우월성을 확정할 수 없다. 후보는 Pro4/none이나 전체 흐름·새 문서·사람 수정 부담 검증이 필요하다. 단위 테스트 통과와 짧은 사례의 개선을 목표 달성으로 대신하지 않는다.

## 후속 설계
문장 분할은 약어 손상 위험이 있어 채택하지 않는다. 기존 quote와 unitId를 유지하며 occurrenceIndex로 등장 순서를 명시하는 opt-in 계약을 별도 제안한다. 이 계약은 잘못된 등장 순서를 선택할 위험이 있으므로 값뿐 아니라 정답 근거 위치를 검증해야 한다. 사용자 승인 전 구현하지 않는다.
