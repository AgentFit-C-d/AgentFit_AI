# 계획
1. 기존 분석기의 _send_payload를 CLI 실행 중에만 관측하고 source_repair를 메모리에 복사한다.
2. 전체 흐름을 완주한 후, 실제 요청과 단독 평가 입력의 동등 여부를 기록한다.
3. 동일 요청3회(40초 제한,2초 간격)를 재생하여 apply_repairs 및 정답 검증을 수행한다.
4. 기존 테스트와 코드 검토로 원문 미보관·요청 불변성을 확인한다.
5. 입력 차이와 반복 결과를 근거로 다음 진단을 결정한다. 통과3회만으로 과거 실패 해결을 선언하지 않는다.

## 동일 요청 변동 확인 후 모델 대조
첫 실행에서 요청 각 구성 요소가 모두 단독 평가와 일치했고 동일 payload 재생3회 중2회 INCOMPLETE_RESPONSE가 발생했다. 입력 차이 가설을 지지하지 않는다. 같은4096/low/40초에서 Solar Pro4로 모델만 바꾼3회 재생을 추가한다. Mini 전체 흐름은 여전히 원래 설정으로 실행하여 실제 요청을 잡는다. 원래 요청과 재생 요청 해시를 구분하고 기본 모델은 유지한다. 새 캡처의 원래 요청 해시가 이전과 다르면 동일요청 모델 비교라고 주장하지 않는다. 오류 시 숫자형 토큰 진단만 추가한다.

## 모델 후보의 범위 검증
같은 원래 요청 해시에서 Mini1/3, Pro4 3/3이었다. 단일 사례만으로 선택하지 않도록 기존 상태13건을 Pro4/low/4096/40초/원래 구역으로1회 평가한다. 채택 게이트가 아닌 확장 진단이며 실패도 전부 보존한다. 단독 평가 CLI의 모델 선택만 추가하고 기본 Mini와 서비스 경로는 유지한다.

## 코드 검토 반영
원래 전체 흐름의 수정 timeout은 남은60초에 따라40초보다 짧을 수 있다. 후속 실행부터 캡처한 원래 timeout과 재생40초를 각각 기록한다. 이미 종료한 두 실행의 원래 timeout은 소급 추정해서 기록하지 않는다. Mini/Pro4의 별도 재생은 둘 다40초였으며, 원래 전체 흐름과 재생의 timeout이 동일했다고 주장하지 않는다. 모델 외 payload 불변성을 검사하는 테스트도 추가한다.

## Pro4 추론 설정 대조
low 확장 평가에서 S04/S05가 각각40초에 PROVIDER_TIMEOUT이 됐다. 같은13건·모델·프롬프트·4096토큰·40초에서 effort만none으로 바꿔1회 비교한다. 추론 시간 감소와 상태 오분류가 맞바뀔 수 있으므로 정답 전체 일치와 실패를 함께 집계한다. 세트 도중 중단·정답 수정 없이 모두 수행한다.
