# 기능·기대효과 경계 조사

## 목적과 근거

직전 실제 H02는 형식상 7/7 완주했지만 유지 정답 3개를 모두 not_product_fact로 제외했다. 검토 요청은 이미 정확한 등장 위치·앞뒤 240자·문서 전체를 전달하므로 단순 문맥 누락이라고 단정하지 않는다. 모델이 구역 제목·계획 시제에 영향을 받아 기능과 기대효과의 경계를 잘못 적용하는지 조사한다.

## 가설·비교

하나의 새 합성 문서에 명시적인 현재 기능 10개와 기능이 아닌 후보 10개를 고정한다. 기능 구역 밖의 동작, 구체적인 요구지만 미구현인 MVP, 운영자 기능, 명사형 기능, 기대효과, 팀 업무, 구성요소, 입력 문서, 부정, 범위 밖 미래 확장, 다른 제품, 반복 표현을 포함한다.

기존 explicit-v1/reasoned 검토와 **동작·범위 판단 순서를 보강한 짧은 규칙**만 비교한다. 모델별로 원문·후보·기존 규칙·JSON 계약·설정은 같고 system prompt의 추가 규칙만 달라야 한다. DeepSeek 기존 thinking=false 설정과 GLM 기존 low 설정을 각각 사용한다. 이는 모델별 짝 비교이며 두 모델의 설정이 같다는 실험이 아니다.

추가 규칙은 일반 기준이며 사례 정답·ID·문서 고유 표현을 포함하지 않는다. 실행 후 정답이나 사례를 바꾸지 않는다. 모델의 자연어 추론은 채점하지 않는다.

## 경계와 실행

- 공개 Profile·제품 코드·기본 분석기 변경 없음. 실제 비공개 문서도 사용하지 않는다.
- 각 모델의 baseline/rubric 한 번씩, 총 최대 4호출, 호출당 600초·8192토큰·재시도0. 기존 streaming·정규화·모델/민감정보/ID/사유 검증을 유지한다.
- 전체 누락 검토 없이 공급한 20개 후보의 판정만 실험한다. coverage나 최종 Profile 성공으로 보고하지 않는다.
- 모든 요청에 직전 검증된 공통 전송 방식(JSON Schema를 system prompt에 넣고 response_format 제거)을 적용한다. 이 변환 이후 baseline은 해당 모델의 기존 검토 규칙이고 rubric은 system 추가 문자열만 달라야 한다. 모델별로 원문/후보/기존 설정 일치와 해시를 사전 확인한다.
- 호출 실패·계약 실패는 채점하지 않는다. 형식 성공, 20개 판단 일치, 유효 기능의 오제외, 비기능의 오유지, 유형별 결과를 별도로 기록한다.
- 원본 응답·추론·키 저장 없음. 새 합성 입력/정답은 추적 가능한 fixture로 저장한다. 실행기는 일회성 local ignored 조사 도구다.

## 판정

baseline이 이미 19/20 이상이면 이 작은 합성 문서는 실제 문제를 충분히 재현하지 못한 것이다. 이 경우 프롬프트 개선을 제품에 반영하거나 실제 문서를 추가 호출하지 않는다. 개선을 주장하려면 baseline보다 rubric 일치도가 높고 비기능 오유지가 늘지 않아야 하며, 그 경우에도 후속 실제 문서 검증을 위한 근거일 뿐이다. 같은 사례로 반복 튜닝하지 않는다. 실사용 전체 목표는 독립 검증·서비스 통합까지 유지한다.
