# 후보 검토 묶음 크기

## 근거와 목적

실제 H02의 고정 후보 판정은 13/16이며 유효한 세 후보를 not_product_fact로 제외했다. 그러나 새 합성 기능 경계 사례에서는 DeepSeek·GLM 모두 기존/보강 규칙으로20/20이었다. 새 규칙 효과는 확인되지 않아 반영하지 않았다. 다음 가설은 동시 검토 후보 수가 판단에 영향을 주는지다. 이 가설은 아직 원인으로 확인된 사실이 아니다.

## 내부 계약

- review_candidates_separately와 evaluate_thinking_reviews에 candidate_batch_size=20 keyword-only 옵션을 추가한다. exact int 1..20만 허용하며 잘못된 값은 호출 전에 거부한다.
- 기본20은 기존 요청·결과를 그대로 유지한다. 확인된 후보만 기존 순서대로 정확히 한 번씩 분할한다. 후보·등장 위치·원문·프롬프트·출력 계약을 변경하지 않는다.
- 배치 인덱스와 각 candidate_count는 실제 분할을 반영한다. 모든 배치가 유효해야 source coverage를 호출하고 이후 투영/채점을 한다. 중간 실패 시 부분 결과를 성공으로 반환하지 않는다.
- Solar adaptive_review의 신뢰된 length 복구 규칙은 유지한다. 사용자 지정 묶음이5이하이면 더 분할하지 않고,6이상이면 기존5개 단위 복구를 적용한다. NVIDIA는 재시도하지 않는다.
- 평가기는 실제 batch size에 맞춰 arm별 ceil(confirmed/batch_size)+1을 호출 한도로 계산하고 settings.batch_size에 기록한다. 짝비교의 두 arm에 같은 batch size를 전달한다.
- 공개 Profile·기본 HTTP 서비스·기본 분석기·의미 규칙·JSON정규화 조건은 변경하지 않는다.

## 실제 실험

approved redacted H02, 기존 frozen183후보/confirmed109, 고정16후보정답/6부분정답을 유지한다. DeepSeek thinking=false,temp0,max8192,timeout600,reasoned/explicit-v1,schema-in-prompt,정규화,streaming,재시도0도 유지한다. batch10으로11후보묶음+coverage1,최대12호출을1회 실행한다.

사전 점검에서 기본20의 첫요청이 이전20실험 해시와 같고,10의 첫요청은 후보/JSON Schema의 batch 크기 의존 부분 외에 같은지 확인한다. 모든109개가 순서대로 한 번씩 다뤄지는지 모의 전체 경로로 확인한다. 기존20결과는13/16·부분6/6이며 캐시된 과거 실행이다. 새 실행과 동시에 얻은 무작위 대조가 아니므로 단일 결과 차이를 원인 확정·일반화로 해석하지 않는다.

전체 검토가 유효한 경우만16/6채점,오제외/오유지 구분을 기록한다. 실패·제한 도달은 미평가다. 원문/응답/추론/키 저장 없음. 코드·원문·후보·실행기·설정 해시를 고정한다.

## 완료 기준

기본 호환,1/10/20 경계,정확한 분할/인덱스/범위,중간실패·adaptive 유지,평가 한도·무효 입력 회귀,전체·SDK검증,최대12실험 종료감사,독립 전체리뷰와feature push/CI. 결과가 같거나 나쁘면 개선으로 보고하지 않는다. 전체 실사용 목표의 독립 평가·서비스 통합은 남아 있다.
