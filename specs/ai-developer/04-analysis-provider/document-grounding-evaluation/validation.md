# 문서 근거 비교: 1차 결과

## 확인한 범위

- 2026-09-29, 서비스 환경과 분리한 `E:/AgentFit/tmp/grounding-venv`에 LangExtract 1.7.0, Docling Slim 2.130.0을 설치했다. 공식 Python API로만 실험 코드를 호출하며 기본 서비스 의존성은 변경하지 않았다.
- 반복·부정·검토안 각각 3쌍, 총 18개의 합성 후보와 정확한 코드포인트 위치를 모델 출력 전에 `adversarial-cases.json`에 고정했다. 이 데이터는 튜닝용이며 독립 검증셋이 아니다.
- 후보를 전부 자동 허용하는 단순 기준선은 18개 중 오확정 9개다. 보수적 규칙 게이트는 동일 사례에서 오확정 0개, 허용해야 할 후보 보류 0개였다. 이는 **작성한 규칙을 작성한 소규모 사례에서 채점한 결과**로, 실제 분석기 개선률이 아니다. 상충된 두 확정 문장을 추가 단위 테스트에서 보류한다.
- LangExtract의 실제 `Resolver.align` 호출에서 `Alpha X. Beta X.`와 `[X, X]`는 문자 구간 `(6,7)`, `(14,15)`로 분리됐다. `[X]`처럼 어느 등장인지 선택할 정보가 부족하면 AgentFit 어댑터는 확인 필요로 보류했다. fuzzy 정렬 결과는 자동 근거로 허용하지 않는다.
- Docling native PDF 파이프라인에서 합성 2쪽 PDF를 파일 저장 없이 변환했다. 정규 텍스트 `Alpha\nBeta`, 페이지 구간 `[0,5)`, `[6,10)`이 기존 간단한 PDF 예제와 일치했다. Docling의 일반 레이아웃 모델, 표·제목 인식, OCR은 아직 평가하지 않았다.
- 독립 원격 diff 리뷰에서 같은 문장 안의 다른 대상 상태어를 후보에 연결해 오확정할 수 있음을 발견했다. 쉼표·접속 표현으로 절을 나누고 후보 뒤의 상태어만 허용하는 보수적 규칙으로 수정했다. 별도 표 컬렉션이 있는 Docling 결과는 이 native 실험에서 조용히 버리지 않고 보류한다. 유니코드 코드포인트 위치도 회귀 검증했다.
- 수정 후 전체 로컬 단위 테스트 718건 통과, `git diff --check` 통과. 합성 2쪽 PDF의 실제 Docling 변환도 다시 성공했다.
- LangExtract 전체 `extract()`와 기존 Solar 전송을 연결한 합성 전용 CLI를 추가했다. 18사례 모드는 `--live`와 고정 골드만 받으며 사례별 실패도 안전 집계에 남긴다. 첫 R01 개별 실행은 미완료 1회(출력 토큰 계측 전), 재실행은 완료했으나 골드 위치를 추출하지 못했다(후보 2, 자동 허용 근거 0). 이는 규칙 이전의 추출 병목이다. 전체 실행의 첫 세 사례는 R01 완료·골드 위치 누락, R02/R03 제공자 120초 시간 초과였고, 이 제한이 품질 판단을 오염시키므로 실행을 중단했다. 해당 결과는 부분 실행으로만 취급한다.
- 전체 추출 CLI 추가 후 전체 로컬 테스트 723건 통과, `git diff --check` 통과.
- 독립 리뷰에서 평가 사례 파일의 버전·건수만 검사해 변조된 문서도 외부 전송될 수 있고, inline HTTP 경로가 전체 호출 기한을 보장하지 않으며, 중복 위치를 미추출로 오집계하는 문제를 확인했다. 고정 파일 SHA-256을 키 로딩 전에 검사하고, subprocess 전송에 사례당 600초 기한을 적용하며, 중복 위치 수를 별도 집계하도록 수정했다. 수정 후 로컬 전체 726건과 `git diff --check`가 통과했다. Linux CI는 push 후 확인한다.

## 남은 검증

- LangExtract-Solar는 18개 합성 사례를 실행했으나 최종 안전 설정에서도 3건이 응답 오류로 끝나고 7건이 허용 대상을 놓쳤다. `INVALID_RESPONSE`의 세부 원인 분류와 NVIDIA 어댑터 비교는 남았다.
- R01/R02는 같은 문서의 서로 다른 골드 위치이나 현재 전체 모드는 사례별로 모델을 다시 호출한다. 쌍별 비교에 모델 출력 변동이 섞일 수 있으므로 동일 문서 추출 결과를 재사용하는 방식이 필요하다.
- 호출 한도를 120초에서 600초로 올린 R02 단독 실행은 160초 후 `INCOMPLETE_RESPONSE`로 끝났고 출력 4,096토큰을 모두 썼다. 시간 초과가 아닌 출력 한도 실패로 분리한다. 다음 비교는 출력 한도와 문서·골드를 유지하고 추론 강도만 `low`에서 `none`으로 변경한다.
- R02에서 추론을 `none`으로 바꾸자 약 1.7초·출력 37토큰으로 응답했지만 LangExtract 정렬 위치는 0개였다. 원문에 있는 8자 후보가 두 번 추출됐고 두 후보 모두 `char_interval`이 비어 있었다. 동일 후보를 공식 `Resolver`에 직접 넣어도 위치가 복구되지 않았다. 한국어 조사가 붙은 이름의 부분 문자열이라는 조건이 있다.
- **철회한 실험:** 원문 등장 수와 모델 추출 수가 같으면 반복 이름을 순서대로 배정해 R01 보류·R02 허용을 얻었다. 독립 리뷰에서 모델이 첫 위치를 두 번 중복 출력했을 가능성을 배제할 수 없어 두 번째 위치를 자동 확정하면 오확정할 수 있음을 확인했다. 이 방식의 18건 결과(완료 14, 실패 4, 허용 누락 6, 근거 일치 5)는 안전한 성능 지표로 사용하지 않는다. 반복 이름의 위치 추정 자동 허용을 제거했다.
- 최종 선택형 규칙은 원문에서 인용이 정확히 한 번 나오고 추출도 한 번인 경우에만 서버가 해당 위치를 계산한다. 반복 이름의 모델 위치가 없으면 `ambiguous_alignment`로 보류한다. 합성 18건 재실행은 완료 15건, 실패 3건, 자동 오확정 0건, 허용 누락 7건, 골드 근거 일치 2건, 후보 위치 누락 13건, 모호한 정렬 4건, 중복 위치 0건이었다. 안전 집계는 `E:/AgentFit/tmp/langextract-solar-adversarial-20260929-unique-only.json`에 있다. 실패 건에는 허용/보류 판정을 매기지 않았다. 튜닝셋이라 일반화 성능의 증거가 아니며 모델 재호출 변동도 있다. **통합 방식의 실사용 판정은 실패**다.
- 반복 위치 추정을 제거한 뒤 로컬 전체 단위 테스트 729건과 `git diff --check`가 통과했다. Linux CI는 push 후 확인한다.
- Docling native 경로는 문서 구조 분석 모델을 사용하지 않는다. 실제 표·단락·제목이 있는 PDF에서 `pypdf`와 비교하고 페이지·문자 매핑, 변환 시간과 메모리 제한을 확인해야 한다.
- 현재 규칙은 일반 자연어 의미 판정기가 아니다. 부정 범위, 같은 문장의 철회·재확정, 인용/예시 문맥의 과잉 보류를 추가 골드에서 검증해야 한다.
- 이 선택형 코드는 기본 FastAPI/PDF Worker에 연결되지 않았고, 새로운 서비스 동작의 품질은 아직 검증되지 않았다.
