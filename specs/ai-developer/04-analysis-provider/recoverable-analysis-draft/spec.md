# 실패 복구형 분석 초안: 내부 선택형 실험 명세

## 목적과 근거

현재 `AnchoredAnalyzer`는 후보·판단·의미 검토·수정 중 한 단계가 실패하면 전체 분석을 실패시킨다. 동일 상류 응답 비교 20건에서 Solar의 최종 실패 13건은 판단 상태 검증 4건, 수정 후 같은 지적 4건, 후보 부족 1건, 검토 형식 오류 1건, 시간 초과 3건으로 분류됐다. 별도 Solar 초안 진단에서는 20건 중 11건만 정답이었고, 내용 오류 5건·초안 생성 실패 4건이 관측됐다. 두 실행은 서로 다른 응답이므로 사례별 인과 비교에 쓰지 않는다.

사용자가 수정할 수 있는 초안을 안전하게 남기는 내부 경로를 실험한다. **복구형 결과는 분석 성공이나 저장 완료가 아니다.** 기존 성공 Profile·기본 분석기·서비스 API는 그대로 둔다.

## 내부 결과 계약

- 선택형 호출만 `complete`, `needs_confirmation`, `failed` 중 하나를 돌려준다. `complete`는 기존 분석기의 검증을 통과한 결과와 동일하다.
- `needs_confirmation`은 구조·근거가 서버에서 검증된 제안만 담는다. 각 필드는 `suggested`(값 또는 명시적 부재 `[]`), `unknown`(값 `null`, 현재 정보로 추출된 사실 없음), `unresolved`(값 `null`, 분석 실패가 해당 필드 판단을 막음) 중 하나로 기록한다. `suggested`도 사용자 확인 전에는 확정값이 아니다.
- `unresolved` 필드에는 원문·모델 답변을 복사하지 않은 안전한 사유 코드와 고정 템플릿 질문 ID를 연결한다. 구체적인 질문 문장과 선택지는 별도 계약 전에는 내부 예시로만 제공한다. 동일 필드에 여러 오류가 있으면 중복 질문을 만들지 않는다.
- `failed`는 재사용할 수 있는 구조 검증 초안이 없을 때의 안전한 오류다. 오류를 빈 Profile이나 저장 가능한 성공으로 바꾸지 않는다.
- 내부 결과에는 원문, 원본 LLM 응답, API 키를 넣지 않는다. 기존 실패 원본 7일 보관 정책과 진단 경계는 유지한다.

## 실패별 복구 규칙

1. 후보 생성 결과가 형식·인용·구역 검증에 실패하면 후보를 재사용하지 않고 `failed`로 끝낸다.
2. 후보는 유효하지만 판단 결과에서 선택 상태·역할·범위·충돌 검증이 실패하면, 전체 실패를 숨기지 않는다. 영향을 받은 필드는 `unresolved`로 낮추고, 나머지 필드도 독립적으로 서버의 형식·역할·상태·근거 검증을 통과한 값만 `suggested`로 보존한다. 원래 오류 코드와 영향 필드를 내부 진단에 남긴다.
3. 의미 검토가 이슈를 반환하면 해당 필드는 수정 성공과 재검토 통과 전까지 확정하지 않는다. 기존 수정 또는 재검토가 실패하면 마지막으로 구조 검증된 초안에서 지적 필드는 `unresolved`로 낮추고, 영향받지 않은 값만 제안으로 남긴다. 후보 밖 누락도 같은 규칙을 적용한다.
4. 의미 검토 또는 재검토가 형식 오류·제공자 오류·시간 초과로 끝나면 의미 검토가 완료됐다고 표시하지 않는다. 마지막 구조 검증 초안의 값은 모두 사용자 확인이 필요한 제안이며, 검토되지 않은 `null` 필드는 `unresolved`로 기록한다.
5. 상한·취소·민감 입력·입력 오류 등에서 초안을 검증하기 전에는 기존 실패를 유지한다. 어떤 복구도 추가 제공자 호출이나 6회·60초 예산 연장을 허용하지 않는다. 네트워크 호출의 관측 경계 초과는 결과에 별도로 보고한다.

## 격리와 서비스 경계

- 새 내부 메서드 또는 평가 전용 진입점은 opt-in이다. 기존 `analyze()`와 `AnalysisResult`, 성공 Profile JSON, 오류 코드는 변경하지 않는다.
- Spring 저장·상태·DB·Frontend 계약은 이번 구현 범위가 아니다. 복구형 결과를 서비스로 전달하려면 Full Stack A와 `needs_confirmation`의 저장 전 상태, 필드별 질문, 사용자 확인·수정 절차를 별도 합의해야 한다.
- 사용자 확인 전에는 복구형 결과를 분석 완료·확인 저장으로 표시하지 않으며 기존 확인 Profile을 덮어쓰지 않는다.

## 평가와 통과 기준

- 최초에는 합성 20건의 동일 실행에서 기존 최종 성공/실패와 복구형 결과를 함께 채점한다. 두 경로의 후보·판단·검토를 독립 재호출해 차이를 주장하지 않는다.
- 실패 유형별로 안전하게 보존한 제안 수, 정답 제안 수, 오제안 수, `unresolved` 필드·질문 수, 완전 실패 수, 시간·호출 수를 보고한다. 오제안은 사용자 확인 전 제안이며 오확정과 구분한다.
- 안전 관문: 잘못된 값의 자동 확정 0건, 잘못된 근거 보존 0건, 실패를 `complete`로 표시한 건 0건, 검증 불가 초안의 유출 0건, 추가 제공자 호출 0건. 이 중 하나라도 실패하면 실험을 기본값이나 서비스 계약으로 승격하지 않는다.
- 품질 관문: 기존 실패 사례에서 유용한 정답 제안이 늘고 오제안·질문 부담이 검토 가능한 수준인지 보고한다. 새 독립 문서가 없으므로 합성 점수만으로 실사용 가능 판정을 내리지 않는다.
