# 진단 결과
## 코드
기존 SECTION_MERGE 코드와 거절 조건을 유지하고 내부 reason/field를 추가했다.
SELECTED_SCOPE/STATUS/ROLE, SELECTED_COUNT, CONFLICTING_FACTS, ABSENCE_MULTIPLE, DUPLICATE_VALUE, PROFILE_INVALID로 원인을 구분한다.
Anchored 진단과 평가기의 안전한 메타데이터에 연결했다. 전체 테스트250건 통과.

## 첫 후보·판단 probe
합성6건, 검토 전에 의도적으로 종료한 진단이다. 분석 성공률로 집계하지 않는다.
- Q001: 원문 전체26자가 후보1개. 두 개별 동작은 독립 후보에 없음. scope=example인데 selected여서 거절.
- Q002: 요청/처리 문장 각각 후보로 존재. scope=unclear인데 selected여서 거절. 과거 짧은 명사구 exact 불일치는 의미 실패와 구별한다.
- Q003: 개발 설명/운영 미정 문장을 모두 project_name으로 selected. 스칼라 복수 선택으로 거절.
- Q004: 명시적 연동 부재 문장을 irrelevant로 제외.
- Q005: 회의 문장을 irrelevant로 제외. 이 사례는 맞음.
- Q006: 제목 아래 기능 문장에서 동작 외 접두사까지 후보에 포함. 판단 분류는 맞으나 최종 표현 골드와 다름.

## 후보를 고정한 판단 비교
후보는 첫 probe의 span으로 원문에서 재구성했다. 원문 응답을 저장하지 않고 span·열거값만 기록했다.
첫 probe none과 low는 같은 원래 판단 프롬프트/스키마/4096토큰이다.
다음 두 visible 비교군은 같은 명시적 출력 계약을 추가하고 형식만 서로 다르게 했다.

|설정|사전 판단 기준 만족|응답/검증 현상|
|---|---|---|
|원래 계약 + schema + none|2/6|Q005·Q006 분류 만족|
|원래 계약 + schema + low|1/6|Q005만 만족, INCOMPLETE_RESPONSE 3건|
|명시적 계약 + schema + none|4/6|Q001·002·005·006 만족, 구조 검증6/6|
|명시적 계약 + json_object + none|4/6|같은4건 만족, Q003·004 역할 계약 검증 실패|

- 분류 기준은 실행 전에 plan.md에 기록했다. 자동 채점기를 새로 만든 수치가 아니라 고정 기준과 보존된 열거값을 대조한 개발자 판정이다.
- low는 Q001·003·004에서 응답 불완전. 원본/finish_reason을 별도로 보존하지 않았으므로 토큰 소진을 확정하지 않는다.
- visible schema는 Q003 개발 설명/미정 문장을 features로 선택했고 Q004 부재를 negated로 제외했다. 구조 검증 통과가 의미 정답을 보장하지 않는다.
- JSON object로 바꾸는 것만의 의미상 이점은 이번6건에서 확인되지 않았다.
- 각1회이며 작은 튜닝 자료다. 명시적 계약의 효과는 반복·다양한 사례로 검증해야 한다.
- Q001/Q006 후보 범위가 그대로라 전체 분석 품질 점수로4/6을 보고하면 안 된다.

## 다음 수정 가설
1. 판단 프롬프트에 JSON 계약/필드 정의/역할 대응/확정·부재·미정 의미를 명시한다. 스키마가 설명을 대신한다고 가정하지 않는다.
2. 후보 프롬프트에 하나의 값/동작 단위와 접두사 제외 원칙을 명시한다. actor/action 구분을 잃을 만큼 잘게 자르지 않는다.
3. 개발 전용 도구와 명시적 전체 부재를 별도 반례로 검증한다.
4. 이번6건 외 새 합성 반례를 먼저 고정하여 일반 규칙 개선인지 확인한 후 전체 pipeline을 재평가한다.
추출/판단 분리 아키텍처 및 공개Profile은 유지한다. 현재 목표는 미달이다.
