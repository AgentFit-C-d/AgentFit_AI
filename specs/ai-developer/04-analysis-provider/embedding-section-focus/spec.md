# 임베딩 구역 포커스 실험 명세

## 질문
현행 후보 생성은 문서의 모든 구역을 최대 2묶음으로 보내며 24,000자를 넘으면 실패한다. 임베딩으로 중요한 구역을 표시하면, 모든 구역을 보내는 현재 흐름보다 후보 누락을 줄이는가?

## 범위
- 독립된 합성 다구역 문서 8건을 작성한다. 각 문서의 현재 제품 사실 위치와 정확한 문구를 미리 표시하고, 과거/예시/다른 제품/미정 구역을 섞는다. 기존 33건 짧은 자료는 구역 검색 평가에 쓰지 않는다.
- NVIDIA `nvidia/nemotron-3-embed-1b`의 passage/query 임베딩을 사용한다. 동일한 10개 Profile 필드 질의를 모든 문서에 사용한다. 정답 필드를 질의 선택에 사용하지 않는다.
- 서버의 기존 분할 구역과 원문 위치를 유지한다. 임베딩은 구역의 우선순위만 정하며 인용문·offset을 만들지 않는다.
- 구역 top 4의 금 정답 포함률을 전 구역(상한선) 및 단순 키워드 검색 top 4와 비교한다. 각 문서의 금 구역은 최대 4개다. 검색의 잘못된 우선순위, 누락, API 호출 시간도 측정한다.
- 현행 Solar 후보 생성 프롬프트를 모든 구역에 적용해 금 문구의 원문 span을 후보로 회수했는지도 측정한다. 후보 모델의 누락과 검색기의 누락을 별도로 집계한다.
- 검색이 정답 구역을 충분히 보존할 때에만 기존 Solar 후보 생성 프롬프트에 우선 구역 힌트를 추가한 동일 문서 교차 비교를 진행한다. 스키마와 서버 검증을 유지하며 모든 구역을 보낸다.

## 사전 관문
- 임베딩 top 4가 8건 전체의 모든 금 정답 구역을 포함하고 현행 후보 생성에 누락이 실제 관찰돼야 우선 구역 힌트 비교로 진입한다. 합성 소표본의 전부 포함은 실사용 증명이 아니다.
- 후보 생성 비교에서는 금 문구를 포함하는 원문 span의 회수율이 증가해야 하고, 잘못된 인용·검증 오류·호출 예산 악화가 없어야 한다. 미달이면 서비스에 통합하지 않는다.
- 서비스 기본 분석기, 공개 Profile, 최대 6회/60초는 변경하지 않는다. 실제 문서·예약 공개 문서는 전송하지 않는다. 키·임베딩 벡터·원본 응답을 결과에 기록하지 않는다.

## 근거와 한계
NVIDIA 공식 문서는 이 모델이 한국어를 지원하고 query/passage를 구분해야 한다고 명시한다. 이는 검색 가능성의 근거이지 AgentFit 정확도 향상 근거는 아니다. [모델 카드](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-embed-1b), [API](https://docs.api.nvidia.com/nim/reference/nvidia-nemotron-3-embed-1b-infer).
