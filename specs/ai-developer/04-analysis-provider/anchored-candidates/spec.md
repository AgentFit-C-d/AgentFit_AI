# 원문 단위 후보 생성·판단 분리 — 구현 전 검토안

상태: 사용자 설계 승인 후 opt-in 구현 및 첫 파일럿 진행. 목표의 완료 기준은 draft-readiness를 유지한다.

## 근거
현재 quote-only 추출도 한 번에 field/quote/context/role/status/scope를 정한다. Jev 실험은 이렇게 이미 잘못 분류된 후보를 선택하는 방식이라 앞 단계 오류를 복구할 수 없었다.
조건부 스키마는 잘못된 조합만 막았고, 부재와 개발 설명의 의미 오판은 남았다.
새 접근은 첫 후보 생성에서 분류 라벨을 아예 받지 않고, 별도의 Solar 판단 단계가 원문을 보며 라벨을 부여하도록 한다.
효과는 미확인이다. 기존 분리 실험이 실패했다는 사실을 기록하고 사전 기준으로 중단 여부를 판단한다.

## 변경 제안
1. 서버가 문서를 원문 보존 단위로 분할하고 고유 ID·전역 오프셋·제목 경로·인접 문맥을 제공한다. 문장만으로 잘라 표/목록/코드의 의미를 잃지 않는다. 기존 sections를 기반으로 단위 크기와 보존을 검증한다.
2. 후보 생성 응답은 unitId와 원문 짧은 인용만 가진다. field/role/status/scope는 없다. 명시적 부재는 완전한 부정 문장을 인용하며 원문 문맥을 항상 함께 보낸다. 같은 단위 내 중복 인용은 모호하므로 실패한다.
3. 서버가 quote 위치를 계산해 후보 ID를 발급한다. 원문에서 찾지 못한 인용·단위 누락·초과는 구조 실패. 임의의 첫 일치/자동 축약/누락 결과 정상화 금지.
4. Solar가 모든 후보 ID에 한 번씩 판단을 제공한다: 현재 제품 사실 여부, 필드, 역할, confirmed/tentative/negated/historical/absent 상태. 제외 후보도 이유를 갖는다. 추출 단계의 라벨은 입력에 존재하지 않는다. 내부 타입 결합 제약을 사용하되 불확실성을 강제로 확정하지 않는다.
5. 서버가 현재 확정된 후보만 기존 Profile로 변환한다. 명시적 부재는 배열 []+근거, 미정은 null+근거 없음. 기존 계약에서 가능한 표현임을 profile.py/merge_profile에서 확인했다.
6. 전체 원문 대비 의미 검토를 유지한다. 수정 시 선택된 후보 ID의 판단만 고친다. 없는 후보 추가가 필요하면 성공으로 덮지 않고 누락 실패를 기록한다.

## 예산과 실패
후보 생성 최대2회, 판단1회, 의미검토1회, 판단수정1회, 재검토1회: 최대6회.
기존 60초 협력적 예산, 문서 최대2묶음/묶음12000자 유지. 더 긴 공개 문서를 조용히 자르지 않는다.
후보 상한120 유지. 모든 원문 단위 처리 및 모든 후보 판단을 확인한다. 근거/호출/시간 검증 우회 없음.
실패 원본만7일. 평가 보고에는 원문/자유 텍스트 보관 없음.

## 영향
내부 후보·분류 계약과 파이프라인 순서가 달라지는 주요 변경이다. 공개 Profile·Spring/API·DB·기본 분석기는 유지하고 opt-in 실험 경로로 만든다.
추가 단계가 아니라 기존 추출/merge 역할을 변경하지만, 인접 문맥과 후보 증가로 토큰·지연이 늘 수 있다.
후보 생성 단계에서 누락한 사실을 후단 판단이 복구할 수 없는 한계는 남는다. 반드시 recall과 단계별 탈락을 측정한다.

## 고정 검증
- 원문 보존/중복/CRLF/표/부재·미정/문서내명령/호출상한 회귀 테스트.
- 기존 6사례 exact candidate 점수는 별도 보존. 목표는 최종 Profile 의미 정확도로 평가하며 단계별 누락도 함께 기록.
- 모델 출력 전 최종 Profile 의미 골드와 허용 표현을 고정한다. 외부 검증 후보는 아직 사용하지 않는다.
- 최소 비교에서 중대 오확정0, 핵심 의미 모두 회수, 근거 검증100%를 3회 반복 만족해야 기존 실제 튜닝 문서로 확대한다.
- 미달하면 새로운 프롬프트를 계속 추가하지 않고 실패 단계와 원인을 보고해 구조를 재검토한다.
