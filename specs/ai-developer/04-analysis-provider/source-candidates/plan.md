# 구현 계획
## 판단
전체 문장 후보만 제공하면 짧은 기능명을 고를 수 없고, 모든 부분문자열을 제공하면 후보 수가 제곱으로 늘어난다. 따라서 서버 토큰 ID의 시작/끝 쌍을 선택한다. 범위를 잘못 고를 위험은 남으므로 의미 회귀를 유지한다.
## 구현
1. 독립 source_candidates 모듈: 결정적 토큰 분할/오프셋/후보수 제한. 원문 변형 없음.
2. 기능 내부 스키마 및 프롬프트를 ID 선택으로 교체. 메타데이터 호출에는 후보표를 추가하지 않는다. features가 포함된 추출/수정 호출에는 같은 후보표와 상한을 제공한다.
3. 기능 검증은 원문에서 값을 복원하고 기존 Profile 검증으로 넘긴다. 모델 생성 인용을 허용하는 호환 fallback 없음.
4. 단위 테스트를 먼저 실패시킨 뒤 구현. 기존 내부 계약 테스트는 새 계약으로 옮기되 검증 의도를 보존한다.
5. profile-v22로 고정 평가. 실패 원인에 근거한 변경만 고려하고 무한 재실행하지 않는다.
6. 검증/제약 문서와 README 갱신, 범위·비밀값 검사 후 feature/source-candidate-selection push.
## 제약
Python 표준 라이브러리만 사용. HTTP API/DB/배포/다른 모델 도입 없음. 기존 로컬 평가 원문/루브릭/Profile은 Git에 포함하지 않는다.
