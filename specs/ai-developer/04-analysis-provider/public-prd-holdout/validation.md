# 공개 PRD 독립 평가 검증 기록

## 준비 상태

- 2026-09-29: 공개 GitHub PRD 5건의 파일 크기와 Git blob ID를 확인했다.
- 각 저장소의 기본 브랜치 HEAD 커밋을 `sources.json`에 고정했다.
- 고정 raw 파일을 다시 내려받아 5건 모두 SHA-256 일치, UTF-8 디코딩 성공, 100,000바이트 이하임을 확인했다. 크기는 순서대로 8,850 / 22,483 / 32,985 / 96,718 / 23,970바이트다.
- 기존 분석 명세 폴더에서 해당 프로젝트명·저장소명은 검색되지 않았다. 다른 외부 사용 이력까지 증명하지는 못한다.
- 소스 목록 고정 당시에는 모델 호출과 정답 작성 전이었다. 아래 정답 작성 후에도 평가 실행은 아직 하지 않았다.

## 모델 호출 전 수작업 정답

- 2026-09-29: `manifest.json`에 5개 PRD의 양성 점검 35개와 명시적 미정 필드 5개를 기록했다. 고정 원문 다운로드 후 모든 인용이 각 문서에 정확히 한 번 등장함을 검증했다.
- 총 50개 문서·Profile 필드 조합 중 38개 필드에 양성 또는 미정 정답이 있다. 나머지 12개 필드는 미평가이며, 양성 점검 35개는 기능 배열의 여러 항목을 포함한다. 부분 정답만으로 전체 정확도를 주장하지 않는다.
- 기존 공개 튜닝 매니페스트와 저장소·문서 SHA-256이 겹치지 않는다. 모델 전송 차단에 쓰이는 `_SENSITIVE` 패턴은 5건 모두 불일치했다. 이는 실제 비밀값 부재를 완전히 증명하지는 않는다.
- 선택적 `unknown_fields` 검증과 `public-evidence-v4` 집계를 실패 테스트부터 구현했고 공개 평가 테스트 23건이 통과했다. `null` 유지와 비 `null` 값은 구분하며 비 `null`을 미평가 값에도 중복 집계하지 않는다.
- 모델 호출 전 고정한 구성은 (1) 기본 추출 옵션, (2) `repair-context-options`와 `parallel-first-pass` 동시 사용이었다. 두 구성 모두 `analyze_recoverable`, `solar-pro4`, 근거 계약, 의미 검토, 40초였다.

## 최초 평가 결과

- 정답표는 첫 호출 전에 커밋 `e8735b9`로 원격 브랜치에 push했다. 당시 manifest SHA-256은 `fa463b8427ee5aef12c6bc70cf6464b6d5199302f8cac912b345f8ba8a2390f1`이었다.
- 기본 추출 구성: 5건 중 자동 완료 0, 확인 필요 5, 실패 0. 점검 35개 중 정답·근거 위치 일치 11, 값 누락 21, 근거 판정 불가 3, 확정 근거 오류 0. 명시적 미정 5개는 모두 `null`이었다. 정답 밖 출력 값 8개는 평가하지 않았다. 문서별 확인 질문은 8~10개, 최장 40,082ms, 호출은 최대 3회였다.
- 선택형 문맥·병렬 구성: 자동 완료 0, 확인 필요 4, 실패 1. 채점 가능했던 4건의 점검 29개 중 일치 9, 값 누락 15, 근거 판정 불가 5, 확정 근거 오류 0. 명시적 미정 4개는 모두 `null`이었다. 정답 밖 출력 값 10개는 평가하지 않았다. DeReel은 40초 Provider 기한으로 완전 실패하여 해당 6개 점검과 미정 1개는 채점하지 못했다. 최장 40,058ms, 호출은 최대 3회였다.
- 10개 실행 모두 자동 완료하지 못했다. 기본 구성에서 3건, 선택형 구성에서 2건이 최종 `PROVIDER_TIMEOUT`이었다. 나머지는 `INVALID_EVIDENCE` 또는 확인 필요 초안으로 끝났다. 최초 core 추출 검증 성공은 기본 구성의 Campfire 1건뿐이고, 최초 features 추출 검증 성공은 선택형 구성의 Campfire 1건뿐이었다. 수정 호출은 두 구성 모두 완전한 Profile을 만들지 못했다.
- 두 구성의 응답은 서로 다른 모델 실행이며 첫 구성을 본 뒤 옵션을 변경하지 않았다. 일치 수 11과 9를 인과적 개선량으로 해석하지 않는다. 확인 필요 초안의 미정 보존은 자동 정확도와 다르다.
- 산출물은 ignored 로컬 `tmp/public-prd-holdout-baseline-20260929/` 및 `tmp/public-prd-holdout-options-20260929/`에 있다. 두 폴더의 JSON 6개에 API 키 또는 5개 전체 원문이 포함되지 않음을 확인했다. 이 결과를 본 뒤 manifest를 `tuning`으로 전환했다.

## 판단과 다음 작업

- 독립 PRD 평가가 실사용 품질을 지지하지 않는다. 자동 완료 0건, 양성 점검 다수 누락, 확인 질문 8~10개, 40초 기한 반복으로 현재 경로를 운영 기본값으로 전환하지 않는다.
- 반복 실패의 공통 원인은 첫 추출에서 원문과 정확히 일치하지 않는 인용을 생성하고, 수정 단계가 남은 기한 안에 복구하지 못하는 것이다. 다음 실험은 모델이 인용문을 새로 쓰게 하지 않고 서버가 후보 구간을 제공·고정하는 방식과 기한 배분을 검토한다. 이 5건은 이제 튜닝 자료이므로 다음 최종 검증에는 새 독립 자료가 필요하다.
- Spring/Frontend의 확인 후 저장 경로와 실제 사용자 문서의 사람 검수는 여전히 확인되지 않았다. 공개 PRD 부분 정답 38/50 필드 범위와 단일 실행으로 출시 판정을 내리지 않는다.

## 원문 해석 주의

- `gongsi-mcp` PRD는 스스로 현재 구현과 다른 역사 문서라고 밝힌다. 평가는 이 PRD의 기획 내용만 대상으로 한다.
- `TrueTwo` PRD는 별도 product brief를 참조한다. 입력에 포함되지 않은 외부 문서는 정답 근거로 사용하지 않는다.
- `DeReel` PRD에는 잠정 기술 스택과 Phase별 계획이 섞여 있다. 확정 필드로 단정하지 않도록 정답 작성 시 상태를 구분한다.
