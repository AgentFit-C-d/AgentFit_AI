# 검증
N-004 단독 수정 호출을 모델·프롬프트·정답·구역·low·40초 timeout 고정으로 각3회 비교했다. 두 plan.json은 max_tokens 이외 모든 필드가 같았다. 평가 코드상 요청 메시지와 schema 구성도 동일하다.

| 상한 | 통과 | 중앙값 | 최장 |
| --- | --- | --- | --- |
| 4096 | 3/3 | 14719ms | 15718ms |
| 8192 | 3/3 | 33093ms | 36391ms |

4096 completion_tokens: [1718, 1543, 1999].
8192 completion_tokens: [4146, 4146, 4183].

## 해석
이번 단독 호출에서는 기존 상한의 실패가 재현되지 않아, 상한 확대가 실패율을 낮췄다는 증거는 얻지 못했다. 8192 조건의 관측 지연은 더 길었지만 각3회 순차 평가이므로 시간대·샘플 변동과 분리한 인과 효과로 단정하지 않는다.
이 입력은 이전 전체 분석과 같은 문서이나, 단독 평가가 previous와 issue를 고정 구성한다. 이전 실제 요청의 전체 payload를 그대로 재생한 실험은 아니다. 따라서 과거 미완료가 해결됐다고 말하지 않는다.

## 결정과 후속
서비스 토큰 상한은4096으로 유지한다. 근거 없는 전체 확대는 하지 않는다. 다음은 전체 흐름에서 실패한 수정 요청의 비밀 없는 합성 입력을 메모리에서 그대로 잡아 동일 요청을 비교하는 진단이다. 특히 이전 whole-flow와 단독 평가 사이의 previous·issue·근거라인 차이를 먼저 확인해야 한다. 실패를 재현하지 못한 상태에서 프롬프트·구조를 추가로 고치지 않는다.
전체 분석60초·6회, 근거 검증과 공개 Profile은 변경하지 않았다. 전체 unittest290건 통과. 잘못된 --max-tokens 0은 API 호출 전에 거부됐다. 새 단위 테스트는 추가하지 않았다. 예약 공개 문서와 사람 수정 부담 평가는 미실행이며 목표는 미달성이다.
