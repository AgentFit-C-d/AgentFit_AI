# 구역별 기능 검토 검증

## 코드 검증

- 선택형 CLI `--section-feature-review`는 원문 선택자·묶음 검토·8K·정확도 우선·600초 평가 모드에서만 활성화된다. 기본 분석기와 공개 Profile은 변경하지 않았다.
- 구역 분할·응답 범위·대상 ID·안전 보류·12호출 경계를 단위 테스트로 검증했다.
- Windows 로컬 전체 `unittest discover -s tests`: 656건 통과 (2026-09-29). 실제 API 전송과 별개의 코드 검증이다.
- 독립 코드 리뷰가 서로 다른 기능 값의 부분문자열 때문에 다른 항목의 근거를 잘못 청크에 귀속시키는 오류를 재현했다. 항목과 원래 selector 근거 span의 순서 연결을 사용하도록 수정하고 회귀 테스트를 추가했다. 수정 후 Windows 로컬 전체 테스트 657건이 통과했다. 수정 커밋의 Linux CI는 별도로 확인한다.

## 실제 문서 1건

고정 튜닝 문서 Campfire PRD 1회, Solar Pro 4. 결과 파일은 `tmp/section-feature-review-campfire-20260929-1/{plan,results,summary}.json`이다. 공개 평가 파일에는 원문·키·원본 모델 응답·Profile이 없다.

| 항목 | 결과 |
|---|---:|
| 원문 줄 | 547 |
| 기능 검토 청크 | 6 |
| 총 provider 호출 | 10/12 |
| 기능 청크 응답 | 6개 모두 형식 검증 통과 |
| 자동 완료 | 0/1 |
| 확인 필요 | 1/1 (`SEMANTIC_REJECTED`) |
| 부분 정답 | 2/7 |
| 누락 정답 | 5/7 |
| 잘못된 근거 | 0 |
| 미평가 값 | 1 |
| 실행 시간 | 197,154ms |

원문 전체를 청크로 검토하는 흐름은 완주했다. A/B 검토와 기능 청크 5개에서 의미 이슈가 검출돼 자동 완료를 막았다. 한 번의 실행으로 누락이 추출 단계·모델 판단 단계 중 어디에서 비롯됐는지는 확정할 수 없다. 튜닝에 사용된 공개 문서의 부분 정답이므로 서비스 정확도의 독립 검증 자료가 아니다.

나머지 고정 튜닝 문서 4건의 추가 Solar 전송은 자동 승인 검토에서 거절됐다. 사유는 Campfire가 `needs_confirmation`으로 끝나 사전에 정한 확대 조건을 충족하지 않았다는 것이다. 전송을 재시도하지 않았다.

리뷰 수정 후 같은 Campfire 1건을 다시 실행했다. 안전한 결과 파일은 `tmp/section-feature-review-campfire-20260929-2/{plan,results,summary}.json`이다. 6개 기능 청크가 다시 모두 형식 검증을 통과했고, 총 10호출·213,952ms에서 `needs_confirmation(SEMANTIC_REJECTED)`로 끝났다. 부분 정답은 다시 2/7, 누락은 5/7, 잘못된 근거는 0, 미평가 값은 3이었다. 두 실행은 모델 응답도 달라졌으므로, 미평가 값의 차이를 코드 수정의 인과 효과로 해석하지 않는다.

## 승격 판단

이 모드는 계속 선택형 실험으로 둔다. 독립 실제 문서의 사람 검토, 정답 밖 오확정 점검, Spring/Frontend의 확인 전 저장 금지 E2E를 완료하지 않았고, Campfire에서 자동 완료 및 충분한 정답률을 입증하지 못했다. 다음 작업은 검토가 찾은 문제를 원문 후보·판단·수정 중 어느 단계에서 만들었는지 안전한 관측값으로 분리하는 것이다.
