# 원인과 최소 변경

## 재현 (수정 전)
profile-v2, model=solar-pro4, reasoning=medium, temperature=0, max_tokens=4096.
기존 TEXT-SEM-002를 사전 지정한 5회 진단한 결과 전부 이름이 “예약 관리 프로젝트”였다. 사전 정답은 “예약 관리”다.
수신값은 원문에 존재하여 기존 구조/근거 검증기를 통과했다. 의미 경계 문제를 문자열 포함 검사로 잡을 수 없다는 기존 제한과 일치한다.
실측: baseline.json. 합성 이름만 기록했고 운영 원본 응답은 저장하지 않았다.

## 가설
“원문의 표현 그대로” 지시와 “이번 X 프로젝트면 X”의 짧은 규칙만으로는 이름과 설명어의 경계가 충분히 전달되지 않는다.
내부 추론은 관찰하지 않았으므로 모델의 사고 원인은 가설이다. 직접 확인한 현상은 5/5에서 접미 설명어가 추가된 것이다.

## 최소 변경
profile-v3에서 프로젝트명 경계 규칙·대조 예시를 보완한다. 사전 정답이나 검증기는 바꾸지 않는다.
명시한 고유 이름 안의 “프로젝트”를 보존하는 예외를 함께 지시한다. 문자열을 일괄 삭제하는 후처리는 추가하지 않는다.
API/모델/온도/추론 설정/토큰 한도/재시도 정책은 그대로 둔다.

## 평가 구분
- baseline: 알려진 실패 사례5회.
- 기존6건과 사전 추가6건을 각각2회, 총24회 고정 평가.
- 새로운6건은 프롬프트 수정 전에 고정했지만 개발자가 사례를 알고 작성했으므로 완전한 블라인드 평가가 아니다.
- name_passed는 검증된 결과가 정답 이름(null 포함)과 일치했을 때만 센다. API 오류도 전체 실패에 포함한다.
- 전체10필드 비교를 함께 집계하여 이름만 맞고 다른 필드가 퇴행한 경우를 숨기지 않는다.
