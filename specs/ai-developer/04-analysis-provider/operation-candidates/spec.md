# 기능 동작 표현 후보 추출

## 목적과 근거

이전 목표 작업은 공통 필드 지침·동일 후보 비교·push·CI를 완료한 progress다. H02에서는 최종 기능 목록이 별칭/입력 대상으로 구성되고, 표본 동작 표현6개 중5개는 후보 구간에 없었다. 기존 후보를 계속 검토하는 것만으로 빠진 표현을 복구할 수 없으므로 동작 후보를 별도로 확보한다.

## 선택형 계약

- 기존 기본 분석기·공개 Profile을 유지한다. 새 NVIDIA 후보 생성기는 기능과 관련된 원문 표현을 최대60개 `{quote,anchor}`로 반환한다. quote는 최대200 code point, anchor는 최대1000 code point이며 원문의 연속 구간이어야 한다.
- 행위 대상과 동작이 드러나는 짧은 명사구/절을 우선한다. 제품명·기술명·입력 객체만 고르거나 문서에 없는 기능 이름을 합성하지 않는다. 부정·검토안·미래·다른 제품 표현도 후보로 남기며 추출기는 확정 판정을 하지 않는다.
- 서버는 기존 anchored grounding으로 quote·anchor의 정확하고 유일한 위치를 확인한다. 모호·원문 불일치·중복은 반려 목록으로 남긴다. 응답 형태나 길이가 잘못되면 전체 호출 실패이며 부분 성공으로 숨기지 않는다.
- 별도 분류 호출은 기존 explicit-v1 의미 지침으로 각 후보의 필드/상태를 판정한다. 원문 전체·주변 문맥·후보ID를 사용하며 모델이 값/위치를 수정할 수 없다. 분류는30개씩, 같은 NVIDIA 모델로 수행한다.
- 기존 후보와 새 후보를 원문 `(start,end)`로 병합하고 C000부터 새 ID를 부여한다. 동일 위치의 필드/상태가 충돌하면 자동 선택하지 않고 실패한다. 중복 위치의 동일 라벨은 하나로 합친다. 반려 수는 합산하고 합쳐진 후보가240개를 넘으면 실패한다. 이전ID는 병합 후 사용할 수 없으며 평가에 구간-새ID 대응이 필요하다.
- 최종 판단은 기존 분리 검토·explicit-v1 커버리지·Profile 변환을 거친다. 추출 성공을 의미 정확도나 전체 완료로 취급하지 않는다. 기능30개 초과 및 기존 확인 필요 조건을 유지한다.
- 실험 호출 상한은 추출1+새 후보 분류2+최대12개 검토묶음+커버리지1=16회다. 기본 서비스 호출 예산은 바꾸지 않는다. 자동 재시도/수정 호출은 추가하지 않는다.
- 원문·인용·응답·키를 공유 결과에 저장하지 않는다. API 키가 문서에 있으면 호출 전 거부하며 안전한 위치/ID·반려 사유·수치만 저장한다.

## 평가

원문 위치·Unicode·동일 인용의 서로 다른 문맥·부정/미정 후보 보존·중복/충돌·상한·응답 모델 위장/절단을 검사한다. 실제 승인 H02에서는 기존 snapshot의 source hash를 확인하고 새 동작 후보가 원문에 있는지, 최종 대표 기능이 행동을 나타내는지 로컬 대조한다. 이전6개 골드나 표본 문자열 커버리지만으로 전체 기능 재현율을 주장하지 않는다. 이후 다른 문서·반복 안정성·HTTP/Spring 연동은 별도 필요하다.

목표 단위 자율 승인에 따라 명세·계획 후 직접 구현한다.
