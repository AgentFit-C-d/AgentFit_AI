# 후속 검토 실패 복구 경계 — 오프라인 전용

## 승인 범위와 완료 기준

2026-10-03 요청에 따라 기존 실패 실행의 추출·분류 결과를 검사하고 별도 재개 계획을 만든다. 서비스 재개, 실제 전송, 새 응답 계약, 부분 Profile 노출은 구현하지 않는다. 큰 Goal은 paused다. 외부 네트워크는 차단하고 기존 raw 기록은 읽기만 한다.

## 선택한 경계

전체 파이프라인 재실행은 성공한 23요청을 다시 보낼 위험이 있다. 중간 결과를 서비스 성공 응답으로 바꾸는 방식도 허용되지 않는다. 따라서 진단 도구에서 기존 분류 완료 경계를 검증하고 기존 검토 함수만 오프라인으로 호출한다. 저장된 성공 검토 묶음은 동일 요청일 때만 재생하고, 첫 실패 요청 직전에서 계획 생성을 멈춘다. 실패 이후 요청은 실행하지 않는다.

## 신뢰와 일치 조건

- 원본 실행의 필수 기록·코드 snapshot을 별도 SHA-256 manifest로 동결한다. 이번에 만든 seal은 과거 기록의 외부 서명이나 실행 당시의 출력 hash를 대신하지 않는다.
- freeze의 원문/골드/실행 파일 hash, 현재 원문·원본 runtime 파일, endpoint/model/config, Python/패키지 버전을 대조한다. 신규 오프라인 진단 모듈은 기존 실행 파일 변경으로 간주하지 않되 기존 분석 파일의 누락·추가·변경은 거부한다.
- trace와 checkpoint의 단계·호출을 대조한다. journal·요청별 완료 marker·call metadata의 순서/성공/실패/소비량을 검증한다. 시작 marker만으로 성공을 인정하지 않는다.
- 기존 위치 연결·병합·분류 검증기를 사용한다. 원문 Unicode 위치, ID·순서·후보 집합, 원시 응답→분류 결과, 실제 재생 요청 전체(지침/스키마/model/options 포함)를 일치시킨다.
- 유효한 성공 검토 응답의 checkedCandidateIds만 검토 완료로 기록한다. 일반 transport 성공만으로 검토 검증 성공을 추정하지 않는다.
- 누락/손상/불일치/미완료 전송/예상하지 않은 단계는 fail closed. 불확실한 기록을 정답으로 보정하지 않는다.

## 재개 기록과 예산

원본 경로/manifest hash, 후보 상태 hash, 다음 요청 hash, 완료 검토 ID와 미검토 ID, 원본 실패 및 미완료 단계를 새 파일에 연결한다. failed/v3 응답은 그대로다. 모의 재개도 원본 소비량+모의 소비량을 합산하고 요청 전에 예산을 차감한다. 원본 ID별 단일 claim을 원자적으로 생성해 다른 이름의 중복 실행도 거부한다. claim이 남은 불완전 실행은 자동 재개하지 않는다.

현재 전체 승인 1800초의 남은 약76초를 새1800초로 초기화하지 않는다. 원래 첫 실패 중단·재시도0 승인은 이미 종료됐다. 실제 재개에는 실패 요청 재전송, 무료 조건, 합산 호출/시간 예산, 실행 구현에 대한 별도 승인이 필요하다.

## 검증

정상 계획, 원문/코드/설정 불일치, 기록 누락/손상, ID/위치/응답 불일치, 중복 claim, 일부 검토 성공 후 실패, 추가 실패 즉시 중단, 호출/시간 한계, 네트워크 차단을 검사한다. 합성 전송은 로컬 JSON뿐이며 40개 실제 의미 점수를 생성하지 않는다. 최종 Profile/사용자 승인/저장 상태는 만들지 않는다.
