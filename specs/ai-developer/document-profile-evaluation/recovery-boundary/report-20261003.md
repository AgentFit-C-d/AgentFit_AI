# 후속 검토 실패 복구 경계 — 설계·오프라인 검증

## 결론

**저장된 추출·분류 결과는 엄격한 일치 검사 후 재사용할 수 있다. 현재 서비스에서 바로 실제 재개할 수 있는 상태는 아니다.** 이번에는 read-only 검사기, 재개 계획, 합성 검증만 구현했다. 큰 Goal은 paused이며 실제 모델 호출·실패 요청 재전송·외부 네트워크 전송은 0이다.

원본: `E:/AgentFit/output/document-profile-v3-live-20261002-v1`. 원본 실행 코드 `9385e22d39494165e5f0b841ea6d611a7435973b`. 새 산출물: `E:/AgentFit/output/review-recovery-offline-20261003-v1`.

## 1. 기존 보존 상태와 정확한 경계

| 구간 | 원본 기록 | 재사용/완료 판단 |

trace와 checkpoint에는 위 단계·실제 요청24개·성공 응답23개가 이미 남아 있다. 기존 recorder/관측 hook을 수정하거나 새로 만들지 않았다. 마지막 active-request의 `started`는 성공 표시가 아니며 완료 marker·journal·call metadata를 함께 확인한다.

분류 후보156개 중 supported44개가 검토 대상이다. 현재 검토 완료0, 검토 대기44, 기존 정책상 검토 대상이 아닌112개다. 원시 모델 판단·서버 분류를 바꾸지 않았다. **44나156은 정상 의미40개의 점수가 아니다.**

## 2. 실제 재개에 부족한 것

1. 서비스/worker에 검증된 상태에서 시작하는 재개 진입점이 없다. 이번 검사기는 이를 연결하지 않는다.
2. 원본 실행 당시 출력 파일 전체에 대한 외부 서명·원자적 완료 seal이 없다. 이번에 만든208파일 seal은 보존된 로컬 기록을 신뢰 기준으로 고정한 것이다. 과거 시점의 무변조까지 증명하지 않는다.
3. 원본 기록의 검토 transport 성공만으로 검토 계약 통과를 알 수 없다. 같은 코드로 저장 응답을 검증해 checkedCandidateIds와 거절 사유를 복구해야 한다. 일부 성공한 합성 기록으로 이를 검증했다.
4. 원본·여러 재개 시도에 공통으로 적용되는 운영상의 claim/소비량 저장소가 없다. 도구는 지정된 단일 ledger 안에서 원본 ID별 claim을 배타 생성한다. 다른 ledger 경로나 여러 호스트 사이의 전역 중복 차단은 미구현이다.
5. 첫 실패 종료·재시도0의 원래 승인은 종료됐다. 잔여 호출 수가 있어도 실패 요청 재전송 권한으로 해석하지 않는다.
6. 제공자의 내부 모델 build, 추론 결정성, 원격 추론 취소는 미확인이다. 확인 가능한 모델 ID·endpoint·로컬 패키지·실행 파일·프롬프트·스키마·옵션만 결속한다.

정확한 HTTP 오류 번호가 없다는 기존 진단 한계는 유지된다. 이 값 없이 실패 요청을 성공으로 추정하지 않는다.

## 3. 최소 구현과 재사용 조건

새 파일 `ai_service/diagnostic_tools/review_recovery.py`는 별도 CLI로 실행된다. 서비스에서 import하거나 호출하지 않는다. `agentfit_ai`, 기존 관측기·실행기, 모델·프롬프트·골드·계약·Spring 코드는 변경하지 않았다.

- 필수 기록과 요청별 시작/완료 marker가 seal에 모두 있어야 한다. 파일 존재만으로 통과하지 않는다.
- 원문/골드의 바이트 hash, 코드147개와 snapshot, 실제 import 경로, Python 실행 파일·버전 및 패키지 버전을 검사한다. 원문의 CRLF와 Unicode 위치를 유지한다.
- trace/checkpoint·ledger·응답 길이·오류·순서·소비량을 교차 검증한다. 음수/비정상 시간과 원본 시간 축소, 미지원 단계, 누락·손상 기록은 거부한다.
- 일반 추출은 기존 LangExtract로 저장 응답만 재생한다. 동작 추출과 분류도 동일한 방식으로 검사한다. 모든 재생 요청은 저장된 전체 payload와 같아야 한다. 지침·스키마·모델 옵션이 달라지면 중단한다.
- 후보 집합·ID·순서·원문 위치·원시 분류와 서버 처리 결과를 기존 함수로 재검증한다. 불일치한 값을 수정해서 맞추지 않는다.
- 기존 검토 함수로 성공한 저장 묶음만 재생한다. 유효한 checkedCandidateIds 및 rejectionReasons를 보존하고 첫 실패 직전에서 실제 전송 없이 멈춘다.
- 계획에는 원본 경로/seal/code hash, 후보 상태 hash, 다음 요청 hash, 완료/대기/비대상 후보 ID와 예산을 남긴다. 원본 파일에는 쓰지 않는다.

`resume-plan-final.json`의 다음 요청은 원본24번, 스키마 `agentfit_candidate_label_review`, 요청 hash `af98e18bbeaa8e7ce62d02fff2bd42e497dfb1d8dc28c1c68f8545a3c91a10ab`다. 다음 묶음 크기는20/20/4다. 전체 source coverage 요청의 입력은 검토 결과에 따라 달라지므로 미리 확정하지 않는다.

## 4. 상태와 합성 검증 결과

실제 원본 응답은 계속 다음과 같다.

```json
{"contract":"confirmation-v3","outcome":"failed","error":"PROVIDER_UNAVAILABLE"}
```

미검토 후보를 Profile 확정값이나 사용자 승인으로 보내는 경로는 없다. 합성 검토 전체를 통과해도 `simulationStatus=review_complete_synthetic`와 `analysisOutcome=failed`를 함께 기록하며 Profile을 생성하지 않는다.

전용 회귀 **20개 통과**. 핵심 확인 사항:

- 정상 원본: 성공한1–23요청을 synthetic transport로 보내지 않고24번 경계부터 계획.
- 합성 전체 통과: 후보 검토20/20/4와 source coverage, 합성4회. 원본24+합성4=28회, 원본1724.336+모의4=1728.336초로 기록.
- 일부 검토 성공 후 실패: 첫20개만 검토 완료, 나머지24개 대기. 기존 거절 ID/사유 유지. 저장된 성공 묶음을 다시 보내지 않고 두 번째 묶음부터 합성 진행.
- 추가 실패·잘못된 checked IDs: 즉시 중단. 실패/잘못된 응답은 완료 검토로 세지 않음.
- 동일 ledger에서 다른 resume 이름으로 다시 실행해도 원본별 중복 claim 거부. claim만 남은 미완료 실행도 자동 우회하지 않음.
- 원문·코드·설정·실제 import 경로 불일치, 필수 seal 누락, 손상 응답, 변경된 일반 추출 프롬프트, 후보 ID/위치/판정 불일치, 예상 밖 stage 거부.
- 호출 한도 소진은 합성 전송 전에 중단. 시간이 필요한 합성 요청도 원본 잔여시간을 적용하고 초과 후 후속 요청0.
- DNS/socket/하위 프로세스 전송 경로 차단 확인.

독립 리뷰에서 발견한 seal 집합 누락·소비량 축소·일반 추출 raw 검증 누락·미지원 stage 허용은 각각 재현 테스트를 추가하고 수정했다. 재검토에서20개 통과 및 기존 중요 지적 해결을 확인했다.

최종 전체 오프라인 suite: **1441건 실행,1434통과/7skip/실패0/오류0**. 기존 TCP29건은 외부 통신 차단 범위에서 제외했다. skip은 선택 Docling 의존성6·Windows symlink1이다. 모델 키를 환경에서 제거하고 기존 네트워크 차단 도우미를 적용했다. `test-summary-final.json`과 `offline-suite-final.log`에 전체 결과·제외 목록을 보존했다.

합성 결과는 기존40개 의미 평가에 포함하지 않았다. 새로운 추출 정확도·최종 보존·보류·누락·오확정 점수는 **미측정**이다. 서비스 응답/UI/사용자 확정/실제 Spring 연결도 미검증이다.

## 5. 예산과 향후 별도 승인 조건

| 항목 | 원본 소비/잔여 |
|---|---:|
| 호출 | 24/50회 소비,26회 잔여 |
| 실행 시간 | 1724.336/1800초 소비,75.664초 잔여 |
| 종료 예약10초 제외 | 65.664초 |
| 다음 요청의 최대 시간 | 남은 시간보다2초 짧은63.664초 이하 |

이 잔여치는 계획상의 계산이며 재전송 승인이 아니다. 원본 실패 검토302.263초, 이전 기준 검토3회 합계768.565초였으므로 잔여시간으로 완주 가능하다고 주장하지 않는다.

현재 후보로 필요한 후속 호출은 **GLM 검토3묶음+coverage1회=4회**, 검토 후 남는 고유 기능 수에 따라 기능 정리 **0–4회 추가**, 합계 **4–8회**다. 현재 기능 후보42개의 원문 값은38종이지만 검토 거절 후 수는 미정이다. 완료된 추출·분류의23회는 추가 호출 예산에 다시 넣지 않는다. 원본의 실패한1회는 소비량에서 빼지 않는다.

실제 재개를 승인받을 때의 보수적 상한 초안: 추가8회·요청당600초·종료여유10초, 추가 전체4810초(80분10초). 원본과 합하면 최대32회·약6534.336초(108분54초)다. **이 시간은 예측 소요가 아니라 최악 상한 계산이고, 현재 승인된 예산이 아니다.** 새 승인에서는 원본+재개의 합산 한도를 명시해야 한다.

필요한 후속 변경/승인:

1. 진단용 재개 worker와 공통 claim/사용량 ledger 구현·검증. 현재 API의 failed/v3 계약을 유지하는 별도 내부 실행 경계로 시작한다.
2. 매 재개·요청 전 hash/설정/후보 구성 재검사와 실제 시간 종료·프로세스 회수 검증. 이번 합성 시간 검사는 실제 재개 요청 취소 시험이 아니다.
3. 현재 무료 NVIDIA 모델·endpoint 조건 및 실패 요청 재전송1회에 대한 명시 승인, 합산 호출/시간 한도 승인. 내부 자동 재시도는 계속0, 추가 실패 시 중단.
4. 재개 결과는 원본을 덮어쓰지 않고 연결된 별도 실행에 보존한다. 이후 feature curation/최종 계약 검증이 모두 끝나기 전에는 전체 성공으로 표시하지 않는다.

## 6. 변경 파일과 종료

- `spec.md`, `plan.md`, 이 보고서: 범위·경계·제약·검증·후속 조건.
- `diagnostic_tools/review_recovery.py`: read-only 검사·계획 및 합성 재개.
- `tests/test_review_recovery.py`, `tests/fixtures/review_recovery/{manifest.json,records.zip}`: 해시 고정 fixture와 회귀.
- `work/harness/offline-review-recovery/STATE.md`: 진행/검증/중단 기록.

fixture의 Windows Python 바이너리와 다른 환경에서는 해당 실기록 재생 테스트를 건너뛴다. Linux 동등 실행을 검증한 것으로 계산하지 않는다. 실제 복구 허용도 runtime 불일치면 거부한다.

이번 외부 네트워크 차단 요구에 따라 Git push도 하지 않고 로컬 feature 브랜치에 보존한다. 운영 적용·추가 모델 호출·Goal 재개 없이 보고 후 종료한다.
