# 후보 단계별 누락 진단

## 목적과 승인 범위

처음 보는 기획서에서 근거 있는 초안을 얻고 적은 수정으로 저장하는 활성 목표를 위해, 기능 누락이 처음 발생한 경계를 찾는다. 사용자는 이번 목표의 설계·계획·직접 구현을 자율 진행하도록 승인했다. 이 문서는 현재 30회 고정 평가 종료 후 시작할 한정된 진단 작업이며, 구현은 `feature/candidate-provenance-probe`에서 수행한다.

## 관측된 문제

- 현재 DeepSeek 평가에서 PUBLIC-01과 PUBLIC-09는 각각 세 번 모두 기능 반환이 0개다. PUBLIC-07은 세 번 모두 임시 기능 정답 11개가 위치 채점에 일치했다.
- 저장된 호출 메타데이터와 최종 위치 채점만으로는 추출·분류·의미 검토·최종 변환 중 최초 누락 단계를 복원할 수 없다.
- 현 코드의 합성 재현에서는 같은 필드에 201자 후보 하나가 있으면 유효한 짧은 후보도 함께 null이 됐다. 실제 문서에 해당 경계가 작용했는지는 미확인이다.
- 인용 길이·반복 위치가 다른 출력은 현재 문자 위치 채점에서 미평가가 될 수 있다. 진단의 위치 도달 여부를 의미 정답으로 해석하지 않는다.

## 선택한 접근

기존 `analyze_nvidia_candidates(observer=...)`, `analysis_worker.execute_request`, `run_analysis_process(command=...)`를 사용하는 평가 전용 자식 프로세스를 만든다. 격리 프로세스 안에서만 기존 분석 호출에 관측기를 연결하고, 기존 worker 응답은 그대로 부모의 엄격한 검증을 통과시킨다. 관측 자료는 별도의 제한된 JSON 파일로 반환한다. 기본 서비스의 요청·응답 계약과 분석 알고리즘은 유지한다.

기존 `CandidateStageDiagnostics`는 부분 문자열 gold 계약이므로 새 위치 진단의 근거로 사용하지 않는다. 기본 서비스 패킷 전체에 새 메타데이터를 전파하는 방식보다, 이번 진단만 사용하는 worker와 runner가 변경 범위가 작다. 원본 응답을 보관하는 방식은 현재 진단에 필요하지 않다.

## 기록할 정보

1. `grounded`: 후보 ID와 코드포인트 시작·끝 위치, rejected 개수. 일반 추출과 동작 추출을 합친 이후 경계임을 명시한다.
2. `classified` / `reviewed`: 후보 ID별 필드·상태, 필드별 확정 후보 수·고유 값 수·200자 초과 ID·공백 ID. 원문과 값 자체는 저장하지 않는다.
3. `projected`: 필드별 값 개수와 근거 위치. null과 명시적 빈 배열을 구분한다.
4. 최종 분석 결과: outcome, candidateCount, rejectedCandidateCount, unresolvedFields, reviewIssueCount, 선택적인 featureCuration의 개수. 이 값으로 전체 필드 확인 승격의 원인을 구분한다.
5. 실행·검증 상태: 미관측 단계는 null, 진단 실패는 고정 코드. 관측되지 않은 단계를 누락으로 세지 않는다. 기능 정리가 먼저 실패하면 reviewed 훅도 미관측일 수 있다.

최대 후보 240개, 허용된 10개 필드와 `other`, 소스 범위 안의 정수 위치, 기존 계약의 상태 enum만 허용한다. 단계 순서·ID 정합성·크기·필드별 자료형을 검증한다. 진단 JSON은 UTF-8 2MiB 이하이며 비밀 값·원문·값·응답·예외 문자열·임의 모델 문자열을 포함하지 않는다.

## 독립성과 실패 처리

- 관측기는 pipeline이 전달한 복사본만 읽는다. 정상 관측 유무에 따라 동일한 합성 응답의 모델 payload·호출 수·최종 응답이 같아야 한다.
- 관측기 내부 오류나 파일 기록 오류가 발생하면 진단을 무효로 표시한다. 기존 분석의 정상 결과를 변경하거나 자동으로 재호출하지 않는다.
- 부모는 요청별 새 출력 경로를 소유하며, 기존 파일·심볼릭 링크·부분 기록을 성공으로 수락하지 않는다. 요청 ID·소스 SHA256·설정·진단 도구 SHA256을 결과에 묶는다. 기존 평가 결과 폴더를 재사용하지 않는다.
- 문서와 API 키는 기존 stdin 프로토콜로만 전달한다. 키를 argv·환경 확장·로그·진단 자료에 넣지 않는다. 기존 deadline·취소 시 자식 종료를 유지한다.
- gold는 부모의 사후 위치 비교에만 사용한다. worker나 모델 요청에 전달하지 않는다. 진단은 추출 품질을 변경하지 않는다.

## 실행 예산

구현·로컬 검증은 외부 모델 0회·유료 0회·재시도 0회다. 구현은 90분마다 증거·남은 범위를 재검토하며 로컬 테스트 그룹당 180초를 상한으로 한다. 신규 의존성을 설치하지 않는다.

실제 진단은 현재 기준선 종료 및 구현 검증 후 PUBLIC-01, PUBLIC-09, PUBLIC-07을 각 1회 실행한다. 요청당 최대 1800초·64모델 호출, 합계 최대 192호출·90분, 재시도 0회다. 모델은 기존과 같은 `deepseek-ai/deepseek-v4.1-flash`를 모든 단계에 사용한다. 기존 무료 확인 범위와 만료를 매 요청 전 확인하며 초과·요금 미확인·제공자 오류 시 새 요청을 중단한다. 같은 응답을 재생하는 비교가 아니므로 품질 개선율을 주장하지 않는다.

## 완료 조건

- 합성 테스트에서 정상 후보·분류 제외·검토 제외·긴 후보의 필드 전체 보류·미관측·진단 오류를 구분하고 실제 호출 payload와 결과가 변하지 않음을 증명한다.
- 실제 자식 프로세스와 로컬 가짜 제공자에서 평상 경로·진단 경로의 동일성, deadline/취소 정리, 경로 충돌, 부정한 자료형, 비밀/원문 비노출을 검증한다.
- 실제 진단을 실행했다면 각 요청의 완료/실패/미시작을 구분하고, 누락 원인으로 확정할 수 있는 경계와 남은 불확실성을 기록한다.
- 원인을 확인한 후에만 다음 수정안을 선택한다. 모델 교체, 점수 완화, 미평가를 정답으로 간주하는 처리는 이 진단의 완료 조건이 아니다.

## 사용자 목표와의 관계

이번 작업은 누락 보완을 위한 관측 근거다. 새 기획서 10개 일반화, 사람 검토 gold, 수정량 10% 이하, 실제 Spring 저장과 운영 검증은 별도 미완료 기준으로 유지한다.
