# AgentFit 아이디어 검증 보고서

> 이 문서의 Claude Code 사례와 공식 자료 검토는 당시의 조사 기록이다. 2026-09-25 초기 설정 대상이 Codex로 변경됐으므로, Codex의 설정·권한·도구 조합에 관한 대응 근거는 후속 검증에서 새로 확인한다. 문서 분석 모델은 Solar Pro 4를 1차 평가한다.

검토 기준일: 2026-09-07  
검토 대상: 팀 공통 PRD, 첫 문서 분석 Spec·Plan·Research, 원래 AgentFit 기획  
방법: 제품·UX·엔지니어링 관점의 가정 검토, 공식 문서 대조, 논리적 반례 구성

**판정: 해결하려는 문제는 이해되지만, 현재 문서만으로 제품 가치와 실제 환경 구성의 안전성·완료 가능성이 검증되지는 않았다. 핵심 가정을 먼저 확인하는 조건부 진행이 타당하다.**

1–7절은 보완 전 검토 기록이다. 최초 검토에서는 PRD·Constitution·Spec·역할별 Agent.md를 수정하지 않았다.
이후 사용자의 보완 요청에 따라 PRD·역할 지침·첫 Feature 문서에 설계 보완을 반영했다. 항목별 반영 범위와 남은 검증은 8절과 [검증 실행 계획](validation-plan.md)을 참고한다. Constitution은 유지했다.

## 1. 이번에 확인한 것과 아직 확인하지 못한 것

### 수행한 검토

- PRD의 제품 약속·입력·출력·MVP 범위·권한·성공 지표를 대조했다.
- 첫 Feature의 근거 검증·보관·실행 경계에 대한 계획을 읽었다.
- Claude Code 공식 문서에서 Plugin, MCP, 설정 우선순위, 권한과 Hook 실행의 실제 의미를 확인했다.
- MDN의 브라우저 폴더 접근 조건과 MCP 공식 자료의 Tool annotation 한계를 확인했다.
- 동일 입력·다른 로컬 환경, 부정문·후보 기술, 설치 전후 상태 등 논리적 반례를 구성했다.

### 이번 검토에서 수행하지 않은 것

- 실제 고객 인터뷰·지불 의사·사용성 실험.
- AgentFit의 실행·설치·부하·AI 정확도·권한 차단 실측.
- 실제 사용자 프로젝트나 Credential을 사용한 도구 연결.
- Catalog 도구 전체의 코드·공급망·조합 안전성 검증.

따라서 '수요가 없다', '절대로 구현할 수 없다', '안전성이 검증됐다'는 결론을 내리지 않는다.
아래에서 **확인된 사실**, **문서상 공백**, **논리적 반례**, **사용자 실험이 필요한 가설**을 구분한다.

## 2. 이미 잘 정한 원칙

다음은 허점으로 다시 지적할 사항이 아니라 유지해야 할 제약이다.

- AI 초안과 사용자 확인 Profile을 구분하고 미정을 허용한다.
- Catalog 밖 도구·미확인 호환성을 확정 추천하지 않는다.
- Secret 격리, Preview·최종 승인, 소유권 검사를 요구한다.
- Config 생성과 실제 검증을 구분한다.
- 원문 미보관의 관리 범위와 외부 서비스의 별도 보관을 구분한다.
- 한 Client 중심·Modular Monolith·단계별 MVP를 선택했다.
- PRD 14절에서 후속 정책이 아직 미정임을 명시했다.

다만 원칙을 문서에 적었다는 사실과 실제로 지킬 수 있는 구조·사용자 가치가 입증됐다는 것은 별개다.

## 3. 우선 해결할 허점

### F01. 기존 도구보다 나은 이유가 아직 측정되지 않았다

**구분:** 가치·전략 가설 미검증 / 우선순위 높음  
**관련:** PRD 2절, PRD-17–21, 9절

Claude Code에는 이미 Plugin 탐색·설치·구성 확인 기능이 있으며, 특정 관리 설정 아래에서는 현재 디렉터리와 관련된 제안도 표시한다. 단순한 추천 목록과 설치 안내는 기존 기능과 겹친다. [공식 Plugin 탐색 문서](https://code.claude.com/docs/en/discover-plugins)

여기서 AgentFit의 추가 가치가 없다고 결론 내릴 수는 없다. 문제는 **기획서·역할을 사용한 추천이 공식 탐색이나 일반 AI의 설정 도움보다 얼마나 좋은지 비교 기준이 없다는 점**이다.
초보자가 어려워하는 일이 도구 탐색인지, API Key 발급인지, 설치 오류 해결인지도 사용자 자료로 확인되지 않았다.

- **반례:** 사용자의 기존 AI Client 기능만으로 업무가 가능한데 문서에 기술명이 많다는 이유로 여러 확장을 추천한다.
- **영향:** 화면과 추천 설명은 완성돼도 사용자의 설정 시간·오류·업무 완료는 개선되지 않을 수 있다.
- **보완 제안:** 추천하지 않는 것이 적절한 경우와 기존 기능으로 충분한 경우를 품질 평가에 포함한다. '호환 도구 없음'과 '추가 도구가 필요 없음'을 구분한다.
- **검증:** E1에서 같은 과제의 완료율·시간·오류·지원 횟수를 기존 방법과 비교한다. 비교 결과 없이 차별화가 검증됐다고 표현하지 않는다.

### F02. '기획서와 역할만'으로는 실제 설정에 필요한 정보가 부족하다

**구분:** 논리적 정보 부족 / 우선순위 높음  
**관련:** PRD 한 줄 설명, PRD-16·19·24–26, 14절

PRD 본문은 OS·Client·기술 스택을 추가로 입력받으므로 문자 그대로 두 입력만 받는 구조는 아니다.
더 큰 문제는 같은 기획서·역할·OS·Client라도 실제 저장소의 버전·테스트 명령·기존 설정·조직 정책이 다를 수 있다는 것이다.

- **반례:** 같은 기획서와 환경 설명을 가진 프로젝트 A에는 설정이 없고 B에는 팀 정책과 기존 MCP 연결이 있다. 현재 입력만으로 두 환경을 구분할 수 없다.
- **영향:** 프로젝트 맞춤 Skill이 실제 Route·테스트 명령·Convention과 어긋날 수 있고, 기존 파일의 정확한 CREATE/UPDATE·Diff도 판단할 수 없다.
- **공식 사실:** Claude Code의 유효 설정은 조직·명령줄·프로젝트 로컬·프로젝트 공통·사용자 설정을 함께 반영하며 일부 목록은 합쳐진다. 파일 하나를 생성했다고 전체 유효 설정이 결정되는 것은 아니다. [설정 우선순위](https://code.claude.com/docs/en/settings)
- **보완 제안:** '기획서 기반 제안'과 '현재 환경 확인 후 구성'의 결과 수준을 구분한다. 신규 설정용 초안인지 기존 파일을 확인한 변경안인지 표시하고, 기존 내용을 모르면 확정 Diff·충돌 검사 완료를 주장하지 않는다.
- **검증:** E2에서 동일 입력과 서로 다른 로컬 상태를 놓고 어떤 추가 정보가 필요한지 결정한다.

브라우저 폴더 읽기를 선택 기능으로 둔 채 기존 설정을 항상 정확히 병합한다고 약속할 수는 없다.
폴더 접근은 지원 브라우저·보안 컨텍스트·사용자 동작의 제약도 받는다. [MDN 폴더 선택 API](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)
필요하다면 사용자가 선택한 설정 파일 입력·수동 확인 등의 대안을 명세화할 수 있지만, 이번 검토에서 추가 기능을 확정하지 않는다.

### F03. Permission Manager가 무엇을 실제로 통제하는지 아직 부족하다

**구분:** 실행 경계·정책 변환 설계 공백 / 우선순위 매우 높음  
**관련:** PRD-22·23, 8.2절

PRD는 다운로드 이후의 외부 실행을 통제한다고 표시하지 말라고 이미 정했다. 이 원칙은 맞다.
그러나 동시에 작업별 ALLOW/ASK/DENY 실행 제어를 요구하므로 **어떤 작업이 AgentFit을 실제로 통과하는지**를 확정해야 한다.

구분해야 할 세 가지는 다음과 같다.

| 통제 대상 | 가능한 책임 |
| --- | --- |
| AgentFit의 자체 저장·분석·설정 생성 | 서비스 서버가 요청·소유권·승인을 검사 |
| 내려받을 Client 설정 | 지원 형식으로 정책을 표현하고 변환의 정확성을 확인 |
| 다운로드 이후 Client·Hook·MCP의 실행 | 실제 실행 환경의 정책·권한·인증·격리에 의해 결정 |

웹에서 'GitHub 읽기 허용'을 선택했다는 사실만으로 모든 실행 경로의 쓰기가 차단되지는 않는다.
서비스의 의미적 권한과 Client의 Tool·명령·경로 규칙, 외부 인증 Scope를 연결해야 한다. Claude Code도 자체 규칙과 모드로 권한을 판단한다. [Claude Code 권한 문서](https://code.claude.com/docs/en/permissions)

- **보완 제안:** 각 권한마다 지원 여부, 생성할 실제 규칙, 검사 가능한 범위, 기존 설정과의 상호작용을 표로 정의한다. 표현할 수 없는 정책을 '적용 완료'로 표시하지 않는다.
- **검증:** E3에서 실제 지원 환경의 Allow·Ask·Deny와 설정 우선순위를 확인한다.
- **판정:** Permission UI만 만들거나 LLM이 정책 문구를 생성하는 것으로 완료할 수 없는 핵심 기능이다.

### F04. Hook과 Plugin을 일반 설정 파일처럼 다루면 보안·중복 문제가 생긴다

**구분:** 공식 동작으로 확인되는 설계 위험 / 우선순위 매우 높음  
**관련:** PRD 3절, PRD-18·22–26

명령형 Hook은 사용자 계정의 권한으로 명령을 실행한다. 설정을 생성하는 단계에서 실행하지 않았어도 적용 이후 자동 실행이 생긴다.
또한 여러 Hook이 함께 실행될 수 있고 Plugin·Skill에 포함된 복사본은 별도로 남을 수 있다. 따라서 'MVP에서 Shell 자동 실행이 필수가 아니다'라는 문장으로 Hook의 실행 위험이 사라지지 않는다. [Hook 공식 문서](https://code.claude.com/docs/en/hooks)

Plugin은 Skill·Hook·MCP 등을 묶는 배포 단위다. 따라서 MCP / Skill / Hook / Plugin을 서로 독립된 선택지로만 모델링하면 구성 중복을 놓칠 수 있다. [Plugin 구조](https://code.claude.com/docs/en/plugins)

- **반례:** 테스트 Hook을 포함한 Plugin과 같은 역할의 독립 Hook을 함께 선택한다. 두 항목이 개별적으로 정상이어도 중복 실행·부작용이 생길 수 있다.
- **보완 제안:** Catalog에 포함 구성요소·의존성·중복·충돌 정보를 둔다. 실행 가능한 항목은 검토한 템플릿·버전·명령과 검증 범위를 명시한다.
- **검증:** E4에서 개별 항목과 대표 조합을 별도로 평가한다. 같은 이름만 제거하는 방식으로 해결됐다고 보지 않는다.
- **판정:** 도구 15~20개를 검증했다는 수량만으로 조합까지 안전하다고 말할 수 없다.

### F05. 다운로드 완료와 사용자가 원하는 '환경 준비 완료' 사이에 공백이 있다

**구분:** 제품 가치 전달 가설 / 우선순위 높음  
**관련:** PRD 2.2절, PRD-27·28, 9.2절

생성과 검증을 구분한 상태 모델은 정직하다. 하지만 사용자가 원한 일이 환경 준비라면 '검증 미수행'을 정확히 표시하는 것만으로 그 일이 끝나지는 않는다.
실제 MCP 연결에는 인증·런타임·환경 변수 등이 필요할 수 있다. 공식 문서도 설정 등록과 인증·연결 확인을 구분한다. [MCP 연결·인증 문서](https://code.claude.com/docs/en/mcp)

- **반례:** 파일 다운로드는 성공했지만 사용자에게 필요한 인증이나 실행 파일이 없어서 도구를 사용할 수 없다.
- **영향:** 제품의 내부 완료율은 높고 실제 사용자의 완료율은 낮을 수 있다.
- **보완 제안:** 제품이 보장할 종료점을 정확히 정한다. 최소한 지원하는 사례에서 사용자가 설정 안내를 따라 실제로 사용할 수 있는지 관찰한다. 이를 확인하기 위해 Local CLI를 곧바로 추가할 필요는 없다.
- **검증:** E1에서 다운로드 이후 단계까지 관찰하고 각 실패를 설치·인증·설정·호환성으로 분류한다.
- **판정:** 상태 명칭의 정확성과 사용자 문제 해결 여부는 별도 평가가 필요하다.

### F06. 원문 인용이 있다고 문서의 의미를 정확히 이해한 것은 아니다

**구분:** 논리적 반례 / 우선순위 높음  
**관련:** PRD-09·10, SC-002·003, 첫 Feature Research R4

기존 Research도 의미적 정확도는 별도 평가가 필요하다고 적었다. 원문에 값·인용문이 존재한다는 검사는 필요한 검사지만 충분한 검사가 아니다.

- **반례 1:** 'PostgreSQL은 사용하지 않는다.'에서 PostgreSQL 문자열은 존재하지만 DB 확정값으로 넣으면 틀린다.
- **반례 2:** '현재는 SQLite, PostgreSQL 전환은 검토 중'에서 현재값과 후보를 구분해야 한다.
- **반례 3:** '경쟁 서비스는 Firebase를 사용한다'는 본 프로젝트 기술 선택의 근거가 아니다.
- **반례 4:** 일부 페이지의 변경안이 앞의 기획을 폐기했거나, 표·주석이 선택을 제한할 수 있다.

추가로 검증 후 원문을 삭제하면 나중에 위치 정보만으로 해석 오류를 다시 확인하기 어렵다.
이는 원문 미보관을 폐기해야 한다는 의미가 아니라, 사용자에게 근거를 언제 어떻게 확인시키고 재입력을 안내할지 정해야 한다는 뜻이다.

- **보완 제안:** 부정·후보·현재/미래·다른 대상·상충 정보가 포함된 독립 정답 평가를 추가한다. 저장한 위치 정보와 실제 원문 재열람 가능 여부를 구분한다.
- **검증:** E5의 의미 반례와 읽기 실패 사례로 확인한다. 아직 실제 모델에 입력해 결과를 측정하지 않았다.
- **판정:** 구조화 출력 정확도·근거 문자열 일치·의미 정확도를 별도 지표로 봐야 한다.

### F07. 성공 지표가 핵심 가치보다 첫 문서 분석에 치우쳐 있다

**구분:** 측정 설계 공백 / 우선순위 높음  
**관련:** PRD 9절, SC-003·008

문서 9개·정확도 90%는 첫 기능을 검증하는 출발점이다. 그것만으로 역할별 추천 품질, 기존 방법보다 나은 설정, 실제 사용 완료를 증명하지는 않는다.

SC-008은 60초 내 '결과 또는 명시적 실패'를 요구한다.
따라서 이 지표만 떼어 보면 실패를 빨리 반환하는 구현도 통과할 수 있다. 다른 성공 기준이 있으므로 전체 Feature가 자동 통과한다는 뜻은 아니지만, **처리 시간과 정상 입력의 성공률을 함께 보지 않으면 지표 해석이 왜곡된다.**

- **보완 제안:** 정상 입력 분석 성공률·정확도·지연, 적절한 추천 여부, 설정 적용·사용 가능 여부를 분리한다. 실패 응답 시간을 성공 분석 시간으로 합쳐 설명하지 않는다.
- **검증:** E1·E5에서 원래 명세 지표를 유지하면서 사용자 결과도 관찰한다. 새 수치 목표는 결과를 보기 전에 팀이 정한다.
- **판정:** 기존 목표를 낮출 필요는 없지만 '이 지표를 달성하면 아이디어가 검증된다'고 해석하면 안 된다.

### F08. 초보자에게 질문·승인·인증이 오히려 부담이 될 수 있다

**구분:** 사용성·접근 경로 가설 / 우선순위 높음  
**관련:** PRD 2.3·4·7절

로그인 → 프로젝트 생성 → 기획서 → 분석 확인 → 역할·환경 → 추천 → 권한 → Preview → 다운로드 → 외부 인증은 사용자가 해야 할 판단이 많다.
각 단계가 합리적이어도 전체 부담이 기존 방법보다 줄어드는지는 별도다.
개발 초보자 전체와 Claude Code·GitHub를 이미 사용하는 초보자가 같은 집단인지도 확인되지 않았다. Designer 역할의 실제 업무·Client 적합성도 일괄 가정하지 않는다.

- **보완 제안:** 진행자 개입이 필요했던 질문과 단계를 기록하고, 서비스 사용자가 이해할 수 있는 결과·동작 중심으로 설명한다. 필수 보안 승인을 숨겨서 이탈을 줄이는 방식은 사용하지 않는다.
- **검증:** E1·E6에서 실제 과거 설정 경험, 준비된 계정·문서, 단계별 이탈·오해를 확인한다.
- **판정:** '초보자용'은 기능 설명의 표현보다 전체 수행 결과로 검증해야 한다.

### F09. 검증 Catalog와 원문 미보관에는 계속 드는 운영 비용이 있다

**구분:** 실현·운영 지속 가능성 가설 / 우선순위 중간~높음  
**관련:** PRD-18·30·32, 8·12·14절

Catalog 검증은 한 번의 등록 작업이 아니다. Client·도구·OS·인증 조건·구성 조합이 바뀌면 확인 범위도 바뀐다.
예를 들어 15개 도구 × OS 2개 × Client 버전 2개만 가정해도 60개 단일 도구 환경 조합이다. 이는 설명용 계산이며 현재 지원 범위나 실제 공수 추정이 아니다.

MCP의 도구 annotation은 행동을 보장하는 집행 장치가 아니며 신뢰되지 않은 출처의 힌트를 그대로 권한 근거로 삼으면 안 된다. [MCP 공식 설명](https://blog.modelcontextprotocol.io/posts/2026-03-16-tool-annotations/)

원문 미보관·Secret 격리는 좋은 원칙이다. 기존 Plan도 모든 문자열의 Secret 판별이나 물리적 RAM 즉시 삭제를 보장하지 않는다고 한정했다.
남은 문제는 검증 실패 재현·지원, 운영 로그·임시 저장·비정상 종료 검사와 재검증을 누가 계속 담당할지다.

- **보완 제안:** 검증한 버전·환경·검사 종류·실패 상태·재검증 책임을 기록한다. 지원에 필요한 합성 재현 정보와 개인정보 최소화 방식을 합의한다.
- **검증:** E4·E7에서 실제 재검증·지원에 필요한 시간을 재본다.
- **판정:** 산학 프로젝트에 당장 결제 모델이 필수인 것은 아니다. 다만 API 비용·재검증·지원 시간을 감당할 수 있는지는 확인해야 한다.

### F10. 첫 기능 완성을 기다리면 핵심 가설 검증이 너무 늦을 수 있다

**구분:** 팀·실행 순서 위험 / 우선순위 중간~높음  
**관련:** PRD 10·11절, 역할별 작업 순서

첫 사용자 흐름부터 구현하는 순서는 의존성과 통합을 관리하는 데 유용하다.
그러나 인증·삭제·보관·동시성·실제 AI 평가까지 마친 뒤에야 '추천이 유용한가'와 '설정이 실제로 적용 가능한가'를 처음 확인하면 큰 변경을 늦게 발견할 수 있다.
공통 DB·서버 통합이 A, 추출·Profile·추천 평가가 AI에 집중된 점도 실제 가용 시간으로 확인해야 한다.

- **보완 제안:** 구현 순서는 유지하되 수요 인터뷰·공식 문서 조사·계약 검토·수동 결과 검토를 병행한다. 코드나 설치가 필요한 검증은 별도 범위를 제시하고 사용자 승인을 받은 뒤 수행한다.
- **검증:** E7에서 담당·선행 조건·통합·검증 담당을 실제 팀 일정과 대조한다.
- **판정:** 아직 공수 자료가 없으므로 한 학기에 불가능하다고 단정할 수 없다. 핵심 가설을 나중으로 미루는 것은 피할 수 있다.

## 4. 8개 위험 범주별 가정

'신뢰도'는 **가정이 참이라는 현재 근거의 강도**다. 실패 확률이나 통계적 점수가 아니다.
낮음은 실사용 자료 부족, 중간은 일부 설계·공식 기능 근거가 있으나 실제 결과가 없는 상태를 뜻한다.

| 범주 | 성공하려면 참이어야 하는 가정 | 현재 신뢰도 | 실패 영향 | 검증 |
| --- | --- | --- | --- | --- |
| Value — 가치 | 기획서·역할을 활용하면 기존 방법보다 적절한 설정을 더 쉽게 완성한다. | 낮음 | 높음 | E1 비교 관찰 |
| Usability — 사용성 | 초보자가 추가 질문·권한·인증을 이해하고 도움 없이 끝까지 진행한다. | 낮음 | 높음 | E1·E6 단계별 관찰 |
| Viability — 운영 지속성 | 한 학기 가용 인력·예산으로 AI·도구 검증·지원 비용을 감당한다. | 낮음 | 중간~높음 | E4·E7 실제 공수 기록 |
| Feasibility — 구현 가능성 | 지원 환경의 기존 상태를 확인하고 유효한 설정·권한으로 변환할 수 있다. | 중간 | 높음 | E2·E3·E4 |
| Ethics — 신뢰·피해 방지 | 검증·보관·권한 설명이 실제 보호 범위와 일치하고 사용자 판단을 오도하지 않는다. | 중간 | 높음 | E3·E4·E6 |
| Go-to-Market — 사용자 확보 | 대상자가 실제로 쓸 계정·문서를 갖고 있으며 외부 서비스에 필요한 내용을 제공할 의향이 있다. | 낮음 | 중간~높음 | E6 실제 행동 인터뷰 |
| Strategy & Objectives — 전략·목표 | Client 내장 기능이 있어도 AgentFit이 제공하는 추가 가치가 남고 평가 목표와 일치한다. | 낮음 | 높음 | E1, 학교·팀의 성공 기준 확인 |
| Team — 팀 실행 | 다섯 역할이 공통 계약·통합·검증 책임을 유지하고 핵심 담당 병목을 감당한다. | 낮음 | 중간~높음 | E7 담당·가용 시간 대조 |

PM 관점에서는 기존 대안 대비 가치와 목표를, Designer 관점에서는 전체 부담·상태 이해·정보 제공 의향을, Engineer 관점에서는 입력 정보·실행 경계·조합·운영 가능성을 중점 검토했다.

## 5. 실행할 검증안

**아래 실험은 아직 실행하지 않았다. 수치·표본은 작은 탐색 실험을 위한 제안이며 기존 PRD의 완료 기준을 변경하지 않는다.**
참가자에게 연락하거나 모집·설치·구현을 수행하지 않았다.

### E1. 기존 방법과 AgentFit 접근의 비교

- **대상 제안:** 실제로 AI 개발 도구를 사용하려는 초보자 5–8명.
- **방법:** 난이도가 비슷한 설정 과제를 사용하고 순서를 교차해 일반 AI·공식 탐색 방식과 기획서·역할 기반 제안 방식을 비교한다.
- **주의:** 수동으로 제안을 제공하면 Concierge 실험으로 표시한다. 이를 구현된 AgentFit 성능으로 보고하지 않는다.
- **관찰:** 시작부터 실제 사용 가능 상태까지의 완료 여부·시간·오류·지원 횟수, 불필요하게 추가된 도구, 다운로드 이후 막힌 단계.
- **판정 제안:** 완료율·안전성이 나빠지지 않으면서 시간 또는 지원 부담의 일관된 개선이 보여야 추가 가치를 주장한다. 수치 기준은 실험 전에 정한다.
- **연결:** F01·F05·F07·F08.

### E2. 동일 입력·다른 환경 반례 검토

- **사례:** 같은 기획서·역할·OS·Client 설명에 대해 신규 설정, 기존 설정 존재, 조직 정책 존재의 세 환경을 비교한다.
- **관찰:** 필요한 산출물이 달라지는 이유, 현재 입력으로 알 수 없는 정보, 추가 확인 방법.
- **합격 조건 제안:** 확인하지 않은 기존 파일·정책을 안다고 가정하지 않고 필요한 입력이나 적용 한계를 명확히 표시한다.
- **상태:** 정보 부족의 논리적 반례는 본 보고서에 구성했다. 실제 Client에서의 재현은 미실행이다.
- **연결:** F02·F03.

### E3. 권한 변환·실행 경계 검증

- **준비:** 대표 권한에 대해 의미·대상·Client 규칙·외부 인증·검증 방법의 대응표를 만든다.
- **환경:** 격리된 합성 프로젝트에서 Allow·Ask·Deny, 기존 상위 정책, 선택 변경·승인 취소, Hook 관련 동작을 확인한다.
- **관찰:** UI의 약속과 실제 동작의 일치, 표현 불가능한 권한의 처리.
- **합격 조건 제안:** 승인 범위 밖 실행·허위 적용 완료는 허용하지 않는다. 지원 불가·미확인 상태를 명시한다.
- **실행 조건:** 코드·설치·실행이 필요하므로 범위를 구체화해 구현 전 승인을 받는다.
- **연결:** F03·F04.

### E4. Catalog 항목과 조합의 검증

- **대상 제안:** 대표적인 소수 항목으로 먼저 절차를 점검한 뒤 승인된 Catalog 범위로 확장한다. MVP Catalog 수를 변경하는 제안은 아니다.
- **기록:** 출처·고정 버전·지원 환경·포함 구성요소·의존성·인증·검증 종류·시간.
- **사례:** 단독 구성, Plugin과 포함 기능의 중복, 기존 설정과 충돌, 도구 버전 변경.
- **판정 제안:** 실제 확인한 범위가 사용자에게 보이는 검증 표시와 일치해야 한다.
- **연결:** F04·F09.

### E5. 의미 정확도와 성공률·지연의 분리 평가

- **사례:** 부정문, 후보와 확정, 현재와 미래, 비교 대상의 기술, 상충 정보, 텍스트가 없는/부분 추출된 PDF.
- **방법:** 정답을 먼저 정의하고 구조 유효성·근거 존재·의미 정확도·분석 성공률·성공 지연·실패 지연을 따로 기록한다.
- **관찰:** 원문 삭제 이후의 설명·재입력 UX와 지원 한도 경계의 실제 동작.
- **판정 제안:** 원래 SC 목표를 유지하며 '인용문이 있으므로 정확하다', '실패라도 빠르므로 분석 성능이 좋다'는 결론을 방지한다.
- **연결:** F06·F07·F09.

### E6. 문제·준비 상태·정보 제공 의향 인터뷰

- **질문:** 최근 AI 개발환경을 설정한 실제 과정, 가장 막힌 단계, 사용한 대안, 가진 계정·문서, 누구의 도움을 받았는지.
- **방법:** 아이디어가 좋은지 묻기보다 과거 행동과 실제 자료의 존재를 확인한다. 민감한 원문·Secret 제출은 요구하지 않는다.
- **관찰:** 기획서가 있는 시작 시점과 도구를 고르는 시점의 일치, 역할별 차이, 로그인·업로드·권한에서의 부담.
- **판정:** 반복된 문제와 접근 가능한 초기 사용자가 있는지 판단한다. 만족도 답변만으로 수요·지불 의사를 확정하지 않는다.
- **연결:** F01·F08·F09.

### E7. 팀·운영 공수 검토

- **방법:** 첫 기능 필수 검증, 후속 권한·설정 검증, Catalog 재검증·지원 작업을 담당자·선행 조건·가용 시간에 대응시킨다.
- **관찰:** 특정 담당자에게 몰린 공통 계약·통합 작업과 운영 점검, 실제 재검증 소요 시간.
- **판정:** 가용 시간을 넘으면 해당 범위·순서를 팀이 재합의한다. 추정치를 실측 공수로 표시하지 않는다.
- **연결:** F09·F10.

## 6. 구현 범위를 확정하기 전에 필요한 결정

1. **제품 종료점:** 설정 다운로드를 제공하는 MVP인지, 어떤 지원 사례에서 실제 사용 가능 상태까지 확인할지 명확히 한다.
2. **입력과 결과 수준:** 기획서 기반 제안과 실제 환경을 확인한 설정·Diff를 구분한다.
3. **권한 책임:** AgentFit 자체 작업·생성하는 정책·외부 실행의 통제 범위를 분리하고 지원 가능한 권한만 약속한다.
4. **Catalog 구조:** Plugin 포함관계·의존성·중복·대표 조합과 검증 표시 기준을 정한다.
5. **가치와 평가:** 일반 AI·공식 탐색 대비 무엇을 개선할지, 불필요한 도구를 추천하지 않는 기준과 사용자 결과 지표를 정한다.
6. **검증 순서:** 첫 Feature 구현 순서는 유지하면서 수요·실행 경계·조합의 핵심 가정을 조기에 조사·검토한다.

이 결정은 원래 아이디어를 다른 사업으로 바꾸자는 제안이 아니다.
현재 기획의 '프로젝트와 사람에 맞는 환경을 안전하게 구성한다'는 약속을 검증 가능한 범위로 구체화하기 위한 것이다.

실제 검증에서 목표를 충족하지 못하면 해당 원인·범위를 수정하고 다시 평가하며, 결과에 맞춰 사전 정답이나 기준을 사후 낮추지 않는다.
