# AgentFit 검증 실행 계획

이 문서는 보완된 PRD를 실제로 검증하기 위한 준비·실행·판정 기준이다.
**현재 모든 실행 결과는 미수행이다.** 표본·목표는 결과를 보기 전에 정한 설계 기준이며 달성 실적이 아니다.
애플리케이션 코드·테스트 코드 작성, 패키지 설치와 실행 환경 변경은 해당 범위의 구현 승인을 받은 뒤 시작한다.

## 1. 검증 순서와 책임

| 검증 | 준비·실행 책임 | 첫 Feature와의 관계 | 실행 결과 |
| --- | --- | --- | --- |
| V1 사용자 문제·진입 조건 | Designer 주관, Frontend·AI 참여 | 인터뷰 설계·과거 행동 확인은 병행 가능 | 미수행 |
| V2 환경 정보와 Preview 범위 | B 주관, A·Frontend 참여 | 문서·수동 반례 검토는 병행 가능 | 미수행 |
| V3 권한 변환·실행 경계 | B 주관, A 검토 | 실제 실행은 승인된 별도 검증 범위 또는 후속 Feature에서 수행 | 미수행 |
| V4 Catalog·Plugin·Hook 조합 | B 주관, AI·A 검토 | 공식 자료·지원표 준비는 병행, 설치·실행은 승인 후 | 미수행 |
| V5 문서 의미·성공률·지연 | AI 주관, A·Frontend 연결 | 첫 Feature의 SC-003·008·011·012 및 T016·018·021·025·037·043 | 미수행 |
| V6 설정 적용과 기존 방법 비교 | Designer 주관, 전원 지원 | 추천·설정 흐름 준비 후 실제 제품 평가. 사전 수동 실험은 별도 표시 | 미수행 |
| V7 팀 가용 시간·운영 보관·지원 | A 주관, B 재검증, 각 담당 공수 기록 | 준비는 병행, 운영 검증은 실제 대상에서 수행 | 미수행 |

기능 구현 순서와 가정 확인 순서를 구분한다. 다음 기능을 먼저 구현하지 않아도 인터뷰·문서·계약 반례로 핵심 가정을 확인할 수 있다.
실험 참가자 모집·외부 메시지 발송은 별도 요청·승인에 따라 담당자가 수행한다.

## 2. 공통 기록과 판정 규칙

모든 결과에는 사례 ID·기대값·실행 시점·실제 버전·확인 주체·결과·실패 분류를 남긴다.
정답·지원 조건·시간 제한·판정 기준은 실행 전에 고정하고 변경하면 이유와 새 실행 묶음을 기록한다.
Mock·수동 제안·팀 검증 환경·실제 사용자 환경을 구분한다.

공유 자료에는 합성 문서와 안전한 오류 코드·최소 결과만 사용한다.
사용자 기획서 원문·기존 설정 원문·Credential·전체 모델 응답·민감한 콘솔 로그를 결과 문서에 붙이지 않는다.
사용자 프로젝트에 연결된 최소 기록은 프로젝트 삭제 시 제거하며, 별도 사용자 조사 기록은 개인식별 정보를 최소화하고 수집·보관 범위를 참여 전에 설명한다.
프로젝트 감사 기록을 외부 분석 서비스로 무단 전송하지 않는다.

판정은 '통과 / 실패 / 미수행 / 준비 불가'로 구분한다.
준비 불가를 통과로 계산하지 않는다. 기능 적합성, 안전성, 사용자 가치, 운영 지속성의 결과를 따로 보고한다.

## 3. V1 — 실제 문제와 진입 조건

- 개발 초보자 5명 이상을 초기 탐색 대상으로 삼는다. 모집 단계에서 사용하는 Client·계정 준비·역할·최근 설정 경험을 기록한다.
- 최근 프로젝트에서 어떤 설정을 했고 어디서 막혔는지, 어떤 대안과 도움을 썼는지 확인한다.
- 기획서가 있는 시점과 도구를 선택하는 시점이 일치하는지 확인한다.
- 실제 업무와 준비 조건으로 후속 과제 대상을 선정한다. 특정 역할·Client를 사용하는지 추정하지 않는다.
- 민감한 기획서 업로드를 요구하지 않고 합성 자료로 흐름을 설명한다.
- '이 아이디어가 좋은가'라는 만족도만으로 수요를 판단하지 않는다.

산출물: 익명화한 문제·기존 대안·진입 조건·중단 이유 목록.
유료화 의사는 산학 MVP의 필수 통과 조건이 아니다.

## 4. V2 — 같은 기획, 다른 기존 환경

동일한 Project·Developer 입력으로 다음 조건을 비교한다.

| 사례 | 실제 조건 | 기대 결과 |
| --- | --- | --- |
| ENV-01 | 기존 파일 확인 안 됨 | 기획 기반 제안·기존 상태 미확인. 정확한 병합·Diff 완료 표시 금지 |
| ENV-02 | 사용자가 신규 환경이라고 응답 | 사용자 확인 출처 표시. 시스템 직접 검사로 표시하지 않음 |
| ENV-03 | 필요한 기존 설정 입력 확인 | 제공된 범위에서 변경·충돌 판정 |
| ENV-04 | 상위 조직·사용자 정책 미제공 | 그 정책의 유효 권한은 미확인으로 표시 |
| ENV-05 | Preview 후 기존 파일 또는 선택 변경 | 이전 승인 무효화·재확인 |
| ENV-06 | 기존 구성으로 Capability 충족 | 추가 도구 불필요 |
| ENV-07 | 중요 환경 정보 부족 | 필요한 질문만 제시 |
| ENV-08 | 정보는 충분하나 검증 후보 없음 | 호환 후보 없음 |

입력만으로 구분할 수 없는 두 환경을 같은 확신으로 처리하면 실패다.
기존 설정 입력에 Secret이 있으면 정제·차단 경계가 작동해야 하며 원문은 처리 후 서버에 남기지 않는다.
선택적 브라우저 폴더 기능은 지원 브라우저·사용자 동작·접근 거절도 별도 확인한다.

## 5. V3 — 권한 대응과 실제 동작

권한별로 다음 대응표를 채운다.

| 필드 | 기록할 내용 |
| --- | --- |
| 의미 | 대상 리소스·작업·범위 |
| 서비스 내부 검사 | 어느 요청에서 소유권·승인·정책을 확인하는지 |
| Client 변환 | 실제 생성 규칙과 지원 OS·Client·도구 버전 |
| 외부 인증 | 필요한 최소 인증 범위, 로그인용 권한과의 구분 |
| 확인 한계 | 미제공 상위 설정·다른 실행 경로·외부 환경 |
| 테스트 | Allow·Ask·Deny와 정상·차단·취소·변경 사례 |
| 판정 | 지원·미지원·미검증, 확인 주체·시점 |

격리된 합성 환경에서 기본 Ask, 명시적 Allow, Deny, 상위 정책, 선택 해제, 승인 이후 변경, 인증 부족과 미지원 정책을 확인한다.
외부 연결·변경·실행 가능한 구성은 선택 전 비활성이고, 검증하지 않은 범위의 ALWAYS_ALLOW를 제공하지 않는다.
반드시 서비스 요청과 생성된 정책의 검사, Client 실제 동작을 구분한다.
표현할 수 없는 정책을 '권한 적용 완료'로 표시하거나 승인 밖 작업을 허용하면 실패다.

## 6. V4 — Catalog와 조합

Catalog 항목마다 다음을 기록한다.

- 배포 단위 ID·포함 구성요소 ID·기능·의존성·중복·충돌.
- 공식 출처·고정 버전 또는 commit/내용 식별자.
- OS·Client·런타임 버전, 인증·권한·실행 명령의 실제 범위.
- 문서 확인·형식 검사·단독 동작·조합 동작의 결과와 검증 시점·담당.
- 후속 변경으로 무효화되는 검사와 재검증 담당.

초기에는 대표 항목으로 절차를 확인하고 출시 활성화 대상 전체로 확장한다. Catalog 약 15~20개 목표를 대표 실험 수와 혼동하지 않는다.
Plugin과 포함 MCP·Skill·Hook을 별도 추천했을 때의 중복, 기존 설정과의 충돌, 의존성 누락, 버전 변경을 검사한다.
명령형 Hook은 검토한 고정 템플릿·허용 인자만 사용한다. 임의 명령·경로·Hook 코드가 문서나 LLM 출력에서 실행 구성으로 유입되면 실패다.
단독 성공으로 조합 성공을 추정하지 않는다. 검증에 실패하거나 버전이 달라진 조합은 확정 추천에서 비활성화한다.

검증 범위를 바꾸지 않는 문구 변경과 실행·의존성·권한 변경을 구분해 불필요한 전체 재실행을 피한다.
재검증에 걸린 시간을 기록하고 B가 지원표 상태, A가 실행 환경·공통 의존성 영향을 통합한다.

## 7. V5 — 문서 의미·성공률·지연

### 사전 데이터

| 묶음 | 최소 표본 | 목적 |
| --- | --- | --- |
| FACT | 정답 문서 9개, PDF·Markdown·텍스트 각각 3개 | 기존 SC-003의 명시된 사실 정확도 90% 이상 |
| SEM | 6범주 × 2사례 = 12개 | SC-011의 의미 정확도. 세 입력 유형을 모두 포함 |
| NORMAL | 독립 정상 문서 30개, 유형별 10개 | SC-012의 첫 요청 성공률, SC-008 지연 |
| ERROR | 기존 실패·한도·보안 사례 | 올바른 거부·복구·원문 미보관. 정상 성공률과 분리 |

SEM 범주: 부정, 후보와 확정, 현재와 미래, 다른 대상의 기술, 상충 정보, 문맥의 제한.
각 범주에는 확정값을 반환해야 하는 양성 대조와 미정·다른 값을 반환해야 하는 사례를 포함한다.
모든 값을 null로 반환해서 통과할 수 없도록 필수 대상 필드의 정답을 고정한다.
원문에 문자열이 있다는 사실만으로 사실 정확성을 인정하지 않는다.

NORMAL은 지원 정책을 만족하는 서로 다른 내용으로 구성하고 짧은 문서·중간 문서·한도에 가까운 문서를 포함한다.
정상 입력 여부, PDF의 읽을 수 있는 텍스트 범위, 필수 기대 사실과 형식·길이·페이지 분포를 실행 전에 고정한다.
FACT와 NORMAL은 기준을 충족하면 재사용할 수 있지만 각 지표는 독립 집계한다.

### 계산

- 정확도 = 올바르게 추출한 정답 사실 / 사전에 정의한 사실. 근거 없는 값·다른 대상·후보의 확정은 오답이다.
- 의미 반례 = SEM의 모든 필수 대상 필드값·미확정 구분이 정답과 일치해야 통과한다.
- 정상 첫 요청 성공 = 유효한 초안이 저장·표시되고 사전 필수 사실 검토를 통과한 요청이다. 오류·시간 초과·재시도 결과는 첫 요청 성공이 아니다.
- 성공률 = 정상 첫 요청 성공 수 / NORMAL 전체 요청 수. 목표 95% 이상이며 30개일 때 최소 29개 성공이 필요하다.
- 기존 60초 기준은 결과 또는 명시적 실패 안내의 시간을 측정한다. 동시에 성공 분석 지연과 실패 안내 지연을 따로 보고한다.
- 외부 장애로 선언한 실행은 별도 기록하되 유리한 요청만 골라 같은 실행 묶음의 분모를 다시 만들지 않는다. 정상 조건에서 전체 묶음을 새로 실행한다.

실제 Provider 평가 전에는 결과를 비워 둔다. 모델·Prompt·파서·정답이 바뀌면 영향을 받는 묶음을 다시 평가한다.
근거 위치는 원문을 다시 열 수 있다는 의미가 아니다. 처리 후 원문 재열람은 사용자가 가진 원본으로 하도록 안내하고 서버에 인용문을 계속 보관하지 않는다.

## 8. V6 — 설정 적용과 기존 방법 비교

### 준비

- 실제 AI Client를 사용할 준비가 된 개발 초보자 8명. 역할과 경험을 기록하고 대상 범위 이상의 일반화를 하지 않는다.
- 동등 난이도의 과제 두 개를 만들고 동일한 준비 조건·지원 문서·관찰 기준을 적용한다.
- 한 방법은 일반 AI·공식 탐색·설정 안내, 다른 방법은 AgentFit의 추천·다운로드·적용 안내다.
- 순서는 절반씩 교차한다. 한 과제에서 배운 답을 그대로 복사하는 과제를 피한다.
- 각 과제는 최대 40분 관찰하며 참가자·과제·종료 조건을 실행 전에 고정한다.
- 초기 수동 제안 실험은 Concierge로 표시하고 실제 AgentFit 기능 완료나 성능으로 보고하지 않는다.

### 종료 조건과 측정

참가자가 선택·권한·설정을 확인하고 지원 안내를 따라 적용·인증한 뒤, 미리 정의한 무해한 동작을 완료하면 성공이다.
Secret 조회·파괴적 변경·실제 메시지 발송은 성공 과제에 포함하지 않는다.
이미 적합한 구성인 사례는 불필요한 도구를 설치하지 않고 목표 동작을 수행하면 성공이다.

완료 여부·시작부터의 시간·설정 오류·중복/불필요한 도구·도움 요청·진행자 개입·권한 오해·다운로드 후 막힌 단계를 기록한다.
진행자 개입이 있어야 완료한 경우 독립 완료와 구분한다. 중도 포기·시간 초과 참가자를 결과에서 제외하지 않는다.

### 초기 진행 판단 기준

1. AgentFit 방식에서 최소 6/8명이 독립 완료한다.
2. 기존 방법보다 독립 완료율이 낮아지지 않는다.
3. 두 방법을 모두 독립 완료한 사례가 최소 6쌍이며, 참가자별 AgentFit 시간 / 기존 방법 시간의 중앙값이 0.8 이하이다.
4. 승인 없는 변경·안전하지 않은 권한 확대는 0건이다.
5. 모든 참가자의 실패·개입·시간 제한 결과와 불필요한 도구 추가를 함께 보고한다.

위 기준은 작은 탐색 실험의 방향 판단이다. 통계적 시장 효과나 모든 사용자에 대한 보장이 아니다.
기준 미달이면 원인별로 입력·추천·안내를 고치고 다시 검증한다. 결과를 본 뒤 같은 실험의 통과 기준을 낮추지 않는다.
제품 기능 충족과 비교 실험 결과를 따로 보고한다. 다운로드만 성공한 사람을 설정 사용 성공으로 집계하지 않는다.

## 9. V7 — 팀·운영·지원

각 담당자는 본인 작업, 공통 계약 검토, 통합, 테스트, 외부 준비와 재검증의 예상·실측 시간을 기록한다.
A는 인증·DB·분석 연결·배포, B는 Catalog·권한·템플릿·재검증, AI는 추출·의미 평가, Frontend·Designer는 UI·적용 안내·사용성에 대한 담당과 인계 조건을 확인한다.
특정 담당의 가용 시간을 넘으면 해당 Feature 범위를 팀에서 재합의한다.

운영 보관 검증은 실제 배포 대상의 요청 본문 로그·임시 저장·APM·swap·dump·중단 결과를 확인한다.
서버 관리 범위와 외부 Provider의 조건을 구분한다. 원문 미보관 때문에 재현에 필요한 경우 합성 사례나 사용자 재입력을 안내한다.
최소 이력의 재생성 정보가 기존 프로젝트 파일의 백업·복원을 보장한다고 설명하지 않는다.
API 비용·재검증 시간·지원 횟수를 기록하되 지불 의사를 추정하여 수익성을 확정하지 않는다.
