# AgentFit 파트 PRD — Designer — 사용자 흐름·설명·사용성

> 배포 기준: 2026-09-08 · 역할: Designer — 사용자 흐름·설명·사용성 · 대상: 담당 팀원과 협업 파트
>
> **개발 초보자가 필요한 구성과 권한·변경 내용을 이해하고 다음 행동을 선택하게 한다.**

이 문서는 이 파트가 제공할 제품 결과·기능·수용 기준을 정의한다. 작업 방식은 같은 역할의 Agent.md, 전체 제품 요구는 공통 PRD를 따른다.
아래 파트 ID는 책임 추적용이며 공통 PRD의 PRD-01–41 또는 첫 Feature의 FR·SC를 대체하지 않는다. 목표·예시는 실제 검증 결과가 아니다.

## 1. 제품 맥락과 공통 결정

AgentFit은 기획서·역할에서 출발해 환경을 확인하고, 필요한 AI 개발 구성을 추천·생성·적용 안내하는 웹 서비스다. 사용자는 자신의 프로젝트 정보를 확인하고 필요한 구성·권한·변경 내용을 선택한다.

제품 흐름은 **문서 분석·Profile 확인 저장 → 역할·환경·Capability·추천 → 권한·Preview·최종 승인·다운로드·적용 안내** 순서다. 첫 흐름의 필수 동작·검증을 충족하기 전에 후속 서비스 구현을 앞세우지 않는다. 초기 Client는 Codex 중심이며 정확한 지원 버전·조합은 검증 후 명세화한다. 문서 분석 모델은 Solar Pro 4를 1차 평가하고 운영 채택은 결과로 결정한다.

| 팀 공통 제약 | 적용할 기준 |
| --- | --- |
| 인증·접근 | GitHub 로그인만, 저장소 권한 요청 없음. 본인 소유 프로젝트만 접근하며 직접 API 요청에도 동일하게 적용 |
| 입력 | PDF·Markdown·직접 텍스트, 요청당 하나. 파일 최대 10 MiB = 10,485,760 bytes, PDF 100쪽, 추출·직접 텍스트 100,000 Unicode code points. 공백·줄바꿈 포함, 포함 경계, 자동 절단 금지 |
| Profile | 문서 사실·사용자 수정·미정을 구분. null은 미정, 빈 배열은 명시적 없음. 초안·확인 결과 분리, 미정이 있어도 확인 저장 가능 |
| 복구·보관 | AI 실패 시 기존 확인값 보존, 재입력 재시도와 직접 작성·수정 제공. 원문·추출문은 처리 종료 후 보관하지 않고 Profile·최소 문서 정보·분석 시도·감사는 프로젝트 삭제 시 함께 제거 |
| 환경·추천 | 기획 기반 / 환경 조건 / 기존 설정 확인 수준 구분. 추천 가능·추가 도구 불필요·정보 확인 필요·호환 후보 없음의 네 결과 |
| 권한·설정 | LLM 밖에서 검사. 서비스 내부·Client 정책·외부 실행 구분. 미검증 정책을 적용 완료로 표시하지 않으며 Preview·승인·산출물 일치 |
| 검증과 비밀정보 | 다운로드와 설치·연결·검증을 구분. 확인 주체·범위·버전·시점을 표시. Credential과 식별한 Secret을 LLM·로그·일반 산출물에 넣지 않음 |

원문 삭제 후 보관된 근거 위치는 원문을 다시 여는 기능이 아니다. 외부 AI의 별도 처리·보관 조건을 고지한다. 후속 기존 설정 원문·원문을 포함한 병합본·Diff도 서버에 처리 후 남기지 않고 필요한 경우 재입력받는다.

브라우저 폴더 적용은 선택 확장이다. Local CLI·Shell 자동 실행·모든 Client 지원은 MVP 필수가 아니며 OCR·여러 문서 병합·팀 공유는 첫 기능 범위 밖이다.

## 2. 이 파트의 목표와 경계

- 입력부터 확인·저장, 추천부터 적용 안내까지 연결된 사용자 흐름을 설계한다.
- 미정·실패·확인 범위·권한의 효과를 실제 시스템 의미에 맞는 말로 설명한다.
- 실제 사용자의 어려움을 관찰하고 개발 가능한 화면·문구·상태 기준으로 인계한다.

Designer는 제품 UX·화면·문구·관찰 계획을 담당하고 Frontend가 동작 UI를 구현한다. API·권한·보관·AI 의미를 디자인에서 독자적으로 바꾸지 않으며 A·B·AI와 실제 가능한 동작을 확인한다. 디자인 요청은 앱 소스·설정·설치 승인으로 해석하지 않는다.

각 사례는 시작 조건과 기대 결과를 함께 확인한다. 화면·서버·AI·외부 환경 중 어느 범위에서 실행했는지 기록한다.

| 사례 | 시작 조건·사용자 행동 | 기대 결과 |
| --- | --- | --- |
| D-AC01 | 처음 방문한 사용자가 문서를 제출하려 함 | 지원 형식·한도·외부 전송·원문 미보관을 확인하고 분석 시작을 선택할 수 있음 |
| D-AC02 | DB가 미정인 초안을 확인하거나 AI 분석이 실패 | 미정으로 저장하는 경로와 재시도·직접 작성의 차이를 이해 |

| D-AC06 | 화면·색상 대신 키보드로 주요 흐름을 진행 | 순서·focus·label·텍스트 오류/상태로 행동과 결과를 파악 |

## 6. 착수 순서와 기존 Tasks 연결

1. 기획서·공통 PRD·첫 Spec을 읽고 사용자 흐름·화면·필수 상태 목록을 만든다.
2. A·AI·B와 실제 가능한 의미를 확인하고 Frontend에 첫 흐름의 연결된 화면·문구를 먼저 인계한다.
3. 인터뷰·수동 추천 관찰과 실제 구현 화면의 사용성 평가를 구분한다.
4. 후속 추천·권한·Preview·적용 안내를 설계하고 지원 과제의 기존 방법 비교를 수행한다.

| 작업 묶음 | 기존 Task | 이 파트의 역할 |
| --- | --- | --- |
| 첫 화면 설계·문구·상태 인계 | T014, T024, T029, T032의 선행 디자인 | 코드 담당은 Frontend. 설계 산출물 위치·검토자는 팀 작업 목록에 기록 |
| 접근성·실제 UI 검토 | T035–T036, T040 | Frontend의 동작 결과를 화면·상태·접근성 기준과 대조 |
| 첫 기능 사용성 | T044 | 실제 초보자 5명의 과제·관찰·개입 기준·결과를 주관 |
| 사용자 문제·후속 가치 비교 | 후속 구현 Task 없음 | V1 인터뷰·V2 반례·V6 비교를 준비. 결과를 기능 구현 완료로 집계하지 않음 |

위 연결은 기본 분담안이다. 공통 파일·Task는 구현 담당과 검토 담당을 같은 Tasks에서 확인한 뒤 작업하며 중복 소유하지 않는다. 후속 구현의 Task ID를 임의로 만들거나 현재 T001–T046의 완료 상태를 바꾸지 않는다.

## 7. 전달할 산출물과 완료 기준

- 사용자 여정·정보 구조·화면 목록과 첫 흐름의 연결된 Wireframe/Prototype.
- 정상·미정·빈 상태·로딩·실패·충돌·취소·완료의 화면·한국어 문구.
- 입력·Profile·권한·Preview·다운로드 후 안내의 이해도와 접근성 기준.
- 화면별 목적·진입 조건·데이터·행동·다음 화면·상태·반응형/키보드 동작을 담은 개발 인계 자료.
- 인터뷰 질문·과제·관찰표·실제 결과·개입/실패·개선 우선순위. 결과를 보지 않은 항목은 미수행으로 표시.

V1은 초보자 5명 이상 과거 행동 확인, SC-007/T044는 첫 흐름 5명 중 4명 이상 독립 확인·저장을 목표로 한다. V6는 Client 준비가 된 초보자 8명에게 동등 과제 두 개를 방법 순서를 교차해 제시하며 과제당 최대 40분을 사전 고정한다. 최소 6/8명 독립 완료, 기존 방법보다 낮지 않은 완료율, 양쪽 완료 최소 6쌍의 개인별 시간 비율 중앙값 0.8 이하를 초기 기준으로 한다. 실패·포기·개입을 제외하지 않으며 승인 없는 변경·안전하지 않은 권한 확대는 0건이어야 한다. Prototype 이해도와 실제 제품 사용 결과는 별도 기록한다.

담당 완료와 Feature 전체 완료를 구분한다. 관련 요구·인수 시나리오·계약·필수 검증과 실제/Mock 구분을 갖춰 인계하며, 외부 계정·실제 사용자·운영 환경이 필요한 검증을 추정으로 통과시키지 않는다.

## 8. 후속 명세에서 구체화할 사항

- 구체적 화면 배치·컴포넌트·문구·반응형 기준과 인계 도구/형식. 특정 개인 계정·유료 도구를 필수로 가정하지 않는다.
- 참가자 모집 경로·실제 역할/경험·과제·일정과 개인정보 최소 기록 범위. 외부 모집 메시지 발송은 별도 요청에 따른다.
- 후속 UI가 표시할 실제 지원 권한·검증 상태·환경 정보 계약. 디자인만으로 지원 범위를 확대하지 않는다.

기존 제품 원칙을 다시 미정으로 돌리지 않는다. 확인되지 않은 환경·정책·조합은 확정 추천·생성 대상으로 활성화하지 않는다. 계약 변경은 공통 PRD와 Feature 문서에 먼저 반영하고 영향받는 파트에 인계한다.

## 9. 개발 기준과 함께 볼 문서

개발 기준은 Constitution → Feature Spec·통합 Clarification → Plan → Tasks → 코드 순서다. 공통 PRD와 이 문서는 제품의 맥락·책임을 연결한다. 실제 API·DB·패키지 버전은 아래 기술 문서에서 관리한다.

애플리케이션 구현·설정·테스트 코드 작성·패키지 설치는 대상 작업·계약 영향·검증 방법을 제시하고 구현 승인을 받은 뒤 시작한다. 이 문서 전달만으로 구현이 승인되거나 기능이 완료된 것은 아니다.
